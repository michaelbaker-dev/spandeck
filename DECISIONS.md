# spandeck decisions

Read this before starting any task. It is a condensed copy of the Decisions tab of the
spec doc (https://claude.ai/artifact/QT8LDppx4qGnuttvvMwmPt). Where it disagrees with
anything else in the repo or the Features tab, this file wins. Copied 13 Nov 2026.

## Decisions

- **Rust, our own daemon, written from scratch.** herdr and Wolfpack are read for lessons, not forked.
- **v1 runs on macOS and Linux.** Windows is being added (see Windows, below); platform code stays isolated (`crates/terminal/src/sys/`).
- **Name**: spandeck; daemon spandeckd; the command center is the Control Deck; machines are stations, agents are crew, the event log is the ship's log.
- **Live handoff on upgrade, no per-pane host process.** The old daemon execs the new binary in place (same pid, inherited PTY descriptors). After a crash or reboot each agent resumes its conversation by session id.
- **Stations under the same Tailscale login find each other automatically, and each joins the fleet on the owner's approval, once** (changed 14 Nov 2026; before, they trusted each other with no step; a machine that has not joined is found within 60 s, decided by default on 15 Nov 2026, see A station that is slow or away slows nobody else down). There is one fleet: a station that joins brings its fleet-mates, and a request can be approved at any station (15 Nov 2026). Tailscale identifies a device, not a program on it, so a station also signs its calls with a fleet key and a browser on another device holds a token the owner approved. An agent reaching another station gets only what its task grants.
- **Agent messages are stored records** sent and received through tools (send, inbox, reply, ack), never keystrokes. A typed one-line nudge only wakes an idle agent.
- **A durable task record** exists for delegated, scheduled and recipe work. A pane you are just talking to has none.
- **Workspaces**: the agent you talk to stays in the main checkout; a delegated helper that writes gets its own worktree and branch; review-loop reviewers read a snapshot at the commit; testers read the same tree. Sign-off is bound to the commit reviewed.
- **Shared project memory** (start digest, findings board, automatic capture from hooks) on by default.
- **Session archive**: spandeckd copies every Claude Code and Codex session file as it grows, keeps raw lines plus a normalised copy, keyword search through `spandeck recall`. Own history always searchable; same-project on by default with secrets scrubbed; cross-project opt-in.
- **Standing orders at five layers** (fleet, group, station, project, role), as guidance and as enforced rules.
- **Review loop is the first recipe**: three rounds, stall check, sign-off before push.
- **Activity strip on every pane.** Tree, timeline, heat view are v1.5.
- **Usage per agent** (the owner's request on 14 Nov 2026; before, usage and cost views were not in v1): each pane shows its agent's model, tokens and context, with an estimated cost; the station and the fleet show totals. See Usage and cost.
- **Phone**: status, blockers, approval requests and stop controls; and, since 0.2 (the owner's request on 14 Nov 2026), talking to any pane: a message box that can be typed or dictated into, the keys a phone lacks, fitting the pane to the screen, and starting a pane. In the browser; no native app. Since 15 Nov 2026 (the owner's request): a conversation view of an agent pane, for the phone and the desktop, and on the phone a list of sessions that opens on what needs the owner and what was last active (see The conversation view). Since 16 Nov 2026: a question an agent asks, and a plan it wants approved, are answered there (see Answer in place).
- **Station-to-station SSH** uses short-lived certificates spandeck issues per task (v1.5, with cross-station delegation).
- Not in v1: desktop shell, native iPhone app and widget, Officer of the Deck, fleet updates and channels (of spandeck itself), common config, cross-station delegation, flow view, agent tree and timeline. (OpenCode and Antigravity adapters were on this list until 14 Nov 2026: see Agent programs.)
- **Planned, not built: a browser pane** (the owner's decision on 15 Nov 2026: "add the web page stream to the future plan"). A Chrome runs on the station, beside the agent and its dev server, and what it shows is streamed into a pane of the Control Deck, so it works for any site and from the phone. The agent drives it through tools (open, read, click, type) and the owner watches or takes over. To settle when it is built: the browser has a profile of its own, never the owner's sign-ins; the owner approves which sites an agent may act on; an agent's browser is its own, and another agent reaches it only if its task allows; the streamed page is kept apart from the Control Deck so that a page an agent built cannot act as the owner; what happens on a station with no Chrome. A pane that only frames a web page in the owner's browser was considered and set aside: most sites refuse to be framed, and it cannot see a station's localhost.
- **Tailscale key expiry in the Control Deck: the deck informs and gives the steps; it renews nothing and changes nothing in Tailscale** (built 15 Nov 2026; see "The Performance page and Tailscale key expiry", below; the owner's request the same day: "a Tailscale token expiring and lost access to the machine ... how can we expose this in control deck, either information, or renew or disable token expiration", and the direction agreed then). A machine whose Tailscale key lapses drops off the tailnet. (1) **Information**: each station reads key expiry from its local Tailscale client and tells the fleet, so every station shows the same thing: the days left on each station's tile and on the Performance page, a notice and a phone push at 14, 7, 3 and 1 day and on expiry, still shown for a station that is off, and for the owner's devices that are not stations, the phone above all. (2) **Renew**: the steps, to be done at the machine. (3) **Never expire**: the steps, with a link to Tailscale's admin console; recommended for a machine that is always on and that nobody sits at, not for a phone, and the owner's call for a laptop. (4) **Already expired**: what happened and the ways back, from any device, at the machine, or over its own network. **Planned, not built**, each needing the owner's word: starting a renewal from the deck (Tailscale's help says a forced sign-in may bring the connection down and should not be done remotely; to be tried by hand on a spare machine first), and a "never expire" button (it needs a Tailscale credential that can also remove machines).

## Pre-build resolutions (13 Nov 2026)

- One `spandeck hook` command for every vendor. Claude Code: hooks first. Codex: hooks where accepted, screen detection otherwise; the Codex adapter is fixture-tested and unverified until a live canary runs.
- Remote approval is in v1: the permission hook holds for an answer from the Control Deck or phone, then falls back to the terminal prompt on timeout.
- spandeckd listens on localhost and the tailnet address. Tailnet connections are identified by a Tailscale whois on the real address and must be the owner's login; they then need the fleet key (stations) or an approved token (browsers). Localhost needs a token. Serve identity headers are never trusted.
- Every pane gets a pane-scoped token. Enforced on cross-station calls; advisory on the same station.
- OSC 7501 is read when present, never required.
- The activity strip shows state, current tool and elapsed time, and since 14 Nov 2026 the model and a context gauge (before: no context gauge or cost).
- Fleet, group and station orders live in `~/.config/spandeck/orders.toml`; project and role orders in `.spandeck/orders.toml` in the repo.
- Cross-station in v1: discovery, fleet view, attach, stop, recall search, message relay. An agent's first route to another station needs one approval.
- The v1 enforcement table covers Claude Code and Codex.
- The host's Tailscale; no embedding.
- v1 notifications: one inbox, browser notifications on connected clients, optional ntfy or webhook sink.
- Backpressure: the PTY reader never waits for a client; slow clients are dropped and resynced from a snapshot.
- Every long-lived connection has a heartbeat, and each one drives something the owner sees (16 Nov 2026; before, none had one and a connection that went silent without closing was never noticed). A page asks its station "are you there" when it has heard nothing for a second (while it is looked at), says "no answer" after 1.5 s without one, and makes a new connection after 10 s; a station pings a deck every 15 s and lets it go after 30 s of silence; a connection one station holds to another for a pane is pinged every 2 s from both ends and given up after 6 s. The deck says nothing under 0.3 s, "reconnecting…" to 3 s, the time in amber with "as of 12:01:05" and "typing is off" from 3 s, a bar naming the station from 10 s, and when it last answered from 60 s. See "A connection that has gone silent is noticed, and the screen says so".
- A Control Deck's requests are handled in lanes (15 Nov 2026; before, one at a time): order is kept for what is sent to one pane and for changes to one station; reads may be answered in any order. See "Typing, Stop and Allow never wait behind other requests".
- Command is `spandeck`; the short command is `sd` (chosen by the user on 13 Nov 2026; note it shares a name with a find-and-replace tool some people install).
- Public repo at github.com/michaelbaker-dev/spandeck, Apache-2.0, releases built by CI (the user's decision on 14 Nov 2026; it replaces "local git only until the trademark check"). The trademark check has not been done.
- One size per pane, set by whoever has control; others letterbox.
  - **The rule is the same whichever station serves the deck** (15 Nov 2026, the owner's requirement: "it's all the same view from spandeck ... no matter which machine I'm on"; before, a pane shown through another station did not follow it). The pane's station decides. A browser tab that reaches a pane through another station is a client of its own there (`gw-<serving station>-<the tab's id>`, cut to the letters, digits and `-` and the 64 characters any station takes), where before every tab came as one client, `gw-<station>`, and two windows fought over the size. The serving station also listens to the pane's station's events on that same connection and passes each resize of the pane (size, and which client set it) down the pane's channel, so every deck showing the pane letterboxes or keeps control together, "Take control" works through a gateway, and a phone that watches or fits the pane through one behaves as at the pane's own station. Nothing new is allowed to anyone: the gateway still acts only for the owner's signed-in browser, with the calls it already made (`pane.attach`, `pane.resize`, `events.subscribe`).
  - **With a station on 0.4.0.** As the pane's station: everything above works, since all of it is done by the station serving the deck with calls 0.4.0 already has. As the station serving the deck: nothing changes for decks opened there (its tabs are still one client at the pane's station and are not told of resizes) until it is updated; decks served by updated stations, and at the pane's own station, are right.

## Fleet and device sign-in (0.2, 14 Nov 2026)

- Every station starts as a fleet of one with its own key. `spandeck fleet --join <station>` asks another station for its key; the owner approves there, matching a code shown on both sides. The asking station then replaces its key.
- Calls between stations carry a signature over the exact request, good for two minutes. A task authorization from another station is trusted because the call that carries it is signed.
- A browser on another device asks to sign in, shows a code, and gets a token when the owner approves at a station (`spandeck approve <code>`) or in a signed-in Control Deck. Any station in the fleet accepts the token. It can be revoked.
- Without the key or a token, a device under the owner's login can only ask a station its name and ask to be let in.
- There is no switch that turns this off, in tests or otherwise.

### One fleet: a join is a merge, and a request is answered at any station (15 Nov 2026, the owner's request)

"Should never have multiple fleets, every spandeck should be the same." "Shouldn't all machines get the request? ... you should be able to approve from any machine you're on at the time." What happened: a station that had two fleet-mates asked to join a lone station, took its key and left its mates behind, so there were two fleets.

- **A station that joins brings the stations of its fleet with it**, whichever side asked. After the approval the asking station takes the new key, keeps the old one in `fleet.retired`, and hands the new key to every station of the fleet it was in, in a call signed with the old key (`fleet.rekey`, the call station removal uses, with no station named as removed and the fleet joined named instead). It does so the next time it looks for stations, which it does at once. A station that was off is handed the key when it is next seen at the address it had, for 30 days, exactly as after a removal; after that it joins on the owner's approval. Each station that is handed the key keeps the old one for the same purpose, so a station that only one of them can reach is still told.
- **The key is taken first and the mates are told second.** A station that stops halfway is left with a list of stations still to tell, never with a fleet that moved without it.
- **What joins is whoever holds the old key, not a list of names.** The request does carry the names of the asking station's fleet-mates, so the owner reads "spark2 and 2 other stations (M4-Macbook, LLM-Server) ask to join this fleet" in the notice, under Access and in `spandeck trust`. Those names are text from another machine: cleaned, at most twenty, shown as text, never acted on.
- **Browsers.** A token is made with the fleet's key, so every browser signed in from another device to a station that moves signs in again, and those stations stop listing them. The join dialog says how many stations that is. Browsers signed in to the fleet that was joined are not affected. The station's own Control Deck (`spandeck cc`) is not affected.
- **A request is listed on every station of the fleet.** A station that is asked (by a station to join, or by a browser to sign in) tells the other stations of its fleet, in a signed call only a station can make (`trust.relay`), which requests wait there: the id, the kind, the names, the address it came from, the code, when it lapses. Never the value the asker collects with, and never the key. It sends the whole list again when one is answered, and each time it looks for stations while one waits. Each station lists them in `trust.status` with the station that was asked, raises the same notice, and drops one at the time it lapses.
- **It is answered at any of them.** `trust.approve` and `trust.deny` (the Control Deck, `spandeck approve <code>`, `spandeck deny <code>`) first look for the request at the station they are given to; one that waits at another station is passed to it as the owner's request (`rpc.forward`). The station that was asked decides, and hands over the key or the token as before. Its log says who decided and through which station ("you (via bravo)"); the station the owner used logs that it passed the answer on. The first answer to arrive stands; a later one is told there is nothing to decide, and the request leaves every list.
- **Only the owner answers.** `trust.approve` and `trust.deny` are on no agent's list and no station's, at any station; an agent has no call that reaches another station as the owner. `trust.relay` is a station's signed call, refused from the owner and from an agent: it can only add to or clear what is listed, and what it lists cannot be approved unless the station it names holds such a request.
- **A station on 0.4.0** takes the key when a mate hands it over (its notice words it as a removal, with no station named), and joins a fleet as before; but when it is the one that asks to join, it still leaves its mates behind, and it neither tells its mates of a request nor lists theirs. Update a station before using it to join.
- The ship's log records who asked for a join (`trust.join_asked`), which it did not before.

### The browsers signed in are one list for the fleet (15 Nov 2026, the owner's request)

"It's so important that no matter where I go, it's all the same view from spandeck ... these must stay the same no matter which machine I'm on ... the only thing that would be different would be a machine that didn't join a fleet yet." What was found: each station listed only the browsers approved at it (one station of a fleet listed six, another none), though every station accepts every one of those tokens; and a sign-out was sent once, to the stations that were on, so a station that was off went on accepting the token.

- **One list, the same on every station.** Each station keeps the browsers signed in to the fleet (name, the address it asked from, the station it was approved at, when) and the browsers signed out. Stations exchange both whenever they look for each other, and at once after an approval or a sign-out (`trust.sync`, a station's signed call only: each sends its copy and is sent the other's). A station that was off has both within one look of coming back. Access shows "Browsers signed in to this fleet".
- **A sign-out always wins, and is never dropped while it matters.** The signed-out lists are joined; a browser on the list is refused and listed nowhere. Nothing is ever taken off the signed-out list while the station holds the key that made those tokens, and there is no limit that drops one. The list is kept with the name of that key: once the station holds another key (a station was removed, or the fleet joined another), those tokens are refused for that reason alone and the list starts empty. That is the only time a sign-out is forgotten.
- **Entries say which key made them.** A browser's token is made with the fleet key, so an entry made under a key the station no longer holds is not signed in and is not listed. After a merge the stations that moved list the browsers of the fleet they joined, with its sign-outs (sent with the key); after a removal, only the browser that was given a new token.
- **Entries from before this** do not say which key made them. They stay listed, so that they can still be signed out, with a line saying they may no longer be signed in; one becomes an ordinary entry the first time its token is accepted, and they go when the key next changes.
- **A valid token is always listed.** If a browser shows a token the key made and no station has told this one of it (it was approved at a station on an older version), it is listed from then on as "a browser", first seen at this station, so the owner can sign it out.
- **Going from one station's Control Deck to another's needs no second approval.** Each station's deck is its own web address, and a browser keeps its sign-in per address, so the same phone used to be approved again at each station. A browser's token is already accepted by every station of the fleet. So the station menu has "Open X's own Control Deck", and the deck the browser is signed in to (A) hands X's deck (B) the browser's own token as a message between the two windows:
  1. A opens B's plain address in a new window, in the click itself, and keeps the window. Nothing secret is in the address.
  2. B's page, if it is not signed in and another window opened it, tells that window it is ready. The message holds nothing.
  3. A answers only the window it opened, only when the message came from B's origin, and has the browser deliver the token only to that origin. B's origin is `http://` and the address B gave in an answer signed with the fleet key. A answers once, within two minutes, and sends only a browser's own token, never the station's (`spandeck cc`).
  4. B takes a token only while it waits (30 seconds), only from the window that opened it, asks its own station whether the token is good, and keeps it only then.
- **The token is never in an address** (changed the same day: the first version put it in the address's fragment; a browser records the address it goes to, fragment included, in its history, and may copy that history to the owner's other devices). The only token a deck takes from an address is the station's own, from `spandeck cc` on that machine.
- **What a page the owner opens can and cannot do.** A page that is not the window A opened, or is not at B's origin, is sent nothing, whatever it sends A. A page that opens B's deck itself and sends it a token can only send a token it already holds: B's station refuses any other. With a good one, B shows the fleet in a browser whose owner that sender could already act as, so nothing is gained; this is said here because B does not, and cannot, know who its opener is. A station gains nothing either: B already accepts the token.
- **Where it does not work, the usual request is made instead**, which now shows on every station: a browser that blocks the new window (the deck then says so); a phone's home-screen app or any page with no opening window; a station on an older version. A station serves its deck over plain HTTP at its Tailscale address, and that is the origin used whatever address A's page was opened at (an HTTPS address from `tailscale serve` included). A one-time code made by one station for another to accept was not built: it would be a second way in, to be guarded, for no gain over the token the browser already holds.
- **A station on 0.4.0** in the fleet: it keeps its own list and shows only that; it is told of a sign-out one at a time and only while it is on, as before; a sign-out made at it is taken by the stations that are on and spread by them; a browser approved at it is listed by the others once it is used at one of them. Its deck does not ask the window that opened it, so opening it asks for an approval as before.
- Authority: `device.revoke` is the owner's alone, as before. `trust.sync` is refused from the owner and from an agent.

## Closing every pane, and removing a station (15 Nov 2026, the owner's request)

"I should be able to delete a machine and it should kill all the sessions that are running, or delete all sessions on a machine."

- **Close all panes on a station** (`station.close_all`; the station's menu; `spandeck pane close --all [--station NAME]`). Every pane is ended and taken off the list, as "Kill and remove" does for one. Projects, layouts, history and the archive are not touched. The owner's alone: on no agent's list and no station's; it reaches another station only as the owner's forwarded request, like `station.restart`. The ship's log says who and how many.
- **Ending a pane ends its whole session, not only its process group** (Unix; a change to Kill for every pane). A shell puts a job (`sleep 300 &`) in a group of its own, and that job used to outlive "Kill and remove". Kill now also reaches every process in the session the pane's program started. A program that started a session of its own (`setsid`, a daemon) is still not reached. On Windows the job object already ended the tree.
- **A station is removed by replacing the fleet key, because there is no other honest way.** Every station of a fleet holds the same key, and that key signs station calls and makes browser tokens. A list of removed stations would not stop a machine that still holds a key the others accept. So `fleet.remove` (the station's menu; `spandeck fleet --remove NAME [--stop]`) does this, in order:
  1. The station being removed, if it answers (`station.leave`): closes every pane, takes a new key of its own (a fleet of one), and forgets the other stations, its links to their projects and the browsers signed in to it.
  2. The station the owner is using makes a new fleet key and hands it to every other station that answers (`fleet.rekey`, a station's signed call only, never the owner's or an agent's), then takes it itself.
  3. The removed station is forgotten: the list of known stations, pinned panes and layouts that point at it, its panes in global layouts (a layout left empty goes), project links to its projects, stops and messages waiting for it. Project files in the owner's folders are not changed.
- **What follows, and is said in the dialog before anything is done:**
  - Every browser signed in from another device signs in again, and connections made under the old key are closed at once. The browser that asked for the removal gets its new token in the reply and stays signed in. The token of a station's own Control Deck (`spandeck cc`) does not rest on the key and is unaffected.
  - **A station that was away at that moment keeps the old key.** Until it has the new one it shows as not in the fleet, and the removed station, if it kept the old key, could still act on it. Each station that changed keeps the old key in a private file (`fleet.retired`) for one purpose, never to accept anything (a fleet that joins another one uses the same file the same way): when a station it knew is seen again at the address it had, still showing the old fleet, it is handed the new key in a call signed with the old one. No approval is needed for that, since it is a station the owner already approved. After 30 days it is no longer offered, and that station rejoins with `fleet --join` and an approval.
  - **A station that cannot be reached is removed from the fleet's side.** Nothing is done on it: its panes keep running until someone stops spandeck there. It keeps a key nobody accepts, so it cannot act on the fleet, and it cannot rejoin without a new approval. If spandeck is still running there it is listed again as "not in this fleet", like any machine under the owner's login that never joined.
  - **The vault token is that station's own.** A removed station keeps it and it keeps working there; the owner is told to revoke `spandeck:<station>` at the vault. spandeck does not revoke it: only the vault ends a token.
  - **"Also stop spandeck there and stop it starting at login"** is a tick box, off by default, not offered for a station that cannot be reached. It removes the login service (`systemctl --user disable` and the unit file on Linux; the launchd agent on macOS; the Scheduled Task on Windows) and the daemon then ends by itself. The programs, the state folder and the config folder stay on that machine's disk, and the dialog names them.
  - **Removing the last other station** leaves the station in use as a fleet of one with a new key. **Removing the station in use** is done through another station that answers, which does steps 2 and 3 for the rest; with none in reach the station leaves by itself (it throws its key away), says which stations were not told, and the owner removes it at one of them as well, which is what replaces their key. The only station of a fleet of one cannot be removed from it.
- **What this does not do.** It does not undo what a station did while it was trusted: a machine that was already hostile could have left something behind on the others. Removal is for a machine that is retired, sold, lost or no longer wanted.
- A machine that is not in the fleet and stops answering leaves the list (before, it stayed as "unreachable" until the daemon restarted). Stations of the fleet that are off stay listed, as before.
- Both dialogs name the station and its counts, open on Cancel, and act only on the red button. `fleet.forget` ("Forget this station") stays: it only takes an unreachable station off the list.

## A new pane can continue the last conversation (15 Nov 2026, the owner's request)

"We should have a resume session checkbox when creating a new pane, this way if it's there it would load, if it's not then it just start a new one."

- **`pane.spawn` takes `resume_last`** (the New pane dialog's tick, off until ticked and then remembered: since 15 Nov 2026 as one of the owner's preferences, for every station and browser, before that in the one browser; `spandeck pane new --resume-last`). The agent goes back to the conversation it last used in the pane's folder; with none, a new one starts and the pane says so (`resumed` in the pane and in `pane.created`). A caller's own `resume` id wins. A shell ignores it.
- **The agent's own saved conversations are read, not spandeck's records**, so one started outside spandeck counts. Claude Code: the newest session file in its directory for the folder that holds a message (not an empty file, not a sub-agent's). Codex: the first line of its session files, the 200 most recently started only. OpenCode: its database. Antigravity: none can be found, so a new one always starts. Only read, never changed.
- **Two live panes are never put in one conversation.** One a live pane on the station is in is passed over for the next most recent, or a new one.
- **`pane.last_session`** says what would be continued and when it was last used, before the pane is started. It reads only, and is for whoever may start a pane: on no agent's list, no station's and not the read-only one.

## Themes: how the deck looks (15 Nov 2026, the owner's request)

"I also want to think about custom theme and borders colors etc. … if I create one I like I should be able to set as a theme to reuse." "Ligatures should work, emoji should work, you should be able to customize, or edit these option in a pane or in a layout."

- **A theme skins the whole Control Deck, not only the terminals.** A theme is a set of settings by name: the terminal's colours (background, text, cursor, selection, the 16 colours programs use), the deck's colours (page, bars, buttons, lines, text, the five state colours, the outline of the pane with the keyboard and its width), the terminal's font (family, size, line height, letter spacing, weights, ligatures on or off), the deck's font and size, the cursor's shape and blink, and a contrast floor for terminal text.
- **Three levels, the most specific wins: the deck, a layout, a pane.** Each may name a theme, change single settings, or both; its settings win over its theme, and what it does not say follows the level above. The page's colours and the deck's font follow the deck, or the layout on screen. A pane's own look changes only that pane's terminal and its frame. "Appearance" in the top bar (and in ⌘K), "Appearance…" in a layout's menu and in a pane's menu open the same editor for that level; a layout and a pane can go back to "the deck's".
- **The editor shows the change on the real page as it is made**, in that window only, with a sample terminal; Cancel puts everything back and nothing is saved until Save. It warns, and never blocks, when text has less than 4.5:1 contrast with what is behind it, or two of the state colours (green, amber, red, blue) are close. A look can be saved as a theme under a name, and themes can be duplicated, renamed, deleted, exported to a file and imported from one (spandeck's own format, and other terminals': see Fonts, icons and other terminals' themes).
- **Built-in themes are in the Control Deck's code and cannot be changed or deleted, only duplicated:** Spandeck Dark, Spandeck Light, Solarized Dark and Light, Dracula, Gruvbox Dark, Nord (NOTICE has each palette's licence). **Spandeck Dark is the default and is the deck exactly as it was before themes**, so nothing changes for anyone until they choose. For it the worked-out shades (a pressed button, a chip's border) are the values written out before; for every other look they are mixed from the theme's colours, which is what makes a light theme light everywhere. The outline of the focused pane has width 0 in every built-in theme, because the deck had none.
- **Stored in a document of its own, `look.json`, kept the same on every station** (`look.get`, `look.set`, `look.theme.save`, `look.theme.remove`; `look.push` between stations), by the deck document's rules: only the owner changes it, the station where they did offers it to the others, the newer copy is kept. **It is not part of the deck document, and a layout's look is not written inside the layout**, because a station from before themes (0.3.0) reads the deck document and a project file into the fields it knows and writes only those back: it would drop the themes and, at its next change, push the document without them to the whole fleet. Such a station never holds this document: it is offered only to a station that says it keeps one. The same loss could happen between two later versions, so the document has a format number: a station takes no copy in a format newer than it knows, takes none in a format older than the copy it holds, and does not change a copy newer than it knows.
- **A layout's look and a pane's look are entries in that document**, named `global:<layout>`, `<station>/<project>/<layout>` and `<station>/<pane id>`. So both kinds of layout work the same way, and a pane on a station from before themes can have a look. A pane's look goes when the pane is closed (its station sees to it, and prunes looks of panes it no longer has at its next change; the Control Deck also asks, for a station that does not know how); a layout's goes when the layout is deleted and moves when it is renamed; removing a station forgets its panes' and its projects' layouts' looks.
- **Changing how the deck looks is the owner's.** No agent has a `look.` method, not even the read; another station has only `look.push`, as it has `deck.push`.
- **What is in a theme is data**, since it comes from a file someone imported or from another station. The station checks every value: a colour is `#rgb`, `#rrggbb` or `#rrggbbaa` and nothing else; a number is within its range; a font is a list of at most 8 names of letters, digits, spaces, `-`, `_` and `.`; names and counts are bounded; a setting it does not know is dropped. The Control Deck checks again and applies a look only as the value of a custom property (`style.setProperty`) and as options of the terminal: no style sheet or markup is built from it. A theme's name is put on the page as text.
- **A font is named.** The font setting is a plain list of names. A name is a font installed on the device showing the deck, or one the owner uploaded (next section).
- **Ligatures** are the font's and need nothing added; the switch turns them off with a style on the terminal's rows. **Emoji take two cells** in every terminal (the Unicode 11 widths, from xterm.js's own add-on): before, the terminal gave them one and drew the next character over them. One flaw stays: a character that a variation selector turns into an emoji (❤️) still counts as one cell, which is also what the station's own screen believes.
- **A font change follows the sizing rule.** The client in control of a pane fits it again and tells the station; anyone else only scales what it shows. A resize to the size a client already holds a pane at is not taken as losing control, so two windows that fit a pane alike do not both let go when a font change reaches them at the same moment.
- The deck's own look is also remembered in the browser, so the page (and the sign-in page) opens in it before the station has answered. The colour a phone's home-screen icon was installed with (`manifest.webmanifest`) does not follow the theme.
- **On a phone, Appearance is a sheet, not the editor** (15 Nov 2026, the owner's request: "Can the mobile change colors fonts etc?"; the owner agreed to a small sheet, with colour editing left to a computer). It opens from "⋯" in the phone's top bar (with Usage and Performance, which the bar has no room for) and from "Appearance…" in a pane's menu, in a conversation and in a terminal. The editor is made for a wide screen and is not offered at a phone's width.
  - **The theme chosen there is the deck's, for every device and station**: the built-in and saved themes as swatches, applied at once and saved with the editor's own `look.set`; the sheet says "Changes the theme everywhere". As in the editor, choosing a theme drops single colour changes made on top of the last one; unlike the editor it keeps the deck's single font, size and cursor settings, so a tap on a phone does not undo what was set up on a computer. The 4.5:1 and close-colours warnings are shown under the swatches. A layout or a pane with a look of its own keeps it, and the sheet says so.
  - **The terminal's font is the deck's too**, chosen from what that phone can draw: the theme's font, each family the owner uploaded that has loaded there, and each device's own monospace.
  - **The size of the text is the device's own: one size for a conversation and one for a terminal, in pixels, kept in that browser (`localStorage`) and never sent to a station.** Decided by default: the owner was asked whether a phone's size should be shared and did not answer, and a phone needs another size than a 27-inch screen. **The owner may overrule this**; making it the fleet's would mean two new settings in the look document. It is the third kind under The same view from every station (the device's own), and the sheet says "Only on this device". Bounds: 12 to 24 px for a conversation, 8 to 24 px for a terminal; "Reset to the deck's size" forgets both. They are used only while the deck is shown at a phone's width (760 px or less), so the same browser on a wide window shows the deck's sizes, and the editor on a computer has no such control.
  - **A size is absolute, not a step from the deck's**, so changing the deck's size on a computer does not move a phone that chose its own. A pane's own font size (set on a computer) is likewise replaced on that phone.
  - **With no size chosen, a conversation on a phone follows the phone's own text-size setting where the browser says what it is** (iOS's Dynamic Type through `-apple-system-body`; elsewhere the browser's default font size), within 0.8 to 1.6 times; where it does not say, nothing changes.
  - **One size per pane is unchanged.** A terminal's size on a phone is a font change like any other: a pane fitted to the phone ("Fit to screen", in control) is fitted again and its station told; a pane the phone is only watching keeps its size and controller and is shown whole, shrunk to fit, so there the terminal size changes nothing that can be seen, and the sheet says so. The conversation never attaches, at any size.
  - Before this the phone's terminal was drawn at the deck's size (`termOptions`' "smaller" was never asked for).

## Fonts, icons and other terminals' themes (15 Nov 2026, the owner's request)

"Think about how to setup fonts special characters colors etc." "Ligatures should work, emoji should work."

- **A font file can be uploaded** in the Appearance editor (WOFF2, WOFF, TTF, OTF; 5 MB each, 24 files) under a family name, and a theme then names it like any font. It reaches every browser that opens the deck, a phone too. A family can have several files: regular, bold, italic, bold italic, or one variable file for every weight. Removing a file takes it off every station; the editor first says which themes still name it, and they keep the name and fall back to the next font in their list.
- **Which fonts there are is in the look document** (`fonts`: id, name, face, format, size), so the list is the same everywhere and travels by that document's rules. **That is format 2.** A document is written as format 1 until the first font is uploaded, and never goes back: a fleet with a station from before uploaded fonts keeps sharing themes with it until then, and after that the old station keeps the copy it has until it is updated.
- **The files do not travel in the document.** Each is kept in the station's `fonts` folder (beside `look.json`) under an id that is the first 32 hex digits of the SHA-256 of its bytes. A station that takes a document naming a font it does not hold asks the sender for it, and after every look for stations asks any station that keeps fonts (`look.font.fetch`). What arrives is kept only if its bytes give that id and are in the format the document says. A file no longer on the list is deleted.
- **The file is not trusted.** Only the four formats are taken, told by their first four bytes; size and count are bounded; the name follows the rule for every font name and may not be one that means a kind of font (`monospace`). The station never reads into a font: the browser that draws with it checks it, as it does any web font.
- **Served at `/api/font/<id>`, to the owner's signed-in browsers only** (the token in a header; a pane's token is refused), found by looking the id up in the document, never by making a path from what was asked. It goes out with its font type, `nosniff`, and may be kept by the browser for good, since an id always names the same bytes. The Control Deck makes a `FontFace` object from the bytes; a font's name is never written into a style sheet.
- **Rule 7:** `look.font.add` and `look.font.remove` are the owner's. Another station has `look.font.fetch` and nothing else new. No agent has any of them.
- **A terminal measures again when a font arrives late**, because it measures its cells once, with whatever font stood in. Then the sizing rule, as for any font change: the client in control fits the pane and tells the station, anyone else rescales.
- **Prompt icons and powerline signs are drawn on any device** from a bundled font, last in every terminal's font list: Symbols Nerd Font Mono 3.5.1 (1.2 MB), under the name `Spandeck Symbols`. Its `unicode-range` is only where Nerd Fonts' icons live (the private-use ranges U+E000–E00A, E0A0–E0A3, E200–E2A9, E300–E3E3, E5FA–E6BB, E700–E958, EA60–EC84, ED00–F385, F400–F533, F0001–F1AF0, and the power signs U+23FB–23FE and 2B58), so the browser fetches the file only when such a character is on screen, and keeps it (the file's name has the version in it). The font's ♥ (2665), ⚡ (26A1), ☰ (2630) and angle brackets (276C–2771) are left to the device's own fonts, so it never replaces a letter, an emoji or a box-drawing line. A font earlier in the list that has an icon (a Nerd Font, or Fira Code's own powerline signs) wins.
- **Icons are one cell wide**: the font's glyphs are one em square, shown at 60%. **Powerline separators (U+E0B0–E0D7) come from a second file of 7 KB**, made from the same release by `scripts/make-powerline-font.py`: the same glyphs scaled to a cell 0.6 em wide and 1.2 em tall. A browser draws a fallback font's glyph at its own shape, so without this a separator is half the height of its row. A terminal whose font has an unusual cell (JetBrains Mono's is taller) shows a hairline gap; `font.lineHeight` over 1 does too, as in any terminal.
- **Import reads iTerm2 colour files (`.itermcolors`) and Windows Terminal colour schemes**, alone or in a whole `settings.json` (with its comments; the editor asks which scheme when there are several). They say only the terminal's colours. The deck's are worked out from them: the page is the terminal's background, bars, buttons and lines are steps from it toward the text, the five state colours are the palette's own (the normal or the bright of each, whichever reads better, moved toward the text until it has 3:1), and light or dark follows the background. The result is shown in the editor, unsaved, to be changed and then saved as a theme. An iTerm2 file is parsed as XML, which runs and fetches nothing, and only numbers are read from it; every colour goes through the same check as any theme's. iTerm2's colour space is not converted (P3 values are read as sRGB), and its colour for selected text and its bold colour have no setting here.

## Hiding and showing panes in a layout (15 Nov 2026, the owner's request)

"Having panes show and hide options so you can manage them better, for example if you have a layout of 2 over 1, if you hide the bottom one the 2 top ones would resize to take all the space, if you [unhide] it it will go back to its original size."

- **Hide is on a pane's title bar and in its menu; the layout keeps its shape.** The tree of splits and their sizes are not changed. A hidden pane is left out of what is drawn: a split with one side hidden shows the other side at full size, and one with both hidden takes no room. Show puts the pane back where it was, at the sizes the splits had. "Show only this" hides every other pane of the layout in one step; "Show all" is beside the chips and in the layout's menu.
- **Hiding changes only what is seen.** The pane's program is sent nothing and keeps the size it had: the Control Deck lets go of the hidden pane's terminal as it does of any terminal that leaves the screen, and resizes nothing but the panes that grew, by the sizing rule. When the pane is shown its screen and history come from the station's own copy, which is what a reload gives. A selection, or how far back the terminal was scrolled in that window, is not kept.
- **A hidden pane stays in sight as a chip beside the layout's name**: its agent's icon, its name and its state, and it stands out in amber when the pane needs the owner (red on an error), as a pane's own bar does. The chip shows the pane; the button beside it, or a right-click, opens the pane's usual menu. The list on the left marks the pane "hidden". Approvals, the inbox and notifications are untouched by hiding.
- **The last pane showing cannot be hidden** (its Hide is not offered, and is greyed in its menu), so a layout does not go blank by a slip. Every pane can still end up hidden when the one pane showing is taken out of the layout: the layout then says so, with the chips and a "Show all" button.
- **Saved with the layout, as a list beside the tree** (`hidden`: each entry names a pane exactly as its leaf in the tree does), in the project file for a project's layout and in the deck document for a global one, so it is the same after a reload, on every device and on every station. A layout hides at most 16 panes, each entry is a pane and never a split, and its names are checked like a leaf's. An entry that names nothing in the tree means nothing, and goes at the Control Deck's next save. Duplicating or renaming a layout carries it.
- **A station from before this (0.4.0 and earlier) reads such a layout and shows every pane.** It reads a layout into the fields it knows, so `hidden` is passed over and the layout is not refused; when it next writes that project file or the deck document it writes it without the list, and the hidden panes are showing again everywhere. Nothing else is lost: the tree and its sizes are untouched. This is the loss described under Themes, and here it is accepted because all it costs is pressing Hide again; a layout's look stays in `look.json`, where that loss would cost more. Hiding a pane of a project's layout that is kept on such a station does not last: the pane is back at the next redraw.
- **A hidden pane that is gone for good leaves the layout**, so no chip leads nowhere: a pane in no project that was closed, and a project's pane that is neither running nor one the project starts. The Control Deck does this when the layout is opened, and only for a station that is answering. A pane the project starts that is not running now keeps its chip, marked "not running"; a pane whose program ended but is still listed keeps it, marked "ended".
- **A pane added to a layout goes beside one that is showing**, so it is seen at once. In Arrange only the panes showing are moved about; the hidden ones keep their places in the tree and their chips.
- **On a phone**, where a layout is one pane at a time, a hidden pane is left out of the order that Previous, Next and a swipe go through, and is drawn dashed and dim in the map (not dimmed when it needs the owner). Tapping it there looks at it without changing the layout; "Hide" and "Show" under the map change it, for every device. (Since 16 Nov 2026 the map and Hide open from the one line that says which pane is showing: see The conversation view.)
- Hiding is a change to a layout, so it is the owner's by the methods a layout is already saved with (`project.layout.save`, `deck.layout.save`): no new method, and nothing for an agent.

## The same view from every station (15 Nov 2026, the owner's requirement)

"It's so important that no matter where I go, it's all the same view from spandeck. I hop around across multiple machines and now I see my phone is different from my m5 and that different from rtx6000... these must stay the same no matter which machine I'm on ... I guess the only thing that would be different would be a machine that didn't join a fleet yet."

**The rule: a Control Deck shows the same things whichever station of the fleet serves it.** Whatever the deck shows is one of three kinds, and nothing may be a fourth: kept the same on every station (a synced document, or the roster); fetched from the station that holds it, from every station that answers, with a station that does not answer named as not counted; or the device's own. What is only the serving station's is said to be, by name. A machine that has not joined the fleet is the one exception the owner named.

- **The inbox is the fleet's** (before: the serving station's notices, unread count, "Mark all read" and "Messages to you" only). Each station keeps the notices it raised and the messages sent to "you" there; the deck asks every station that answers, and each entry says which station it is from. A notice is marked read at the station that holds it; "Mark all read" goes to every station that answers. A station that does not answer is named under "Not counted", as the Usage view does, and what it last said stays on screen.
- **A notice raised at any station reaches a deck served by any other at once.** The station that raises one tells the other stations (`notify.relay`, a station's signed call only: refused from the owner and from an agent), and each passes it to the decks connected to it as the same `notify.new` event, with the station it is from. Nothing is stored at the stations told. What is passed is text from another machine: bounded, control characters dropped, a link kept only if it is a place in the deck, shown as text. That an inbox was read is passed the same way. The deck also announces a notice it first sees in a station's list, so one from a station that does not tell the others (0.4.0) is announced at the deck's next look (2.5 s, while the page is in front; not while it is in the background).
- **The synced documents: the newer copy wins, and "newer" is made honest** (`crates/core/src/sync.rs`). The deck document (global layouts, pins), the look document, the agent setup and the owner's preferences are each one whole document, a copy on every station, the newer copy kept. What was wrong: a station only ever offered its copy, so one that had just come back held a stale copy until another station looked (up to 10 s); a change made to it in that time, by the owner or by the station itself when a pane closed, was stamped with the present time and replaced what had been changed while it was away, on every station. Now:
  - **A station takes a newer copy as well as offering its own** (`sync.pull`, a station's signed call only, since the agent setup can hold credentials; a 0.4.0 station has no such call and is read with the call a deck would make of it, `rpc.forward` of `deck.get`, `look.get`, `setup.get`). It does so at every look at the fleet, so at start, and before its own copy is offered.
  - **Before the owner's change to one of these documents is taken, a station that has not looked at the fleet in the last 12 seconds looks first** (it has just started, or the machine slept), and a change waits for a look that is under way. The change is then made to the newest copy in reach.
  - **A change nobody asked for never makes a copy newer.** A pane that is closed takes its own look out of its station's copy only: the stamp stays and the copy is not offered. The other stations drop the entry at the owner's next change to the looks made at that station, or when the deck that closed the pane asks (it does). Until then they hold a look for a pane that is gone, which shows nowhere.
  - **A stamp is later than the clock, than the copy it replaces and than every stamp the station has seen in the fleet**, so a station whose clock is slow does not lose.
  - **Each copy says which stations' changes it holds** (`changes`: per station, the stamp of the last change made there). A station whose copy is replaced by one that lacks a change it held raises a notice naming the station whose change went ("A change to the global layouts and pins made at alpha was not kept"); every station that held it says the same words and the inbox shows them once. A copy with no such record is taken to hold everything up to its own stamp.
  - **The agent setup is saved whole by an editor**, so its save says which copy the editor opened; if the setup was changed since, the save is refused ("not saved: … open it again"). A station that answers a save with "I kept mine" is reported as not saved, never as saved, and its newer copy is taken at once.
  - **What window is left.** It is still last-writer-wins on a whole document; there is no per-item merge and no record of deletions. A change is lost when the same document is changed at two stations and neither had the other's change: (1) both changed while they could not reach each other (one was off or off the network and its deck was used locally); (2) a station was out of reach for less than the 12 seconds and is changed within 10 seconds of coming back; (3) two changes within the time a copy takes to travel (normally well under a second; since 15 Nov 2026 a copy is offered to every station at the same time, so a station that does not answer delays no other station's copy: see A station that is slow or away slows nobody else down). In each case the later change wins whole, the other is lost, and the owner is told which station's change went, unless that copy passed through a 0.4.0 station (which drops the record) or the loss is of something only removed. Per-item merge with tombstones would close this; it was judged too much for what is left, and is the next step if the notice is ever seen in real use.
  - **A 0.4.0 station** reads these documents as before: the stamp and every field it knows are unchanged, `changes` is a field it passes over. It still only offers its copy and stamps with its own clock, so the fault remains at that station until it is updated: a change made at a 0.4.0 station that has just come back can still replace newer work, and because it writes the document without `changes`, nothing is said.
- **A global layout names the same panes on every station.** Each of its leaves names its station (the deck has always saved them so). A leaf with no station, saved through the API or kept from before, used to mean "the station serving this deck", so one layout showed different panes on each station, and a hidden one could be dropped by a deck that looked for it on the wrong station. It now means no station until it is given one, and it is given one once, by the first deck that can tell, which saves the layout: a pane in no project is named by its id, which is its own, so it gets the station it is found on; a named pane gets the one station that has such a pane only when every station of the fleet answers, because a project of the same name may be on a station that is away. Until then the leaf says it was saved without its station, offers the stations that have such a pane, and is never guessed or dropped. Nothing is knowable about where such a leaf was saved (the document does not say), which is why it is found and not assumed. In a fleet of more than one station a pane of a global layout always says "on <station>", not only when it is on another station than the serving one. A project's layout is unchanged: it is kept on one station and a leaf with no station is on that one. A 0.4.0 station reads the saved leaf like any leaf that names its station; its own deck still reads a stationless one as the serving station.
- **The owner at a deck is at a keyboard for every station.** A push (ntfy, webhook) is held back while the owner is at a full client; that used to be known only to the station serving the deck, so the others pushed to the phone meanwhile. The serving station now passes the deck's `presence.touch` (sent at most every 20 s while the owner types or clicks) to every station that answers, as the owner's call through `rpc.forward`, which a station of any version takes; one passed on is not passed on again. Each station still decides its own pushes, by its own `at_keyboard_secs`. What stays the serving station's: a call that changes something also counts as presence there, from a phone too, and that is not passed on.
- **The roster of the fleet's members is the same on every station.** A station used to list the members it had itself seen online, so a station that had never seen C did not list C while C was off, and "Forget this station" took it off one station's list. Each station now says in `station.info` which members it knows (name, address, when it last saw each, and the three things kept to wake or describe one) and which the owner said to forget and when; at every look a station makes its roster the union of its own and what each station of its fleet says, taking a member from whoever saw it last. **Forget is fleet-wide:** the station where the owner forgot one says so, the others read it at their next look (10 s at most; a station that is off, when it is back) and drop it too; a station seen after it was forgotten is a member again everywhere. Removing a station from the fleet marks it forgotten the same way, so a station that was off during the removal does not bring it back. The time of forgetting is set later than any time the station was last seen, so clocks that disagree do not undo it; a forgotten station is remembered as such for 90 days.
  - What a station says about the roster is data. Names and sizes are checked, only those three things are kept, and **an address is taken only if it is one this station would look at by itself**: one in its own config, or a device under the owner's Tailscale login, on spandeck's port. No station can make another send a call, or later a key, to an address of its choosing.
  - **What stays different:** up to one look (10 s) between a change and every station showing it. A machine under the owner's login that has not joined is seen within 60 s (15 Nov 2026; before, 10 s: it is asked at every look for its first minute online and once a minute after that, and at once when the owner adds a machine or joins a fleet). A 0.4.0 station neither tells nor reads a roster: it lists what it saw itself, as before, and Forget there is its own; the other stations still learn the members it is silent about from each other.
- **The owner's preferences follow the owner** (`crates/core/src/prefs.rs`). Each station is its own web address, so what a browser kept for one station it did not have for the next: which parts of the list on the left are folded, and the "Continue the last conversation" tick. They are now in one document for the fleet, `prefs.json` (`prefs.get`; `prefs.set`, the owner's alone; `prefs.push`, a station's only; no agent has any), synced by the rules above. **A document of its own, not a section of the deck or look document:** a 0.4.0 station reads the deck document into the fields it knows and writes only those back, so a preference kept there would be dropped fleet-wide at that station's next change; the look document would need a new format number, which would stop a 0.4.0 station taking themes at all. A new document costs an old station nothing: it is offered only to a station that says it keeps one, and it has a format number of its own. A preference is one of a fixed list, each value checked and bounded; one this version does not know is dropped. What a browser had chosen before becomes the fleet's once, if the fleet has none; the browser's copy remains only as what the page opens with before the station answers, and as what is used when the deck is served by a 0.4.0 station.
- **What is the device's own, and stays in the browser:** the sign-in token and the client's name; the look the page opens in before the station answers; which pane of a layout a phone is showing; a draft in a message box; fit-to-screen; the size of the text in a conversation and in a terminal at a phone's width (see Themes); the user name last typed in Add a machine; whether browser notifications are allowed. None of these is something the owner chose for the deck as a whole.
- **The deck says when the stations do not all run the same version.** The Control Deck is each station's own copy of it, so a station on an older spandeck serves an older deck (a page reloads itself only when the station that serves it changes), and everything in this section holds only between stations that know how. When a station of the fleet runs an older version than the newest one in it, a bar that blocks nothing says which, on every station's deck: when it is the serving station, that this deck is the older one and what is seen may differ; otherwise which stations are behind. It offers the update each station already has in its menu (`station.update`, for the stations that answer; one that is off or needs an update before it can be controlled is updated at that machine), and "Not now", which holds in that page until the versions change. The versions of stations that are off are the ones they last had.
- **Stops are shown from every station, sent to the fleet's members, and timed by the station that is stopped.** No Guarantee under "Stop, pause and offline" is changed; three faults in how they were met are.
  - A stop is kept by the station it was issued at. A deck showed only the serving station's; it now asks every station that answers (`stop.list`), so a stop is on screen wherever the deck is opened, with the station it was issued at. Stops issued at a station that does not answer are said to be not shown.
  - "Stop every agent in the fleet" went to every machine on the list, including one that has not joined; that one cannot take the fleet's calls, so its row said "station unreachable" for ever, which is the state the Guarantees keep for a station whose stop will be delivered. A fleet stop now goes to members only, a stop named for a machine that is not a member is refused with that reason, and a waiting row for a station that is no longer a member is dropped and logged (`stop.dropped`). A member on a version this station cannot otherwise control is still sent the stop, and is tried again like any other.
  - "Applies only to the work that was running when it was issued" compared the issuing station's clock with the stopped station's own times, so two clocks a few seconds apart could miss a turn that was running, or stop one started after. The issuing station now says how long ago the stop was issued (`age_ms`: a length of time, counted on one clock) and the stopped station counts back from its own now. What is left is the time the call takes to arrive, by which the cut-off is late: a turn started in those milliseconds is stopped too. The same for how old a stop is on screen: the station says, and the browser's clock is not compared with it.
  - **What stays the issuing station's:** delivering a waiting stop. If that station is off when the stopped one comes back, the stop waits until both are on; the row says so. A 0.4.0 station stopped by a newer one uses the issuing clock's time as before; a newer one stopped by a 0.4.0 station does too.
- **A stop is sent to every member at once, and aimed at the moment it was pressed** (15 Nov 2026; step 1 of the performance and continuity plan, `crates/core/src/stops.rs`). No Guarantee under "Stop, pause and offline" is changed. Measured before this: a station that answered waited 5.01 s behind one that did not, and a request written before a link was cut was applied 14 s late and stopped a turn started 6 s after the stop.
  - **At once.** This station's agents, the rows, and every other station's stop are started together; each station has its own five seconds, and none waits for another or for the database.
  - **The cut-off is the moment the stop was accepted, converted at each send to the stopped station's clock** (`cutoff_ms`, beside `age_ms`). The row keeps only that moment, on the issuing station's clock, as before. The difference between the two clocks comes from the standing readings (`station.hello`, taken at every look) only when the newest is under 15 seconds old, the one before it agrees to within 250 ms, and its age by the station's own clock matches its age by the clock that only runs forward; otherwise, and always when an earlier send of that stop failed (the station was away, or the first request may still be on its way), the station is asked its clock first and the stop follows on the same connection. The stopped station stops a pane whose work began at or before the cut-off, by its own clock, whenever the stop arrives.
  - **How right:** to half the round trip the clock was read in, plus any step either clock made after the reading (at most 15 seconds before the send; a step between two readings, or of the issuing station's own clock by more than two seconds, forces a new reading). If the issuing station's clock is set while a stop waits for a station that is away, the cut-off moves by that much: the row holds a time on that clock. The stopped station never takes a cut-off to be later than counting back by `age_ms` gives, so a wrong reading cannot stop more late-started work than the old rule did.
  - **When the work began** is the later of the last prompt a hook reported and the pane last going from idle to busy (kept in the pane's record from this version on). So an agent with no prompt hook is judged by when it became busy, and work that has changed state since (working, then asking the owner) is still the same work; counting back by age missed that. Where neither is known (a pane busy since before this version, with no prompt hook), the work is stopped. A pane made after the cut-off is never stopped.
  - **Once.** The ids of applied stops are kept in memory in front of the database's record of them, so a second arrival is not a second stop when the database cannot be written. **States only move forward:** requested, unreachable, confirmed; a failure that comes in after a station confirmed changes nothing.
  - **The row and the stop at the same time.** A stop is applied and sent whether or not its row can be written. The database is given one second; a row not written by then is held in memory, written by the stops task when it can be, and shown meanwhile as "waiting for golf · not yet saved on spark2" (`saved: false`): if the issuing station's daemon ends before it is written, that stop is not delivered. A row that is written survives a restart and an upgrade, as before; one that is not yet written is now carried through an upgrade too, and written by the image that takes over (see Nothing waits for the database).
  - **Waiting stops are delivered by a task of their own**, every 2 seconds and at once when the list of stations changes, every station at the same time; no longer inside the twice-a-second work.
  - **A station one version behind** does not announce `stop_cutoff` (`caps`, in `station.hello` and `station.info`): it is sent `age_ms` and nothing is asked of it first, exactly as before; a stop it issues carries no cut-off and is applied by its age, as before. `[flags] stop_cutoff = false` makes a station behave so in both directions.
- **Smaller things made the same.** A station's "working" and "need you" counts on its tile and in the list are counted from the pane list the deck has just fetched from it, as the top bar's count is (before: from what the serving station last heard, up to 10 s old, so two decks disagreed). An uploaded font the serving station does not hold yet is fetched through any station that has it (`look.font.fetch`), so a theme's font does not show on one station's deck and not another's. An action in ⌘K that acts on one station names it ("New pane on spark2…").
- **Fetched from the station that holds it, from every station that answers** (and so the same on every deck, with a station that does not answer named or shown as unreachable): panes, projects and their layouts, tasks, recent messages, approvals, the inbox and messages to the owner, stops, usage, vault state, agent versions.
- **Still the serving station's own, and said to be:** Add a machine, Wake and Start act from the station being used (by design: a password or an SSH connection never passes from one station to another), and their dialogs name it; which browsers are signed in is listed per station today (being made one list for the fleet separately); standing orders above the project level are each station's `orders.toml`; the Agent setup panel reads agent versions from the serving station's last look.
- **What can still differ between two decks, in one place:** (1) for up to one look, 10 s: the roster, a forgotten station, and a synced document a station could not be given at once; (2) for up to 2.5 s, the deck's own refresh: everything fetched (since 15 Nov 2026 a station's answer is put on the page when it comes, so one station's is never held back by another's; every fourth round, 10 s, the deck asks each station for everything, compares it with what it holds, repairs a difference and counts it as a correction on the Performance page: see The deck asks each station one question); (3) a station on 0.4.0 keeps the old behaviour for whatever it serves or stamps, until updated, and the deck says which stations those are; (4) the three cases under "What window is left" where one of two changes to the same document is lost, which the owner is told of.
- **One thing every station raised is one entry.** A request to be let in is raised at each station; the deck shows notices with the same kind, title and text and no pane as one, naming the stations, announces it once, and marks every copy read.

## The Performance page and Tailscale key expiry (15 Nov 2026, the owner's request)

"Control deck should have a performance page that you can see across the fleet." "A Tailscale token expiring and lost access to the machine, how can we expose this in control deck, either information, or renew or disable token expiration." This is step 0 of the performance and continuity plan: it measures and shows. It changes nothing about how Stop, Pause, approvals, input, messages or hooks behave.

- **Each station counts for itself, always, in memory** (`crates/core/src/perf.rs`). How long requests took, by the way they came in (a Control Deck, the local socket that agents and the command line use, another station, plain HTTP); how long a deck's request stood behind the ones before it on its connection; the five slowest of the last five minutes, by method name and never with what they carried; how late the twice-a-second work ran and how long it took; how long a look at the fleet took; clients repainted because they fell behind a pane; a message from sent here to stored there, and from stored here to its agent being told; and per other station: the round trip of the unsigned `station.hello`, every call's time, calls that failed and how, the difference between the two clocks, and when the link last changed. Figures are of the last five minutes (ten-second windows). Nothing is written to disk, and nothing a station decides reads a counter. Restarts and their reasons come from the ship's log, which now also records a start (`station.started`: the first, after a stop, or after ending without one) and a stop on request (`station.stopped`).
- **`perf.get` is the owner's and a station's, never an agent's** (rule 7), and not on the read-only list: call timings show when other projects are busy, and it carries the Tailscale list below.
- **The page is the same from any station** ("Performance" in the top bar, the station menu, ⌘K, and a button on the phone's list; `#/perf`). Every number is asked of the station that holds it, from every station that answers. One that does not answer is "not answering", one on a version from before this is "not reported (its version)", and neither is ever shown as zero. Each station has one sentence, the first that applies: not answering; clock differs; Tailscale key expired or within 14 days, or Tailscale signed out or not running; restarted three times in an hour; its periodic work ran 250 ms late; a link's round trip over 150 ms at the 95th percentile; messages waiting over 30 seconds; else "fine". Stations send numbers; the page writes the sentence. Then a table of stations, a grid of links (each station's own view of each other), the slowest requests, restarts, Tailscale keys, and what this browser measured itself (key to echo for panes it controls, reconnects, how long its refresh takes, and since unit 06 how many questions the refresh asked in the last minute and how many corrections its check made), which is the device's own and is sent nowhere. The button carries a dot when a sentence is not "fine"; for that the page's question is asked once a minute while the page is closed, every four seconds while it is open.
- **First version.** No charts and no history beyond five minutes. Direct or relayed is what the local Tailscale client says of a link in use, and "path not known" otherwise. The switches of later steps are not there because those things are not built. (The database's figures were added with its writer, the same day: see Nothing waits for the database.)
- **A clock that differs is said to be that.** Two stations whose clocks were more than two minutes apart listed each other as unreachable, and a call answered "not in this fleet". The rule stands: such a call is refused. But `station.hello`, which needs no signature, now says the station's clock, so each works out the difference (the reading from the shortest of the last eight round trips, not used after a minute); a refusal of a signature that was made with the fleet's key says "clock" (to no other caller: any other signature is refused as before); and the station is listed as unreachable with the reason, on its tile, on the phone, on the Performance page and in `spandeck doctor`, where a difference over 30 seconds is already mentioned. Wake and Start are not offered for it: the machine is on. A station that was never seen before and is refused for its clock is now listed, where before it did not appear at all.
- **Tailscale key expiry, step 1: information.** With discovery on, a station reads `KeyExpiry` and `Expired` from the `tailscale status --json` output it already fetches at every look (`crates/core/src/tailnet.rs`); with `discovery = false` it asks Tailscale nothing and says "not read here".
  - **Whose keys.** Every station of the fleet, and the owner's other devices (same login, not tagged) that expire within 30 days or did in the last 30. A station's key is looked up in the local client's list by the Tailscale id that station gave (`tailnet.report`, asked when a station is first seen and then once a minute), so it is still shown, and still current, while the station is off; where the local client does not list it, what the station last said of itself is used, and that is remembered across a restart.
  - **Where.** A chip on a station's tile and in the phone's list from 30 days (amber) and from 7 days or expired (red); a line in its menu; the Performance page; `spandeck doctor` on the machine itself; and in the top bar, "This device's Tailscale key expires in N days", when the device the browser is on (the station tells the page which Tailscale device its connection comes from) is within 14 days. Each opens the steps (below). A station whose key has expired says so in place of "unreachable", and Wake and Start are not offered: the machine is on, and both would fail after a wait.
  - **Notices** at 14, 7, 3 and 1 day and at expiry, for each station and for each device that opened a Control Deck at any station in the last 30 days (a station remembers the Tailscale address a deck connects from, and says so to its fleet in `tailnet.report`). Every station raises it in its own inbox in the same words, which name no "this station" and give the date in UTC, so the deck shows one entry (as for a request to be let in). What was said is kept in the station's key-value table, so a restart does not repeat it; a station that was off says the level it finds when it is back, once. **One station pushes:** the one whose name sorts first among the stations it sees online that can tell, itself included; the others mark theirs "left to another station". Each decides alone, so a fleet split in two may push twice. The push follows the notification settings every other notice follows: sent only where an ntfy or webhook sink is set, and held back while the owner is at a keyboard. With no sink set, which is the default, nothing is pushed.
  - **Who may read it.** The list of the owner's devices, their addresses and expiry dates is in `perf.get`, `tailnet.view` and `tailnet.report` only: the owner's and a station's signed call. None of it is in `station.info` or `fleet.view`, which an agent or a read-only caller can read; `station.info` says only that the station answers these calls.
  - **Not built:** starting a renewal from the deck, and a "never expire" button.
- **Tailscale key expiry: the steps, and the sign-in address** (15 Nov 2026; the owner agreed: renewal steps, never-expire by a link to Tailscale's admin console and not by a credential, and plain steps for a machine that has already expired).
  - **spandeck does none of it.** No renewal is started or automated, no setting of Tailscale's is changed, and no Tailscale credential is held anywhere. The deck gives steps and links; every step is the owner's.
  - **The words and their order are Tailscale's**, from its key-expiry help (https://tailscale.com/kb/1028/key-expiry, read 15 Nov 2026; "Last validated: Jan 5, 2026"): the Machines page of the admin console, the row of the device, the menu at the far right of it, and there "Disable Key Expiry", or for an expired device "Temporarily extend key" ("only appears for devices with expired keys"; "The key will be extended for 30 minutes"; then sign in again at the machine "or disable key expiry for this device within that window"), or "Reauthorize machine" where Tailscale offers that in its place. At the machine: `tailscale up --force-reauth`, which "might bring down the tailnet connection and thus should not be done remotely over SSH or RDP", so the deck says to do it at the machine.
  - **Before expiry**, two ways: stop it expiring, from any device (three steps and the link), or renew it at the machine. Then which one: stop it on a machine that is always on and that nobody sits at (Tailscale's help names "trusted servers" and devices "that are hard to reach"); a laptop is the owner's call, since one with no expiry stays on the network if lost until it is removed; a phone keeps its expiry, and for a phone or tablet (iOS, Android) renewing in the app is listed first.
  - **After expiry**, three ways, in this order: from any device, extend the key in the admin console and within the 30 minutes disable expiry or sign in at the machine; at the machine, sign in; and for a station, over its own network: `ssh` to its last address there and sign in again, which that connection survives because it does not go through Tailscale. The steps always say to extend first: Tailscale's help does not say whether "Disable Key Expiry" alone brings back a key that has already expired.
  - **The links.** `https://console.tailscale.com/admin/machines`, which is the address Tailscale's help gives (`login.tailscale.com/admin/machines`, which the notices name, still answers: it asks for the sign-in and carries that page along as where to go next); and, in the steps for an expired machine, the same page with `?q=disabled%3Aexpired`, a filter and a form of address that Tailscale's help on filtering documents. Tailscale documents no address for one device's page, so none is made, and no device's name is put into an address. Links open in a new tab.
  - **A machine's last address on its own network.** Two sources: the endpoint the local Tailscale client is using for the device when that is an address of a private network (`CurAddr`; kept in memory per device while the client lists it, since an expired machine has none), and the station's own private addresses (`Self.Addrs`), which it says to its fleet in `tailnet.report` and which the others remember with its key across a restart. At most three, the one seen here first. A public address is left out: it is a router's. They are in `tailnet.view` and `perf.get` only (the owner's and a station's), never in `station.info` or `fleet.view`.
  - **Signed out, or its own key expired: the machine's own deck says so**, in a bar above everything: the machine is off the tailnet, the deck opens only there, the agents keep running. Where the Tailscale client offers a sign-in address (`AuthURL` of the status output) the bar gives it as a link and as a QR code drawn in the page (`crates/web/assets/qr.js`; the address goes to no outside service), so it can be finished on a phone; where it offers none, the bar says to open Tailscale and sign in, or to run `sudo tailscale up` there. The bar goes by itself once the client is signed in.
  - **Who is given the sign-in address** (`tailnet.signin`): whoever opens it chooses the account the machine joins. So it is given only to the holder of the station's own token (the deck `spandeck cc` opens on the machine, and its command line), and only while the client is signed out or its key has expired: not to a browser signed in from another device, not to another station, not through a request passed on from one, never to an agent (rule 7). It is in no event, no notice, no log entry, and not in `tailnet.view`, `tailnet.report` or `perf.get`. Only an `https` address is ever made a link. (The brief asked for "a connection from loopback"; the method cannot see the connection's address, and the station's own token is what a deck on the machine holds. While the client is signed out, no other device reaches the station over Tailscale at all.)
  - **A station on 0.4.4** serves its own deck as before: the step-0 dialog without links, and no bar. In a fleet with newer stations nothing is asked of it that it lacks; it says nothing of its own addresses, so the steps for it give only an address a newer station has itself seen it at, or say that none is known. The notices keep their words, so one raised by both versions is still one entry.
- **A station on 0.4.2 in the fleet.** It has no `perf.get`: its row says "not reported (0.4.2)". Its `station.hello` says no clock, so a difference with it is not known and it reads as unreachable, as before. It says nothing of its own key and raises no notice; the other stations still show its key when their own Tailscale client lists the device at its address, and still warn. It is never the one that pushes. Its own deck has no Performance page.
- **Cost.** Recording is three atomic operations (measured: 1,000,000 samples in 10 ms with the time given and 50 ms reading the clock each time, so about 50 ns a sample, on the machine it was built on). A Control Deck's requests now pass through a queue of 64 between the socket and the loop that takes them, so that each can be stamped on arrival (one at a time when this was written; in lanes since, see "Typing, Stop and Allow never wait behind other requests").

## Nothing waits for the database (15 Nov 2026, the owner's request)

"Low latency, high performance." This is the database part of step 1 of the performance and continuity plan (`crates/core/src/db.rs`). What was measured on 0.4.2 with the station's database held locked by another program for 12 seconds: one keystroke took 10 s, a hook 10.3 s, starting a pane 10 s, and that pane's record was never written, so the pane would not have come back after a crash. Measured after, same lock: a keystroke and its echo under 50 ms, a hook 7 ms, a pane started and answered for after the one second the database is given (told "not saved"), and its record written when the lock went. No Guarantee is changed, and no migration is added.

- **One thread writes, and nothing typed, stopped or answered waits for it.** The station's database has a connection that writes and one that only reads, so a read never stands behind a write that waits for a lock. What is written falls in four kinds:
  - **The ship's log is best effort** (and so are the notes a hook captures for project memory). An entry is handed to the writer and never waited for. 10,000 may wait; when more arrive the oldest are dropped and counted. `log.query` shows what still waits over what is written.
  - **Changes of state are kept until they are written**: a pane's record (its pause and holds included), a pane closed, a stop this station issued and the record that a stop was applied here, an approval asked for, answered, expired or cancelled, a notice, how far a conversation was read, when the station was last running, what it knows of the fleet's Tailscale keys and roster. Each is made in memory first, held as the newest state of that thing, written ahead of the ship's log in the order the changes were made, and tried again every second until the database has it. An answer to an approval is never replaced by an expiry that came after it.
  - **What the owner is answered about says whether it is saved.** Pause, an answer to an approval, a stop, and a pane started or closed take hold at once; their answer then waits for the database for at most one second and carries `saved: true` or `saved: false`. In ordinary running that is a millisecond or two and the record is written before the answer, as it always was. `saved: false` means held in memory and still being written: if the station's daemon ends before it is written, a pause is not kept (the pane comes back not paused), a pane just started is not started again and one just closed is listed again, who answered an approval is not recorded (the agent already has its answer), and a stop still waiting for an unreachable station is not delivered. Nothing is ever reported as saved before it is.
  - **A message is stored before its sender is answered, as before** (`msg.send`, `relay.accept`): the caller's own transaction, and a failure is told to the caller. It now asks for the write lock at its start, so it waits up to five seconds for another program's lock where it used to be refused in a moment; while it waits, the thread it runs on is given up to other work.
- **Reads never go backwards.** What is not written yet is laid over what the database gives: `approval.list` (and a pane's conversation view), `stop.list`, `notify.list`, `log.query`, and the values the station reads back itself. Panes were always listed from memory.
- **When the database takes nothing.** After 30 seconds of failed writes, or with 1,024 changes of state waiting, the station says it cannot write its database: one notice ("alpha cannot write its database", raised once, and listed although it cannot itself be written yet), an entry in the ship's log when it starts and when it ends (`station.database`), and the Performance page. From then until a write succeeds, what is only worth doing if it is stored is refused at once with "this station cannot write its database; nothing was changed": a new pane, a project added, opened, closed, removed or linked, a message sent, replied to, acknowledged or accepted from another station, a task delegated, given a result, cancelled or continued, a sign-off, a review started or cancelled, a note. **Stop, Pause, Kill, typing, pasting, answers to approvals, hooks, the switches and an upgrade are never refused for this.** At most 4,096 changes of state are held; past that a change to something not already waiting is dropped and counted, so memory is bounded on a disk that stays full.
- **Before the image is replaced, and before a clean stop, the writer is given two seconds.** At an upgrade or a restart in place it is then stopped, and what it could not write (pane records, stops, answers, notices, log entries) travels to the next image in the same private file as the terminals, and is written by it before anything it changes itself. So "a stop request for an unreachable station is delivered on reconnect" holds for a stop that was not yet saved when the station was upgraded. At a clean stop there is no next image: what the database did not take in two seconds is lost, and the daemon's own log says how much.
- **What a crash at the worst moment loses** (the daemon is killed, or the machine goes down, between a change and its write; ordinarily a few milliseconds, longer only while the database is locked or the disk full): log entries not yet written; a pane record's last change (a pane started in that moment is not started again; a pause is not kept); the record of who answered an approval (the row stays "pending" and is expired at the next start); a stop row (a stop already delivered stays delivered, one waiting for an unreachable station is not delivered: the Control Deck said "not yet saved"); that a stop was applied here (the issuing station's retry is then applied again, to work that began at or before the stop's cut-off only); a notice; a read mark (the conversation shows as unread again). Never a message: it was either stored and its sender told so, or refused and its sender told so.
- **The Performance page** has a "Database" figure per station ("0 waiting, 0 dropped"; its title gives the oldest unwritten change, log entries waiting and dropped, tries that failed, writes over 50 ms), and the station's sentence is "cannot write its database" when that is so. `perf.get` carries the figures as `database`.
- **The switch `db_writer`** (`[flags] db_writer = false`, or `station.flags`). Off: the ship's log, captured notes and changes of state are written by the caller that made them, waiting up to five seconds for a lock, as before this. What the switch does not take back: a change that cannot be written is still kept and tried again (before, it was dropped); the two connections; reads laying unwritten changes over the database; `saved` in the answers; the refusal and the notice; the hand-over at an upgrade; a message's transaction taking the write lock at its start.
- **What still waits for the database, and why.** Whatever must be stored before it is answered or acted on writes on its caller's thread, up to five seconds under another program's lock: messages (sending, accepting, marking one announced to its agent, so a hook that has mail to announce waits), tasks (a hook of a pane that is on a task writes the task's state), projects, recipes, sign-offs, posted notes, marking notices read, and the lists the trust rules rest on (browsers signed in and signed out, the fleet's roster when the owner forgets a station). The session archive is a database of its own and is not changed by this.
- **Mixed versions.** Nothing here crosses stations: no new call, nothing new in `caps`, no change to a call's meaning. A station on 0.4.3 in the fleet behaves as before. `saved` is a new field in the answers of `pane.spawn`, `pane.close`, `pane.pause` and `approval.answer` and in rows of `approval.list`; a deck or a command from before passes over it. An upgrade from 0.4.3 hands over nothing unwritten (it wrote everything itself); going back to 0.4.3 after a failed health check loses what this version had not written, since 0.4.3 does not read it.

## After a restart (15 Nov 2026, the owner's request)

"Make sure the plan … covers every situation like reboot, recovery … seamless to the user." "How to bring a session back on line in case of a failure." This is the restart part of step 1 of the performance and continuity plan. What was measured on 0.4.2 after `kill -9` of the daemon: agents were started again in their conversations and nobody was told; 49 of 50 restored agents' first hook failed ("spandeckd is not running"); an approval that was waiting stayed "pending" for ever; a task kept the state it had; a job that ignored hang-up ran on in no pane; a shell vanished from the list; requests to join or sign in were lost at an upgrade; the web server never tried an address again. No Guarantee is changed. "Processes do not survive a daemon crash; agents resume by session id" stands.

- **The order of start-up is not changed: panes are restored, then the station answers**, so no deck ever sees a station with its panes missing (a deck that did would take hidden panes out of saved layouts). The first hook of a restored agent used to arrive before the socket was served. So an agent's hook (`spandeck hook`) that finds no daemon to connect to (nothing listening, or no socket yet) tries again after 25, 50, 100, 200, 400 and 800 ms and then every 500 ms, for 3 seconds in all, and then gives up silently, as before. Only the connection is tried again, never a request that was sent. An agent's tools (`spandeck mcp`) do not wait yet.
- **A waiting approval whose agent went with the daemon is expired** at the start, so it leaves every list (`approval.resolved`, `expired`). One whose pane was kept alive (an upgrade, a restart in place, the pane host) is left waiting for its hook to find it again. (Since 16 Nov 2026 the hook does: see While spandeck is away. One that no hook has come back for 15 seconds after the start is expired then. Before that step was built, the first answer the owner gave such an approval found nobody waiting and expired it.)
- **A task whose agent's program went with the daemon is failed with its resume information** (the Workspaces Guarantee, which until now was met only when an agent ended while the daemon ran): the session, the pane, the worktree, the branch, the reason "spandeck restarted" and when. This holds whether the pane is started again or not.
- **"Continue this task"** (`task.continue`; a button beside a failed task that kept resume information, in a project's Tasks) sets the task back to running and types one line into its pane: "spandeck: your task was interrupted by a restart at 14:02 UTC. Check your last step, then continue." Refused when the pane is not running (bring it back first), is no longer on that task, or is paused: Pause means no new work. The owner's alone: on no agent's list, no station's and not the read-only one; it reaches another station only as the owner's forwarded request.
- **What a pane's program left running is ended only for a pane that is started again.** A job that ignored the hang-up used to run on beside the agent that replaced it, in no pane. The time a pane's program was started is now kept beside its pid; at a start, every process still in that program's session is ended before the pane is started again. Nothing is touched unless all of this agrees: the record has the pid and the start time; if a process has that pid now, it leads that session and started when the record says (else the number was given to something else, and nothing is done); and each process ended started no earlier than the pane's program and no later than 30 seconds after the station last wrote that it was running (it writes that every 10 seconds), so that a session which was given the same number while the station was down is not taken for the pane's. A pane from before this has no start time and its leftovers are not touched until it has been started once by this version (a pane kept through the upgrade to this version is given its start time then). On Windows nothing is left: the job object ends the tree.
- **What a pane that is not started again left running is not touched** (the owner may have detached it on purpose). It is named in the notice and in the log, ten at most, as the program's name and pid.
- **A pane that is not started again stays listed for 7 days as ended**, with the reason: "ended when spandeck restarted at 14:02". Its terminal says so, with **Bring back** (`pane.restart`, as for any ended pane: an agent goes back to its conversation if it has one, a shell is a new shell). Closing it takes it off the list for good. Before, a shell, and an agent with no conversation to go back to, were simply gone. An open terminal for a pane that is no longer on its station says so once, with a Retry button, where it used to ask again every 3 seconds for ever.
- **One notice and one entry in the ship's log per recovery.** `station.recovered` says why (`crash`: the station ended without being stopped; `stop`: it was stopped and started; `upgrade`: terminals were lost in a handoff), how long it was away, and how many sessions were kept, started again, ended or held back, tasks failed, approvals expired, and the leftovers. The notice: "spark2 restarted at 14:02 UTC (away 12 s)" · "4 sessions were started again, 1 shell ended, 1 task failed. They wait for you." Times in it are UTC, since it is written by the station. **At most one such notice in 10 minutes:** a recovery inside 10 minutes of the notice that stands rewrites it ("spark2 restarted 3 times since 14:02 UTC"), shows it as unread again and does not push it a second time. No notice when no session was open. The Performance page shows the last recovery under Restarts.
- **"They wait for you" is true of the agents' own turns and of their mail.** A session that is started again sits at its prompt, nothing is typed into it, and it takes no mail until the owner releases it (the same day: see A stopped agent stays stopped). The notice says so and how to release them, unless that waiting is switched off on the station (`holds.restored = false`), when it says only "They wait for you.".
- **Three restarts in ten minutes: sessions are listed and not started.** The station counts its starts that followed no clean stop (kept in its key-value table; a stop on request resets the count). At the third within 10 minutes it starts no agent: each is listed as "not started again: spandeck restarted 3 times in 10 minutes", with Bring back. Their records stay open, so the next start that is not held back (after a clean stop, or once fewer than three lie within 10 minutes) starts them. Panes kept alive by the pane host are not affected.
- **A request to join or sign in is still waiting after an upgrade or a restart in place.** The daemon that takes over is handed the waiting requests with everything else. They hold the hash of what the asker collects with, never the key, as before; one already answered and not yet collected is not carried, and neither is this station's own request to join another fleet.
- **The web server keeps trying, and follows the Tailscale address.** An address that could not be bound at start is tried again every 10 seconds. With no `web_bind`, at each look at the fleet the station compares its own Tailscale addresses with those it serves: a new one is bound and added to the Host values it answers to (within one look, 10 seconds), one that is gone is no longer served and its Host no longer answered. So a station that started before Tailscale was up is served there without a restart. With `web_bind` set the addresses are the owner's and only the retry applies; with `discovery = false` Tailscale is not asked and nothing is followed.
- **Switches.** `[flags]` in a station's `config.toml` (true or false, a whole number, or a short text; `holds.restored = false`) is read at start, and the owner can set one while the station runs (`station.flags`; kept in the station's state, never written to the config file; the owner's value wins, and taking it back restores the config's). The owner's alone, like `task.continue`. `perf.get` shows what is in force. (When this was written nothing read a flag; `stop_cutoff`, `db_writer`, `holds`, `holds.stopped` and `holds.restored` do now.)
- **`caps` in `station.info`** lists what a station can be asked for that an older one cannot (`task_continue`, `station_flags`); the Control Deck offers such a thing only for a station that says so.
- **A station on 0.4.3 in the fleet.** Nothing here crosses stations but the notice (relayed as any notice is) and `task.continue` through the owner's forwarded request, which a 0.4.3 station refuses as a method it does not have: the button is not shown for it. Its panes, restarts and approvals behave as before; a deck served by an updated station still stops asking for a pane that is gone there. A station taken back to 0.4.3 ignores what this version added to its records, and no longer lists the panes that were ended or held back.

## A stopped agent stays stopped, and what is sent to a pane goes as whole items (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is the input and holds part of step 1 of the performance and continuity plan (`crates/terminal/src/input.rs`, `crates/core/src/holds.rs`). The owner's requirement behind it: stops and pauses must hold through failures, and "100% uptime" must not mean agents waking themselves into paid work. What was found on 0.4.2 and was still so on 0.4.4: a stopped agent was woken again by the next message, by the typed nudge and by its hooks, and the turn it was stopped in was continued with that mail; an agent started again after a crash took mail at once; a stop's interrupt key was written like any input, behind whatever was waiting, and a stop of a program that was not reading was reported like any other. No Guarantee is weakened; four lines are added under "Stop, pause and offline".

**Decided by default on 15 Nov 2026** (the owner said "execute" without answering each question; the owner may overrule each, with the switch named):

- **A stopped agent stays stopped when mail arrives, and is released explicitly.** To overrule: `holds.stopped = false`.
- **A session started again after a crash or a reboot waits for the owner before it takes mail.** The consequence: after a crash at night, agent-to-agent work on that station halts until the owner releases it. So "Release all on this station" is one action, in the Control Deck (the station's menu and the recovery notice), on the phone (the same menu), and on the command line (`spandeck pane release --all`), and a per-station setting turns the waiting off: `holds.restored = false`.
- **A held pane is released by typing into it, Release, Release all, or the command line; never by looking at it.**

**The three marks.** A pane's record carries three marks, each on its own:

| Mark | Set by | What it blocks | Cleared by |
|---|---|---|---|
| `paused` | the owner's Pause | mail, and "Continue this task" | Resume (unpause) only |
| `held_stopped` (who, when, and whether the stop reached the program) | a stop of the pane: Stop on the pane, or a "stop every agent" that hit it (an agent that was idle when "stop every agent" was pressed is not marked: that stop is for the work that was running) | mail | the owner's release |
| `held_restored` (when, and why: `crash`, `stop`, `upgrade`) | the station, for every agent it starts again itself after a restart, a crash, or an upgrade that lost terminals | mail | the owner's release |

- **"Mail" is every road a message has to an agent**: the typed nudge that wakes an idle agent, the notice in the answer to its prompt hook and to its tool hooks, and the turn continued at its end. A pane with any mark gets none of them. The message stays stored, unread and not announced; `held.mail` in the pane's view counts it, and it is announced within a second or two of the last mark going.
- **Clearing one mark never clears another.** A paused pane that is stopped, or started again after a crash, and then released is still paused. Release is not Resume.
- **The marks are in the pane's record**, written like a pause (kept until the database has it; Stop on a pane and Release answer `saved`). They are carried through a restart of the pane's program by the owner, a restart by the station after an agent update, and a recovery. The window is the one "Nothing waits for the database" gives a pause: a station killed before the record is written comes back without that mark.
- **Release is the owner's alone** (rule 7): `pane.release {pane}` and `pane.release {all: true}` are on no agent's list, no station's and not the read-only one; they reach another station only as the owner's forwarded request. The ship's log says who released and how (`pane.released`: `release`, `release_all`, `typed`; `station.released_all`).
- **Typing releases, and it is decided at the pane's station**, so it works from a Control Deck of any version, through any station: `pane.input`, `pane.paste`, `pane.send_text` and "Continue this task" from the owner clear `held_stopped` and `held_restored` before what was sent is queued. **Looking never releases.** Attaching, watching, resizing and reconnecting send nothing that counts. A deck's terminal also sends, as input, things nobody typed: that the window gained or lost focus, the mouse, and its answers to the program's questions (where the cursor is, what kind of terminal it is, its colours). The station tells those apart and they release nothing. (Found while building this: without that, opening a held agent's pane released it, since agents ask their terminal to report focus.)
- **An agent's own turn is not blocked.** A held agent that the owner did not stop mid-turn and that goes on by itself (a prompt already typed) runs; it is its mail that waits. Pause and holds are about new work, as Pause always was.
- **The switches.** `[flags] holds = false` (or `station.flags`): no stop or restart sets a mark and none counts; mail is held back by Pause alone, as before this. `holds.stopped = false` and `holds.restored = false` turn off one mark each; a mark already on a pane stops counting while its switch is off. In the config file `holds = false` and `holds.restored = false` cannot both be written (TOML: one name cannot be a value and a table); with `station.flags` they can. Pause is not switchable.

**What is sent to a pane is whole items in one line.** Keys, a paste, a line of sent text and the mail nudge are each one item of the pane's input, written by the pane's own thread in the order they arrived, from whichever connection or station. A sent line's Enter belongs to its item (the pause before it, 30 ms, and 60 ms after a paste, is the pane's thread's; nobody waits for it and nothing lands between the text and its Enter). (Since 16 Nov 2026 the mail nudge is sent the way a paste is, with the paste's 60 ms: see Every agent can talk to every other agent.)

- **A stop marks its place** the moment its request is read, before anything is waited for. When it runs: an item sent before the mark and not yet started is thrown away whole; the item being written is cut at the next 4 KB, and if it is a paste the program was told is a paste, the end marker `ESC[201~` is written first, so the interrupt key is not read as pasted text; a line whose text is written and whose Enter is not loses the Enter; then the interrupt keys are written, ahead of everything; what was sent after the mark is kept, waits for the stop, and is written after the keys.
- **Whoever sent what was thrown away is told**, as a count and never the content: `{"chan", "input_discarded": n, "why": "stopped"}` on that client's channel for the pane (through a gateway too), and the deck says "Not sent: the pane was stopped before …". The event `pane.input_discarded` carries the counts per client.
- **A program that is not reading cannot be stopped by a key**, because the key cannot enter a full terminal either. The keys are given two seconds. If the terminal has not taken them, they are taken back and never written late (a key that arrived minutes later would interrupt newer work). The stop then says so and nothing reports that pane as stopped: `pane.stop` is refused with the code `not_reading` and "this program is not reading input: Stop could not reach it; use Kill" (an error, so a deck of any version shows it); "stop every agent" lists the pane under `not_reading`, never under `stopped`, and the stop's row says "1 stopped, 1 not reading input and not stopped: use Kill"; the ship's log has `pane.stop_not_reading`, not `pane.stopped`; the pane's mark says `reached: false`, and the pane says the same words. Kill works on such a pane, and the station keeps answering (measured on the machine it was built on: `station.info` answered in under a millisecond with 20 KB waiting in a pane whose program read nothing).
- **What "the terminal took the key" means.** It is in the terminal's buffer. For a program that reads its terminal, that is the interrupt; a program that stopped reading a moment ago with room still in the buffer is not told apart, and is reported as stopped. That the turn ended is still confirmed as before, from the agent's hook or its screen.
- **The mail pump cannot pass a Pause or a Stop.** Its look at the marks is made again with the pane's input locked, and whatever sets a mark takes back a nudge not yet typed. A nudge that is not typed announces nothing.
- **Stops run off the request threads**, since one waits up to two seconds for a program that is not reading; "stop every agent" stops its panes at the same time, each on a thread of its own.

**What the owner sees.** A held pane's bar: "stopped by you at 13:58 · mail is waiting (2)" or "started again after a restart · takes no mail until released", with **Release**; the list on the left marks it "held"; its menu has "Release (take mail again)"; a station's menu has "Release all on this station"; the recovery notice says "They wait for you, and take no mail from other agents until you release them: type into one, or release them all …" and has "Release all on <station>" beside it in the inbox. On the phone the conversation shows a card with the same words and Release, the pane's menu and the station's menu are the same, and sending the agent a message releases it. `pane.list`, `pane.get` and a conversation's `live` carry `held: {stopped, restored, mail}` (null when not held).

**Mixed versions.**

- **A Control Deck from before this (0.4.4)** has no Release button and does not know `held`. Typing into the pane releases it, from that deck too. The pane's `needs_reason` says "stopped by you at 13:58 UTC: it takes no mail until you type into it or release it" when the pane has no reason of its own, and that deck shows it on the station's tile, in the pane list of a phone and as the title of the pane's dot. A refused stop is an error it shows. The recovery notice's words name the command and "type into one".
- **A station from before this** sets no marks and has no `pane.release`: its panes behave as before, a deck offers "Release all" only for a station that announces `holds` in `caps`, and shows Release only on a pane that says it is held.
- **Stops between versions.** `stop.apply`'s answer gains `not_reading`; an issuing station from before passes over it and counts `stopped`, which never includes such a pane. A newer station stopped by an older one marks the panes it stops, as for any stop.
- A station taken back to 0.4.4 passes over the marks in its records: the panes take mail again.

**Not done here, and said so.** The place of a stop was marked where the request is taken up to be run, in the dispatcher, which was the moment it was read while every connection's requests were taken one at a time. Since requests are handled in lanes (the same day; see "Typing, Stop and Allow never wait behind other requests") a Control Deck's connection takes the marks as it reads the stop (`Daemon::stop_marks_unless`, `Pane::mark_stop`, handed to the dispatcher as `AtRead`); the local socket and another station's call are still one request at a time, and mark in the dispatcher. A pane the pane host holds (Windows, and the option elsewhere) is written through the host: a program there that is not reading should be found out the same way, by the two seconds, but that has not been run. Nor has any of this been run on Windows or macOS, or with a real Claude Code or Codex: the scenario tests use the stand-in agent, on Linux.

## A channel number names nothing on another connection (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is unit 02a of the performance and continuity plan (`crates/web/src/lib.rs`, `Channels`), and it goes in before requests are handled in lanes, which would widen the fault. What was measured on 0.4.2: every connection of a Control Deck counted its channels from 1, and a page that comes back after a drop keeps a terminal's old number until its new attach is answered, so a key carrying one pane's old number was written to the pane the new connection had given that number to. No Guarantee is changed.

- **Each connection starts counting at a place of its own**: a number below 2^30 from the system's random source, then one more for each channel, for a pane attached, a conversation watched and a pane or conversation of another station passed through this one alike. It never gives 0 or a number it still has open. The frame is unchanged (five bytes, the number in four), and a page uses whatever number an answer gives it, so a page of any version works.
- **What is sent with a number this connection did not give is refused** ("no such channel"), and a key sent that way, which asks for no answer, goes nowhere: typing, resizing and letting go alike. A number that does not fit four bytes names nothing; it used to be cut down to one that fits.
- **Through another station** the browser's number is the serving station's; the pane's station gives a number of its own on a connection made for that one pane, and the serving station puts its own in place of it both ways. So it is the station serving the deck that refuses a stale number.
- **What is left, and said so.** This makes a wrong pane unlikely, not impossible: a number left over names a live channel only if the two connections started within a few numbers of each other, which is a chance of about one in fifty million for a deck with ten panes open. Unit 03b closes it: the page names each attachment with a number it never reuses and the station takes input only for a name attached on that connection. (16 Nov 2026: done, see A key can never reach another pane.)
- **Mixed versions.** Only the station serving the deck matters. A deck served by a 0.4.4 station still counts from 1, for its own panes and for panes of an updated station shown through it; a deck served by an updated station is right for every pane, a 0.4.4 station's included. A 0.4.4 page loaded before its station was updated works unchanged.

## A key can never reach another pane (16 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is unit 03b of the performance and continuity plan (`crates/web/src/fence.rs`, `crates/web/src/lib.rs`, `crates/web/assets/api.js`, `term.js`). What was measured on 0.4.2: channel numbers restarted on every connection and a page kept a terminal's old number until its new attach was answered, so a key carrying pane B's old number was written to pane C (the audit's gap 13). Unit 02a made that unlikely; this makes it impossible, and adds the rule for a page that comes back while its station still holds its earlier connection. No Guarantee is changed.

- **The page names each attachment, with a number it uses once in its life.** A page starts counting at a random place below 2^30 when it loads and never starts again, whatever becomes of its connections; it sends the number in `pane.attach {chan}` and the station attaches the pane under it. So a number left over from an earlier connection is one the new connection was never given: it names nothing there, by construction and not by chance. The frame is unchanged (five bytes, the number in four).
- **A name is one attachment's.** The station refuses a name that is 0, that does not fit four bytes, or that is attached or being attached on that connection ("channel 1000 is already attached on this connection"). And on a connection whose page said at sign-in that it names its panes (`auth.caps`, `names`), a pane attached without a name is refused, so no pane of that connection has a number the page did not choose. A watched conversation takes no typing and may still be given the station's number.
- **A terminal that has no attachment sends nothing.** When a connection ends, every terminal on the page lets go of its channel at that moment, and has none until its own next attach is answered. One pane is attached by one request at a time, each after the one before was answered (and let go of, if the terminal that asked is gone).
- **The same page come back replaces its own earlier connection, and no other.** A page makes an *instance* when it loads (16 random hex digits, kept in memory only) and sends it at sign-in with its client id. A new connection with the same caller, client id and instance closes the older one before it is told it is signed in; what the older one had read and not yet handed to a pane is thrown away, and what it has not read is never read. This is the case of a half-open link: the page gave its socket up after ten seconds of silence and made a new one, while the station still held the old one with keys on their way in it.
- **A duplicated tab is left alone, and becomes a client of its own.** It copies the client id (the tab's part is in `sessionStorage`) but loads as a page of its own, with its own instance: the two never close each other. (The second review: fenced on the client id alone they would have evicted each other for ever.) So that the sizing rule still holds ("one size per pane, set by whoever has control": each tab is a client), the pages of one browser tell each other who they are (`BroadcastChannel`), and of two with the same client id the one loaded later makes itself a new tab id and connects again under it. A page that finds a tab id already in its storage, and was not reloaded, waits 80 ms for that before it first connects.
- **Through another station, a tab's connection for a pane replaces that tab's earlier connection for the same pane.** The station serving the page opens one connection per pane to the pane's station, every one of a tab's under the one name `gw-<station>-<tab>`. It now says which pane the connection is for and passes on the page's instance (`auth.fence: {pane, instance}`); the pane's station closes an older connection with the same caller, client id, instance and pane. A tab's second pane does not close its first, and two tabs showing one pane do not close each other's. The brief had "client id and pane": the instance is added so that a duplicated tab, before it has renamed itself, cannot close its original's panes.
- **Only a connection that asks is ever closed by this.** A page from before sends no instance and names nothing: it is given the station's numbers (unit 02a) and is never fenced. A gateway from before sends no `fence`. Whose connection it is (the caller it was let in as) is part of what is compared, and only the owner's connections are fenced: an agent's token, or another station, cannot name a page's connection.
- **The switch `deck_names`** (`[flags] deck_names = false`, or `station.flags`; read when a connection begins). Off: the station does not say `names` in `caps`, gives its own numbers whatever a page asks for, closes no connection for another, and sends no `fence` to another station. The page's own rules (a name used once, no channel while not attached) do not depend on it.
- **The Performance page's figures**: `perf.get` has `connections.replaced`, how many connections were closed because their page came back.
- **Mixed versions.** `names` is announced in `caps`; `PROTOCOL` is unchanged; no call was added. A page of today on a station from before (or with the switch off) sends a name the station passes over and uses the number the answer gives, as every page always did; nothing is fenced there. A page from before on a station of today is as before. A gateway of today towards a pane's station from before: its `fence` is passed over there, and nothing is closed. A gateway from before towards a pane's station of today: no `fence`, nothing closed.
- **Tests.** Every change: the fence's table (`fence.rs`: the same page closes its older connection; another instance, another tab, another pane and a connection that did not ask do not) and the names (`lib.rs`). Merge tier, real stations (`crates/cli/tests/typed.rs`): names taken, refused twice and required; a duplicate and its original both connected and both sent the pane's output over four seconds; the same page come back closing its own connection only; a key with the old name reaching no pane before and after another pane is attached; through a gateway, two panes of one tab kept, the same pane attached again closing the tab's earlier connection there, another page's kept; a page from before untouched; and the switch off. Nightly, in a browser: a tab duplicated by `window.open`, both typed into. The brief's "stay up for 10 s" is four seconds here: nothing in the rule is timed, so a longer wait would prove nothing more.
- **Not done here, and said so.** What a closed connection had waiting behind a Stop or a Pause for the same pane is thrown away by three checks that no test reaches (it needs a stop held up for seconds on the connection that is being replaced). A real "Duplicate tab" in a browser's own menu was not driven; the test opens the copy with `window.open`, which copies the session storage the same way. Whether the pages of a phone's browser can tell each other who they are while one is in the background was not measured on a phone; if they cannot, the two stay one client for the sizing rule, as before this, and still never close each other.

## What is typed (16 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the rule this is held to: "This has to be well designed and seamless to the user." This is unit 03c of the performance and continuity plan (`crates/core/src/typed.rs`, `crates/web/src/lib.rs`, `crates/web/assets/typed.js`, `term.js`, `api.js`, `app.js`, the composer in `chat.js`). What the audit measured on 0.4.2 (gap 3): keys typed during a gap were dropped without a word (about 0.8 s at every upgrade or reconnect, about 3 s through another station) or delivered much later in one burst (232 keys up to 60 s late; 2,996 up to ten minutes late through another station, into a shell), and in a two-pane layout the terminal lost the keyboard after a reconnect. Measured after, a real page in Chrome at a computer's width and a phone's (`crates/cli/tests/typed.rs`): typed into a link that stood still for one second, everything arrived, once; typed into one that stood still for five seconds, the pane said after 2.0 s "the last 7 keys typed into here may not have been sent", refused the next keys after their second and a half with their count, and when the link returned said "7 keys typed into here were not sent: they reached alpha 5.0 s after you typed them", with nothing written to the pane, then or later. No Guarantee is changed.

**The promise: what is typed into a pane reaches that pane within two seconds plus the path's round trip, or the owner is told how many keys did not. Never another pane (see A key can never reach another pane), never later, never twice, and never lost without a word.**

**Decided by default on 16 Nov 2026** (the owner said "execute"; the owner may overrule each):

- **Keys typed while the page cannot send are held at most 1.5 s**, then refused where the owner can see it. To change how late a key may arrive: `deck_input.fresh_ms` (default 2000, between 500 and 10000). The 1.5 s is the page's and is under that limit on purpose, so a held key still arrives on time.
- **On a slow but live connection a key is refused when it is older than 2 s plus twice the round trip** the page measured (at most 30 s are added, whatever a page says). The round trip a page reports for this is the middle one of its last 8, or the latest when that is longer, but then counted as at most a second more than twice the middle one: a link that has just turned slow can be typed over at once, and one answer that came late because the link stood still does not make the next keys' limit long.
- **To turn it off:** `[flags] deck_input = false` (or `station.flags`; read when a connection begins). The station then says nothing of `input` in `caps`, takes what is typed as it comes, however late, and its page holds nothing to send later. (In the config file `deck_input = false` and `deck_input.fresh_ms` cannot both be written, as for `holds`; with `station.flags` they can.)

**How old something typed is, without either wall clock.** The page stamps each thing typed with its own forward-only clock (`t`, milliseconds) and numbers it on its attachment (`iseq`, from 1): `{"id": null, "method": "pane.input", "params": {"chan", "data", "iseq", "t"}}`. The station knows how the two clocks stand from the page's pings, which carry the same clock (`{"ping", "t", "rtt", "fresh"}`): the baseline is the smallest "my clock when it arrived, minus its `t`" over the last 8 pings. Something typed is as old as it arrived later than the baseline says a prompt one would have.

- **Only a ping sets the baseline, never anything typed** (the second review: a key held by a page that froze would otherwise measure as fresh). Until a connection has one, what is stamped is refused (`not_ready`); the page pings the moment it is signed in, and sends nothing typed until that ping is answered.
- **The last 8 pings, not all of them.** The brief had the smallest ever seen. Two clocks drift apart over hours, and with the smallest ever seen a page whose clock runs a little slow would, after a day, have every key refused as late. The page pings at least every 5 s while it is looked at, so that a reading is never old on a link that is busy printing (before: only after a second of silence).
- **A page that was not running says so** (`fresh` in its next ping), and the readings from before then count for nothing: its clock may have stood still. **What it sent before that ping is judged by the baseline as it stood when it was read off the connection**, so a key that was in the connection while the page slept is refused, and cannot ride in on the new reading. The page takes itself to have been away when a tick of its clock is more than 2 s late by its own clock *or by the clock on the wall* (on some machines the page's clock stands still during sleep, and a tick after an hour would look on time), and when it is shown again.
- **A number is taken once.** An `iseq` not above the last one taken on that attachment is not written (the page never sends one twice; this is what makes "never twice" a property of the station and not a hope). A second try of something typed by its request id was already refused (A retried change is done once): kept.
- **Judged at the moment it would be handed to the pane**, not when it was read: a key that stood behind a Stop for longer than its limit is not written either.
- **What is not stamped is taken as before**: a page from before, the command line, an agent's tools.

**The limits, and why.**

| What | Limit | Why |
|---|---|---|
| A key (`pane.input`) | 2 s + 2 × the round trip, at the receiving station | two seconds is as long as a person waits before typing it again; the round trip is the link's own time, so a slow link that is alive can be typed over |
| One deliberate act: the message box, the paste dialog, Paste in a pane's menu (`pane.paste`, `pane.send_text`) | 10 s end to end, at the receiving station | the limit of a click (the second review: a dictated message is not a keystroke) |
| Held on the page | 1.5 s and 256 bytes | a reconnect at an upgrade is over in less; under the key's 2 s |
| One thing typed that is a paste (marked as one, or over 64 bytes) | never held | a paste into the wrong moment is worse than a paste refused |
| "Is the link answering?" after a key | asked after 300 ms with nothing back; "not answering" after max(1.5 s, 4 × round trip) ≤ 6 s | unit 03a's own bound; a key now asks at once instead of at the next quiet second |
| A station passing keys on, when the pane's station has said nothing | refused after 3.5 s of silence (2 s between pings + 1.5 s), or 2 s + 4 × that hop's round trip, at most 6 s | the same rule, for the second hop |

**On the page** (`term.js`, `typed.js`):

- **A terminal sends only when it can**: the page is connected and answering, the station has read its clock, and that terminal's own attach has been answered. Otherwise a key is held, and goes out in the order typed the moment the terminal can send, with the time it was typed (so the station counts the time it was held).
- **Then refused, visibly, and never sent later.** When the oldest held key is 1.5 s old, when more than 256 bytes would be held, or when a paste arrives: all of it is refused, the pane says "alpha is not answering: 3 keys typed into web were not sent. Typing is off until it is back." (or "Not connected to alpha: …", "bravo is not showing this pane yet: …"), every further key is refused at once and adds to the count, and the pane flashes at each (a visual bell; one frame for a reader who asked for less motion). When the terminal can send again: "4 keys typed into web were not sent. Typing works again.", for twelve seconds.
- **A key held by a page that then was not running is not sent.** A held key is too old after 1.5 s by the page's clock or by the clock on the wall, whichever says older; and on waking, whatever is held is refused: "This page was not running for a moment: 1 key typed into web was not sent."
- **Keys that were sent just before the link went silent** (after the last thing heard from the station) are counted when the page finds out: "alpha stopped answering: the last 7 keys typed into web may not have been sent. Look at the pane before typing them again." When the same connection answers again, each of them has been taken or refused by the station, and a refusal is said; with a new connection it is not known, and the sentence stands for its twelve seconds.
- **What a station refused is said with its count and how late**: "7 keys typed into web were not sent: they reached alpha 5.0 s after you typed them, and nothing typed is delivered more than 2.0 s late." The station says which (`{"chan", "input_dropped": 1, "iseq", "why": "late" | "not_ready" | "silent", "age_ms", "limit_ms", "station"}` on the pane's channel, one message for each thing typed; never what was typed). The brief had `input_refused: "not ready"` and a count: one message for each numbered key lets the page say exactly which were typing and which were only the terminal's own reports.
- **What a terminal says by itself is not typing**: that the window gained or lost focus, the mouse, its answers to the program. It is never held, never counted as a key and never "not sent" (the page's rule is the station's, `holds::is_typing`).
- **The probe never drops the connection.** A key with nothing back in 300 ms makes the page ping at once; unanswered within the bound, typing is off and said so; any frame turns it back on (unit 03a's state, `api.live`). A link two seconds away each way was typed over without one key refused and without a new connection.
- **The message box, the paste dialog and Paste are one deliberate act** (`sendAct`): the button says "Sending…"; refused, the text stays in the box and the box says why ("Not sent: alpha is not answering. Your message is still in the box."). **When the page cannot know** (no answer within 10 s plus the round trip, or the connection was lost first) it says so and not "not sent": "No answer from alpha within 11 s: this may or may not have been sent. Look at the pane before sending it again." The station refuses it if it arrives more than ten seconds after it was sent, so "may" is the honest word only for those ten seconds; the page never sends it again by itself. (Seen while building: a page gave its silent connection up 9.9 s after Send and said it did not know; the link returned a moment later and the message, not yet ten seconds old, was delivered. "Not sent", which the brief had for a timeout, would have been false, and the owner would have sent it a second time.)
- **A phone typing into a pane it watches** sends each key as a request by the pane's name, stamped the same way (no number: its request is answered). A refusal is an answer and is said on the pane with the count, where it used to be thrown away.
- **After any re-attach the keyboard is where it was.** The terminal that was last typed into, or clicked, gets the keyboard back when its attach is answered and when the page is drawn again for a change of connection, unless a dialog, a menu or a box someone is typing in has it. (Measured before, by the test with the two lines that give it back taken out: after a reconnect in a two-pane layout the terminal no longer had the keyboard.)
- **The Performance page**, "This browser": "Keys not sent", and when last. `perf.get` has `typed: {late, refused, twice}` for each station.

**Through another station** (the pane is another station's; the page is served by this one):

- **This station judges the way from the page**, as above, and passes the key on with the time it was typed by *its own* clock and the round trip so far. **The pane's station judges the whole way** against this station's clock, which it reads from pings this station sends down every connection it holds there for a pane or a conversation (every 2 s; `boot` names the run of the station, so a restarted station is another clock; `fresh` after it was itself not running). One clock per station, shared by its connections.
- **This station does not write a key into a connection that has gone silent** (above): it is refused at once, "2 keys typed into web were not sent: bravo had not answered for 4.1 s." Before, it went into the connection and was delivered whenever that ended.
- **By the pane's name** (a phone's keys, the message box): this station judges and stamps it the same way, and the pane's station refuses it when late by the clock it has read from this station. **With no such reading** (this station holds no connection there for a pane or a conversation at that moment, which no view of the deck that has a message box or a keyboard is without) **it is taken, as before**: the one case left where the receiver cannot tell how old it is, so a request that sat in a link that stood still is still carried out when it arrives. Said so.
- A paste and the Enter typed after it keep their order by every road, as before (Typing, Stop and Allow never wait behind other requests).

**Mixed versions.** `input` is announced in `caps` (the sign-in answer and `station.info`), and only by a station that also answers pings; `PROTOCOL` is unchanged; no call was added.

- **A page of today on a station from before** (or with the switch off): nothing is stamped, numbered or held; a key typed while the page cannot send is refused at once, with the count on the pane (before: without a word). The message box keeps its text and says "may or may not have been sent" when there is no answer, though that station would still deliver it late.
- **A page from before on a station of today**: it stamps nothing, so nothing is judged; as before.
- **A pane on a station from before, shown through a station of today**: this station judges the way from the page and refuses keys once that station has been silent 3.5 s; keys typed in the first 3.5 s of a silence are in the connection and are delivered by that station if it comes back within the six seconds after which the connection is given up. So up to six seconds late there, where it was ten minutes; and nothing once that station is updated.
- **A pane on a station of today, shown through a station from before**: the page is that station's, from before: nothing is stamped.

**Tests.** Every change (`crates/core/src/typed.rs`): the baseline from pings only, the frozen page's key, the limit at several round trips, the last-8 rule and a restarted station, a number taken once. Merge tier, real stations with a link that can be held still (`crates/cli/tests/typed.rs`): refused before the first ping; once and in order; a gap of one second delivered; a gap of five seconds refused key by key with numbers and ages, nothing written; a key in the connection while the page slept, and a clock that stood still; a link two seconds each way; by the pane's name on time and late; the message box at five seconds and at ten and a half; through another station, the same gaps, the silent refusal, a phone's keys ordered with a paste, and a key by name into the gap; and a station with the switch off, alone and behind a station of today. Merge tier, in a browser: the page's rules as plain functions. Nightly, in a browser, with measured times and pictures at both widths: the gaps on the pane; a held key and a page that stood still; the layout's keyboard and the keys of three reconnects; the phone's message box refused, unknown and sent; a slow link typed over. The brief's 60 s stall is 5 s here (the rule has no other threshold between them; the 60 s and ten-minute ages are in the unit test).

**Not done here, and said so.**

- **"Reaches its pane" means: is handed to the pane's own input, in order, at its station.** A program that is not reading leaves it in its terminal, as any terminal does (type-ahead); when that program reads again it reads what was typed. Unit 01d's rule for a Stop is unchanged.
- **A key is timed from when the page was given it.** A key pressed while the page's own script was held up reaches the page late, and is stamped then.
- **A click that changes something else** (rename, close, a setting) is not stamped: unit 03d.
- **Not run:** on a real phone (whether its browser's clock stands still while it is locked, how soon its timers run again, whether its pages can tell each other who they are in the background, what its keyboard's autocorrect and dictation send as one "key": a dictated phrase over 64 bytes into the terminal counts as a paste); on Windows or macOS; against a real 0.4.6 station (the mixed pairs are a station with the switch off); with a machine that really slept.

## Answers are not held back for 40 ms (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is step 5 of the performance and continuity plan (`crates/web/src/lib.rs`, `no_delay`). Measured on 0.4.4, on one machine: the answers to four requests a Control Deck sent together took 41.8 ms, and 0.9 ms when the client acknowledged each piece at once. The station's system holds a small piece back until the piece before it is acknowledged, and a browser's system acknowledges after 40 ms when it has nothing of its own to send. Measured after: 0.7 ms. No Guarantee is changed; nothing but timing is.

- **What a station writes to a connection is sent at once** (`TCP_NODELAY`): on every connection it accepts (a deck's socket, the calls and relays of other stations) and on the socket it opens to another station to show that station's pane or conversation. The calls a station makes to another were already sent so.
- **The switch `nodelay`** (`[flags] nodelay = false`, or `station.flags`). Off: as before. It is read for each new connection, so setting it changes the connections made after that.
- **Mixed versions.** Nothing is announced or asked of the other end. A 0.4.4 station still holds its own answers back, to its decks and to a station that shows its panes; each station stops doing so when it is updated.

## Typing, Stop and Allow never wait behind other requests (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the owner's words behind it: "the way we communicate across panes is too slow". This is unit 02b of the performance and continuity plan (`crates/web/src/lanes.rs`, `crates/web/src/lib.rs`). What was measured on 0.4.2 and was still so on 0.4.4: a Control Deck's requests were taken one at a time, so a key typed into a pane on the station in front of the owner stood behind every question the page had asked of every other station: 294 ms behind one station's seven refresh questions at a 40 ms round trip, 878 ms behind three stations' worth, and with one station hung the first key took 5 s and the next was not echoed in 40 s (the audit measured up to 19.5 s with a link cut). Measured after, same stations, two runs: 1.0 to 1.4 ms in both cases, and with the station hung for 30 s of typing 1.2 to 1.5 ms at the median and 2.6 ms at worst; Stop on a local pane was answered in 1 to 3 ms. With the switch off the old figures come back (295 ms, 885 ms, 5 s and then nothing in 40 s). No Guarantee is changed, no method list is changed, and a request is allowed or refused exactly as before: lanes decide when a request runs, never whether.

**The rule this is held to** (the owner, 15 Nov 2026): "the slow or absent station has to be fixed with the right architecture for a system like this, never to slow everyone else down." So: **no request, on any connection, waits on another station unless it is itself addressed to that station.** It is built as separation, not as tuning: what is for another station has places, a line, counts and deadlines of that station's own, and what is for this station shares none of them. See "Each other station apart", below.

**A connection reads its requests in the order they came and runs them side by side.** The loop that reads waits for nothing. Each request goes by the method that acts, so a call wrapped in `peer.call` or `rpc.forward` is what it carries:

| Lane | What | How |
|---|---|---|
| input | `pane.input`, `pane.paste`, `pane.send_text`, `pane.resize`, by channel or by pane | for a pane here: handed to the pane's own queue in the read loop itself. For a pane of another station by its channel: handed to the connection made for that pane without waiting (`try_send`). Through `peer.call`: one call after another per pane. Never retried |
| urgent | `pane.stop`, `pane.pause`, `pane.kill`, `pane.release`, `stop.all`, `approval.answer` | a task of its own at once |
| write | every other call that changes something | one after another per station, in the order read. At this station, a change that reaches out (below) keeps the order of its own kind only |
| read | the read-only list, and the owner's calls that only read (`rpc::reads`) | at most 16 in flight per connection for this station and 4 for each other station, each station's apart from the others'; answered in any order |
| attach | `pane.attach`, `pane.conversation.watch` | at most 8 in flight for this station's panes and 4 for each other station's; the channel is in the connection's list before the answer that names it is sent |
| held | `wait`, `task.wait`, `hook.ingest`, `trust.approve`, `fleet.join`: calls that wait on purpose | a task each; nothing stands behind them |

`pane.detach`, `pane.conversation.unwatch` and `events.subscribe` are done in the read loop.

**The order that is kept.**

- **Everything addressed to one pane is applied in the order it was read on that connection**: keys, a paste, a line of text, a resize, Stop, Pause, Release and Kill, whether they name the pane or a channel, and whether the pane is here or reached through this station (by its channel, or by `peer.call`). Each station has a line per connection; a request for a pane waits only for what was read before it for the same pane. So a paste and the Enter typed after it arrive in that order although one is a call to the pane's station and the other goes down the pane's channel; a phone typing into a pane it watches (each key a `peer.call`) is not reordered; Pause then Resume ends resumed.
- **"Stop every agent" and "Release all" stand in that order for every pane of their station.** A fleet-wide stop takes a place in every station's line. Each station's part waits for its own turn and gives its place up when that station's part is done (applied here, or answered or given up on there after its five seconds), so neither the stop nor what is typed after it waits for another station. (A fleet-wide stop asked of another station through this one, which no Control Deck sends, stands in that one station's line only.)
- **What is typed into a pane nothing stands before goes straight to the pane**, which is the ordinary case and the reason typing is at once. Something typed while a Stop, Pause, Release or Kill for the same pane, read before it, is not yet done waits for that, and for nothing else: a millisecond or two ordinarily, the two seconds a stop gives a program that is not reading, the second a Pause gives a database that does not take its record. After "stop every agent" that is so for every pane of the station until its agents are stopped. The same goes for Kill pressed after a Stop of the same pane: it follows it.
- **A stop's place in the pane's input is taken in the read loop**, the moment the stop is read (01d's note said it must be). What was sent before it and not started is thrown away, what is typed after it on that connection is kept and written after the interrupt keys, and the owner typing after a stop releases the pane the stop held, in that order. One exception, to keep the order rather than the moment: when something typed for that pane before the stop is itself still waiting its turn (behind an earlier Pause, say), the stop takes its place when its turn comes, after it.
- **Changes to one station are made in the order read.** They do not wait for what is typed or stopped, and a Stop never waits for a change, however long (`station.update`).
- **Not kept:** the order of answers (a page matches each answer to its request by id, and always did); the order between a read and anything; between a change to a station (restart, close or rename a pane) and what is typed into that pane; between requests on two connections, or for two panes. For a pane of another station the line goes by the name the request gives: the Control Deck always sends the id, and a pane named once by id and once by name in the same moment is not known to be one pane (for a pane here it is).

**A station that is slow or hangs delays only what is for it**, and a page cannot make this station hold more than a bounded number of its requests:

- 256 requests of one connection for this station waiting or running; and, counted apart for each other station, 20 reads (4 in flight), 16 changes, 16 urgent calls, 64 things typed, 16 attaches and 16 calls that wait. Each lane has its own count, so the questions a page keeps asking of a station that does not answer cannot crowd out a Stop for it, and nothing that waits for one station takes a place of this station's or of another's.
- **Past a limit the request is refused at once, that request only, and nothing is done**: "charlie is busy: 20 requests from this page are still waiting for it, so this one was not sent. Nothing was changed", with the code `busy` to a page that said at sign-in it knows the word (`auth.caps`), and the code any failed call has to a page from before. The deck shows it where it shows any refused action; a station whose refresh is refused so carries "not answering: as of 5s ago" on its tile (the words until unit 06, the same day, were "not answering: shown from before").
- **What is typed for a pane of another station that takes nothing** used to stop every request of the page once 256 things waited for that station. It is now refused, and the page is told on the pane's channel (`{"chan", "input_refused": 1, "why": "busy", "station"}`): "Not sent: bravo is not taking what is typed. What you type now is not kept for later." Up to 256 things already handed over are still delivered when that station takes them again, late: saying so within two seconds is the next unit's (03). (16 Nov 2026: done; a station of today refuses them when they arrive late, and they are not handed over once that station has been silent 3.5 s. See What is typed.)

**Each other station apart** (the owner's rule above).

- **Its own places, line and counts, per connection.** A call for station S waits only for S's read places (4), its turn in S's line, and S's counts. Reads of this station have 16 places of their own, attaches 8. However many calls wait for S, none takes anything a call for this station or for station T needs.
- **A deadline the connection enforces itself.** A call for another station that has stood 4 seconds behind others for that station is not sent, and is told so ("bravo is slow: this waited 4 s behind what was asked of it before, and was not sent. Nothing was changed"). One that was sent and is not answered in 6 seconds is given up: a read with "did not answer within 6 s", a change with "could not confirm whether pane.spawn was carried out there (no answer within 6 s) ... check before asking again" and the code `outcome_unknown`, the one a retried change has for that. The call underneath has five seconds of its own, and asking a station again about a change whose answer was lost (see "A retried change is done once") happens inside these six seconds, in that station's line and nowhere else: when the answer was lost and the station is there, that takes a fraction of a second; when the station says nothing for its five seconds, the asking again is cut short at six and the owner is told it could not be confirmed, which is what it would have said. So a call for another station costs its caller at most ten seconds, and costs nobody else anything. Something typed for a pane of another station that waits behind a paste or a Stop for that pane is given the same four seconds, then refused on the pane's channel. Attaching has its own limits, as before: four seconds to connect, five for the answer (ten for a conversation).
- **A station that stops answering is known as that, and is then refused at once.** After two calls in a row to a station with no answer at all (no connection, or nothing in the call's five seconds: any call, the look every ten seconds included) it is "not answering" (`FleetState::not_answering`), until the first answer to any call. While it is, a Control Deck's call for it is refused at once ("bravo is not answering (for 7 s now), so this was not sent. Nothing was changed. It is tried again by itself", code `not_answering` to a page that knows it), calls already waiting for it are refused when their turn comes, and one call every two seconds is let through to find out whether it is back. **A Stop, a Pause, a Kill, a Release or an approval's answer for that station is always sent.** Nothing a station does by itself reads this state: a stop is delivered, a message relayed and a document offered exactly as before. The deck shows "not answering: as of 5s ago" on that station's tile.
- **A change at this station that reaches out does not hold up one that does not.** Some changes made at this station wait for other stations or for a service outside: a document every station keeps (`deck.`, `look.`, `prefs.`, `setup.`), the fleet's members and key (`fleet.`, `trust.`, `device.`), `agents.`, `vault.`, `msg.`, `recall`, `context.`, `tailnet.`, `notify.`, linking a project, `station.update`. Each of those kinds keeps the order of its own kind and stands in no line with the others or with the changes that are this station's alone (a pane started, renamed or closed, a task, a note). So two saves of a layout keep their order, and neither a look at the fleet nor a save that is being offered to a station that does not answer delays starting a pane.
- **What was checked, place by place, for anything this station's work could still share with a call to another station:**
  - *The reader's queue of 64.* The loop that empties it waits for nothing but handing what is typed to a pane's own queue, which never waits; a burst of calls for other stations is taken off it as fast as it arrives, each into a task. (With `ws_lanes = false` the loop waits for each request, which is the coupling this unit removes.)
  - *The way out to the browser* (256 messages): the read loop never waits for it (it hands a full queue's message to a task). It is the browser's speed, not a station's.
  - *The connections made for a pane of another station* (one per pane per tab): what is typed is handed over without waiting and refused when 256 things wait; attaching has that station's own places and limits.
  - *`peer.call` and `rpc.forward`*: each runs in a task of its own, with the deadlines above.
  - *Locks:* the connection's lines, counts and list of channels are plain locks taken for a few instructions and never held across a wait.
  - *The HTTP client stations call each other with* is one for all stations, but it has no limit of connections per station or in all, and each call is HTTP/1.1 on a connection of its own or an idle one of that station's: one station's calls cannot make another's wait. Connecting is given 1.5 s, a call 5 s.
  - *The Performance counters* are atomic numbers and two short locks; none is held across a wait.
  - *The stop marks:* fixed, as said below ("Found while building this").
- **Fast tests** (every change): the not-answering rule (after two silences, until one answer, one call in two seconds finds out, a Stop always sent) and the lanes' rule.
  - **The proof** (`a_frozen_and_a_slow_station_cost_nobody_else_anything`, nightly): four stations, one frozen, one two seconds away, the page asking all three others its refresh's seven questions four times a second on the same connection. Worst of each, with every station healthy / with the two bad ones: a key echoed here 4.3 / 4.5 ms (20 keys), Stop here 3.2 / 3.7 ms, Pause here 3.1 / 3.9 ms, an approval answered here 3.7 / 3.7 ms, a read of the healthy station 3.5 / 4.1 ms, a key echoed at the healthy station 3.8 / 3.7 ms (each includes up to 2 ms of the test's own looking). Every one of 266 questions to each bad station was answered, the slowest after 6.0 s; once the frozen one was known not to answer, half the questions to it were refused within 0.6 ms. The test fails if anything local or at the healthy station is more than 50 ms worse than in the healthy run, if a question to a bad station takes over 10.5 s, or if questions to the frozen station are not refused at once.
- **What still couples stations, and whose it is.** Not built here:
  - The page's refresh asks every station every 2.5 s without waiting for the last (unit 06: done the same day, see The deck asks each station one question). The periodic work (discovery, sync, vault, stops) in one loop (unit 07: done the same day). The message relay's pump (unit 08a: done the same day).
  - **In no unit, found here:** (1) a change to a synced document made within 12 seconds of this station starting or waking first looks at the whole fleet (`sync_catch_up`, "The same view from every station"), so that one save waits up to the look's limit for a station that does not answer; it now delays only changes of its own kind. (2) A saved document is offered to the stations one after another, up to 5 s for each that is listed as on and does not answer (said under "What window is left"); the save's answer waits for that. (3) The answer to "stop every agent in the fleet" comes when every station has answered or been given up on (5 s): the stop for this station is applied at once, but the page hears "confirmed" for it only then. (4) The look at the fleet gives a station 2.5 s; a station further away than that is listed as unreachable although its calls would be answered. (5) `not answering` is known per serving station, from that station's own calls; it is not yet a state the fleet shares or the look uses (units 03a and 10 are where heartbeats and peer events belong), and the Performance page does not show it beyond the link's failures it already counts. (16 Nov 2026, unit 03a: the pings on a connection held to that station for a pane now feed it too, so with a pane of it open it is known within six seconds without anyone calling it, and an attach is refused by it like a call. It is still each serving station's own, and the look does not read it: unit 10.)

**With request ids** ("A retried change is done once", the same day; the two were built side by side and joined here).

- **A request on a Control Deck's connection may carry an id** (`rid`, and `again_ms` on a second try, beside `id`, `method` and `params`, as on the local socket), and is then done once by it in whichever lane it runs: the lane decides when a request runs, the id whether it runs again. The sign-in answer says what the station can do (`auth.caps`, with `rid`). An id that is not one is refused before anything else. The page does not send ids yet; the socket takes them.
- **A second try keeps its place in the order** like any request: it stands in its pane's or its station's line. What it was a second try of is answered from what is kept without anything being done.
- **What is typed is never sent a second time, by any road**: a second try of `pane.input` or `pane.resize` for a channel is refused (`outcome_unknown`) for a pane here and for one of another station alike, as it is by name.
- **"Stop every agent" carries both** its places (taken as it is read) and its id's record. A second try takes no marks and no places: it is given the rows of the first, or, with no record of a first, stops as any stop does and takes its places as it runs.
- **A stop's marks and places go with the request to whatever carries it out** (`AtRead`, now part of what a request carries through the dispatcher beside its id), and are let go of at once when nothing does.
- **While an image is being replaced** a change whose mark could no longer be written waits (04a); on a Control Deck's connection it waits in its own line, where it holds up the changes of its kind behind it and nothing typed, stopped, paused or answered. The connection ends with the image, as before.
- **The two lists that say what a read is agree**, and a test holds them to it: whatever a connection answers in any order (`rpc::reads`) is safe to ask a second time (`rpc::repeatable`), and nothing that is done once by its id is taken for a read. (`tailnet.signin`, which only reads, was missing from the second list.)

**When the connection ends**, reads, attaches, `wait` and `task.wait` are ended; everything that changes something runs to its end, as it always did. An attach that finishes after the connection ended is closed again. When the fleet key is replaced, the connection waits up to ten seconds for the calls it is running (the one that replaced the key among them) before it closes, so the answer that carries the browser's new token is sent.

**Found while building this, and fixed:** a "stop every agent" for another station took a place in the input of this station's agent panes and held what was typed into them until that station answered (up to five seconds for one that is away). Marks are now taken only for a stop that is for this station.

**The Performance page** shows, under "Waited in line", how long requests stood before they were begun for each lane, and how many were refused because too many were waiting (`perf.get`: `requests.waited.lanes`, `requests.waited.busy`); and a station's switches.

**The switch `ws_lanes`** (`[flags] ws_lanes = false`, or `station.flags`). Off: a connection's requests are taken one at a time and in order, each waited for, as before, and a stop's place is taken in the dispatcher. It is read when a connection is made, so setting it changes the connections made after that (reload the page); the sign-in answer says which a connection has (`auth.lanes`). What it does not take back: the fix above, and the lists of what a connection has open being shared between its tasks.

**Not changed:** the local socket (the command line, hooks and agents' tools use a connection per call) and another station's signed calls (a request each): both are one request at a time, as before.

**Mixed versions.** All of this is in the station that serves the page. A page loaded from 0.4.4 works unchanged: it never depended on the order of answers, it gets the plain error code where a newer page gets `busy`, and passes over `input_refused`. A 0.4.4 station reached through an updated one gets up to four reads at once from one page instead of one, by the calls it already had; its own decks are as before until it is updated. An updated station whose panes are shown through a 0.4.4 station handles that station's relay connection in lanes too, which changes nothing it can see.

**Not done here, and said so.** The page still refreshed every 2.5 seconds without waiting for the last refresh, which with a station that hangs is what filled its 20 places (unit 06 ended that the same day: a station is asked one question at a time). Something typed for a pane of a station that hangs is still delivered late if that station comes back (unit 03). None of this has been run on Windows or macOS, with a real browser against a station that hangs, or on the real fleet: the scenario tests use throwaway stations on Linux, with one frozen by a signal.
## A retried change is done once (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is the agent-side part of step 4 of the performance and continuity plan (`crates/core/src/rids.rs`, `client.rs`, `rpc.rs`; `crates/cli/src/mcp.rs`). What was measured on 0.4.2: with the daemon away, an agent's tool call failed in under a millisecond with "spandeckd is not running", 9 of 9 during a 2 second outage and 240 of 240 during a minute, and a call already inside the daemon got "closed the connection"; nothing tried again, not even across the 20 ms of an upgrade. A call made through another station whose answer was lost read as "unreachable" although it had been carried out: a pane was started twice by the owner's second click, and an approval's answer was reported as failed. No Guarantee is changed, and no migration is added.

- **A command and an agent's tool wait for spandeck instead of failing.** When nothing listens, there is no socket, or the connection ends before the answer, the call is made again after 25, 50, 100, 200, 400 and 800 ms and then every second: an agent's tool (`spandeck mcp`) for 15 seconds, a command for 5 (it says "waiting for spandeckd…" on standard error after one; `--no-wait` makes one try, as before). `wait` is asked again for the time it has left. A hook is unchanged here (it waits 3 seconds to connect, as since 15 Nov 2026; the hook that can block is the next unit).
- **Every call carries a request id, made once by the process that makes the call:** 128 random bits from the operating system, sent beside the token as `rid` with every try. It is never worked out from anything an agent could predict.
- **What is sent a second time, and what never is.** A request that was never written is simply sent when the daemon is back: nothing had been asked. For one that was written and not answered: a call that only reads, or sets something to what it already is, is sent again. A change is sent again only by its id, with how long ago the first try was written (`again_ms`), and only to a daemon that says on that same connection that it keeps ids (`caps` has `rid`). To a daemon that keeps none, a change is never sent twice.
- **The station that carries a change out keeps the answer for two minutes**, in the `kv` table (no new table): the key is `rid:<who>:<id>`, the value the method, a SHA-256 of the parameters (the same whatever the order of their fields), the state, the answer and the time. A second try from the same caller, for the same method, with the same parameters is given the first one's answer, an error included, and nothing is done again; while the first is still being carried out the second waits for it. (The plan's key had the method in it. It is in the value instead, so that an id used again for another method is refused instead of run.)
- **Who.** `owner` for every one of the owner's clients, whichever station passed the request on, so that a second try that arrives through another station finds the first; `pane:<id>` for an agent, worked out from its token and never from what the request says. A station's own calls keep no ids: message relay and stops have their own records.
- **The same id for another method or other parameters is refused** (`rid_reused`), never answered from what is kept and never run. An id is 16 to 64 letters, digits, `-` or `_`; anything else is refused before the request is looked at. What a caller may call is checked before its id is.
- **A message's id is written in the message's own transaction** (`msg.send`, `msg.reply`): the row and the message are stored together or not at all, and the row's key is the table's key, so a second try cannot store a second message even if everything else here were wrong. Delivery between stations is as it was: at least once, duplicates dropped by the message's id.
- **For every other kept change, "being carried out" is written first and waited for**, a second at most (the wait every answer that says `saved` already has). The answer is written after, without being waited for.
- **Done once, by id:** starting, renaming, setting, restarting or closing a pane, a file dropped on one; `msg.inbox` (it marks what it returns as read, so it is not "a read"), `msg.ack`; `delegate`, a task's result, cancel and continue, a sign-off, starting or cancelling a review, a note; a project added, opened, closed, removed, linked or unlinked, its layouts; the global layouts and pins, themes, the look, uploaded fonts, the owner's preferences; closing every pane, installing or removing an agent's integration, restoring an archived session, waking, starting or forgetting a station, updating or installing an agent program, and a command sent to agents. It is a list of what is kept, not of what is not: a method added later is not kept until someone has looked at what it answers with.
- **Never kept, and never run a second time** (a second try is told `outcome_unknown` at once, and the first runs exactly as before): what is typed, pasted or sent into a pane and a resize; a hook and an agent's reports of its state; `pane.release`, and Pause being turned off (a late second try could undo a Stop or a Pause made after the first); every call whose answer or parameters carry a token, a key or a password (`fleet.remove` and `fleet.uninstall`, whose answer is the browser's new token and whose parameters can be a password; `fleet.add`, a password; `vault.call`, whose answer is a provider's, and the vault's connect, disconnect and rotation; `setup.set`, which can hold credentials for MCP servers); the calls that decide who is trusted (`trust.approve`, `trust.deny`, `fleet.join`, `device.revoke`); an upgrade, a restart, leaving the fleet, and the switches. An answer with a field called `token`, `secret`, `password`, `fleet_key` or `authorization` is not written either, whatever method gave it: a second try is then told only that the change was carried out.
- **Stop, Kill, Pause and an answer to an approval never go through the store and never wait for it.** Kill and Pause being turned on are simply done again. A second try of a stop of one pane looks at the pane's own mark first: stopped since the first try was written means "stopped", with no second interrupt key; no mark (a shell, or holds switched off) means the key is sent again. A second try of an answer to an approval looks at the approval: already answered that way means "done"; answered the other way is refused, as any second answer is. **"Stop everything" with an id is one stop**: the stops it issued are kept under `stoprid:<who>:<id>`, written without being waited for, and a second try is given those rows. With no record of a first try (the daemon died before it was written) the stop is issued again: a stop errs on the side of stopping.
- **Through another station.** The station the owner is using keeps nothing: it passes the id on (`rid` and `again_ms` in `rpc.forward`). When a change it sent may have arrived and no answer came back (not when no connection could be made), it asks that station again whether it keeps ids and sends the request once more with the same id, its own if the caller gave none. One pane, and the answer. If that fails too the owner is told "could not confirm whether pane.spawn was carried out there ... check before asking again" (`outcome_unknown`), not "unreachable". Only what a station answers for by id is ever sent twice; what is typed goes once.
- **"Cannot tell" is said, and nothing is run blind.** `outcome_unknown` is the answer to a second try when: the row says "being carried out" and no try in this process is carrying it out (the daemon ended, or was replaced, in the middle); there is no row and this station has not kept ids, without a gap, since before the first try was written; the first try is said to be more than 30 seconds old; or the method is one that is never kept. "Without a gap" is this process's start, or further back when it took over in place from an image that also kept ids (an upgrade, a restart in place: that image says for how long, and hands over what it had not written). So after a crash or a kill, a second try whose first left no row is not carried out: the daemon that read the first may have died before its mark was written, or may have been one that kept no ids.
- **What a crash at the worst moment does.** `send` and `reply`: the message and its id are one transaction, so a second try finds the row (one message, the same answer) or none (after a crash: "may or may not have been sent: read the thread before sending again"; after an upgrade: it is sent, once). Everything else that is kept: a daemon that dies between doing and storing the answer leaves "being carried out", and the second try is told it could not be confirmed: a pane may have been started, an inbox may have been marked read (the agent is told to call `inbox` with `all`). One that dies before its mark is written leaves nothing, and the second try is told the same. An image that is being replaced begins no change whose mark it could no longer write: the request waits, its connection ends with the image, and the next image carries the second try out.
- **What an agent is told.** After 15 seconds with nothing sent: "spandeck did not answer for 15 s. Your message was NOT sent." (each tool in its own words; a tool that reads: "try again shortly"). When a change may have been carried out: "spandeck went away before it answered, and cannot confirm this: your message may or may not have been sent: read the thread before sending again."
- **Bounded, and nothing is refused for it.** A caller has at most 1,024 rows and the station 8,192; when a caller's are full its oldest finished row that is over a minute old goes. With none that old the change still runs, with no row, and for as long as that could matter a second try of anything that caller asked is told `outcome_unknown` instead of being run on the strength of "no record": more than a thousand changes a minute from one caller costs it the second try, never the change, and never another caller's. (Found by the scenario test: a first version refused the 513th change in a minute.) An answer over 64 KB is not kept, nor one that would take the answers held in memory past 32 MB: a second try is then told only that the change was carried out. Rows go two minutes after the change was done (the longest any caller tries again is 15 seconds, and a second try that says it is older than 30 is not answered from "no record").
- **The switch `request_ids`** (`[flags] request_ids = false`, or `station.flags`). Off: the station keeps no id and does not announce `rid`, so no change is tried again by its id there; a first try runs as before, and a second is told `outcome_unknown`. Commands and tools still wait for the daemon and still send again what was never written, and what only reads.
- **Mixed versions.** A 0.4.4 station ignores `rid` (a field it does not know) and does not announce it. Towards it nothing changes: a change is sent once, a lost answer reads "unreachable" as before, and a caller's own second try by id is refused at the station the owner is using, never sent on. A command or a tool from this version against a 0.4.4 daemon on the same machine (the program was replaced, the daemon not yet restarted) waits for it, sends again what was never written and what only reads, and never sends a change twice. An upgrade in place from 0.4.4 hands over no record of ids: for the first seconds after it, a second try of a change that was in flight is told `outcome_unknown`. `PROTOCOL` is unchanged.
- **Not in this unit:** the Control Deck's page sending a click again after its socket drops (it needs the web server's request loop, which is being rebuilt), and a blocking hook's id, which belongs on its approval because an approval can wait five minutes (done on 16 Nov 2026: see While spandeck is away).

## While spandeck is away: a rule check waits, then refuses where a rule is enforced; an approval survives a restart (16 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is unit 04b of the performance and continuity plan (`crates/core/src/guard.rs`, `approvals.rs`, `hooks.rs`; `crates/agents/src/install.rs`). What was measured on 0.4.2 and was still so on 0.4.6: with the daemon away an agent's hook printed nothing and exited 0 in 3 ms, 596 of 596 during a minute down, so a rule shown as enforced was simply not applied (the audit's gap 7); an approval that was waiting when the daemon went (an upgrade, a kill, the pane host adopting its panes) stayed "pending" for good and could not be answered (gap 4). And the tool-call hook was installed with a 10 second timeout, so a hook that waited longer than that and then refused would never have refused: the agent cancels it first. No migration is added.

**Decided by default on 15 Nov 2026** (the owner said "execute" without answering each question; **the owner may overrule this**, with the switch below): when spandeck stays away, an agent's blocking rule check waits (about a minute; inside the old 10 seconds for a session started before the update), then **refuses** where a rule is enforced for that pane and the agent can be blocked, and allows otherwise. An approval survives a restart: the hook that asked finds the same request again.

**What a hook does when the daemon does not answer.**

- **A tool call (`PreToolUse`) of an agent that can be blocked is held, not passed.** The hook goes on trying to reach the daemon: the connection is tried again after 25, 50, 100, 200, 400 and 800 ms and then every 500 ms, and a connection that ends before the answer (the daemon was upgraded, started again or ended in the middle) is made again and the question asked again. A daemon that is back within the hook's time gives its real answer: the rule's own refusal, or nothing. An upgrade's 20 ms is no longer a hole.
- **How long it is held.** For a pane where a rule is enforced: 60 seconds, every call. For a pane where none is: until the daemon has been away for 60 seconds in all, and never less than the 3 seconds a hook has waited since 15 Nov 2026; so during a long outage each of its calls waits 3 seconds, as before, not a minute. In every case the hook answers **2 seconds before its agent's timeout**: at 73 of the 75 seconds a session started now gives it, at 8 of the 10 a session started before gives it.
- **Then, for a pane where a rule is enforced: refused**, in the agent's own dialect, with these words: "Blocked by spandeck: spandeck is not running on this station, so the rules enforced for this session cannot be checked. Do not retry this and do not try another way: stop and wait for the owner." Every tool call of that pane is refused, not only the ones a rule names: the hook cannot know which the daemon would have refused. A call that is made again is held again for the full time, so an agent that tries again anyway does so once a minute, not once every three seconds.
- **For a pane where no rule is enforced: allowed**, saying nothing, as before.
- **A permission request (`PermissionRequest`) is never refused for this.** Its hook waits up to 60 seconds for the daemon each time it finds it away, and then says nothing: the agent shows its own prompt in its terminal, as it does when nobody answers ("then falls back to the terminal prompt on timeout" stands).
- **Every other hook** (a prompt, a tool's end, the end of a turn, a session's start) is as it was: 3 seconds for a daemon that is starting, then silence.

**"Enforced" is one answer, the Control Deck's.** A rule is enforced for a pane when a standing order of kind rule is in force for it (any layer) and its agent's integration can block: `block_tools`, and seen to with the real agent (`verified`). That is what `orders.view` shows as "enforced", worked out by the same function. So today: **Claude Code: yes. Codex: no**, until its adapter has been run against a real Codex (its rules are shown as guidance, and still block while the daemon is up, where Codex runs the hook). **OpenCode: no** (it has no hooks). **Antigravity: no** (its tool calls are not hooked). For those three a hook is never held past 3 seconds and never refuses; the Enforcement Guarantee is what says so.

- **Not covered, and said so:** the two checks that are not standing orders, "no raw keys in a command" (with a vault connected) and "sign-off before push". With the daemon away they are not applied, as before; a call is held for them as for anything else, so they are applied when the daemon is back in time. Counting them as enforced would refuse every tool call of every Claude Code pane on a station with a vault for as long as spandeck is down there. Checking those two in the hook itself (both are a pattern on the command) would close this; it is not built.

**The guard: how a hook knows.** A hook cannot ask a daemon that is away. So while it runs the daemon keeps a small private file per agent pane, `<state>/panes/<pane>.guard`: whether a rule is enforced, which rules, and the switch. It is written when the pane starts, rewritten within ten seconds of the orders files changing (they are read when needed; nothing announces a change) and at once when the switch is set, and touched every ten seconds, so its age tells the hook how long the daemon has been away. It goes within ten seconds of its pane being closed. **A guard that is missing or cannot be read is taken as enforced**: a damaged file does not open the gate. The pane's id in the file's name comes from the hook's environment and is cut to letters, digits, `-` and `_`.

**The timeout, and why it is told through the environment.** Claude Code's and Codex's documentation both say a hook that reaches its timeout is cancelled and the tool call goes ahead (read 16 Nov 2026; **not run with the real agents**). So the entries spandeck installs (version 2) give a tool-call hook 75 seconds instead of 10, and the installed command tells the hook: `SPANDECK_HOOK_DEADLINE=75 '<spandeck>' hook claude` (PowerShell on Windows: `$env:SPANDECK_HOOK_DEADLINE='75'; & '<spandeck>' hook claude`); 330 for a permission request, as it had. (The brief passed it as an argument, `--deadline 75`. It is a variable instead: after going back a version, a `spandeck` from before would refuse an argument it does not know and exit 2, and exit 2 from a tool-call hook means "block" to both agents. A variable it ignores.) A hook that is told nothing takes 10 seconds for a tool call and 330 for a permission request, which is what version 1 installed. (Version 3 of the entries, the same day: Claude Code's question and plan have a second entry, with an hour; see Answer in place. Nothing above changes for it: the entry every tool call has is as it was.)

- **Who gets the new timeout, and what the owner must do.**
  - **A Claude Code pane started by spandeck on a station with no global install** gets the entries at launch (`--settings`): every pane started or restarted after the update has 75 seconds. Nothing to do.
  - **A station where `spandeck integration install claude` was run** keeps version 1 in `~/.claude/settings.json` until it is run again. `spandeck integration status` and `spandeck doctor` say "out of date" (the doctor now counts that as a fault for Claude Code too). spandeck does not rewrite the owner's agent settings by itself. Claude Code's documentation says edits to that file are normally picked up by a running session (not run).
  - **Codex** has its hooks only from `spandeck integration install codex`. After running it again the hooks are a changed definition, which Codex skips until the owner trusts them again with `/hooks` (its documentation; not run).
  - **A session that is running keeps what it was started with.** Its hook is the new program all the same, as soon as the program is replaced: it decides by 8 seconds, by the same rule. So for such a session an outage of more than 8 seconds refuses the tool calls of a pane where a rule is enforced.
- **A hook started after the daemon came back is not affected by any of this**: it is answered in a millisecond or two, as before.

**An approval survives a restart.**

- **The hook that asks makes a random id** (128 bits from the operating system, once per firing) and sends it with every try (`hook_id` in `hook.ingest`). A hash of it is kept in the approval's row (`detail.hook`; no new column). A hook that lost its connection asks again with the same id and is given **its own approval back**: it waits on it again, or, if the owner answered meanwhile, is given that answer at once. The 300 seconds an approval waits count from when it was first asked.
- **Answering an approval whose hook is not connected at that moment** (the station has just started again) records the answer and says so: `approval.answer` answers `delivered: false` and "recorded: the agent will get it when it reconnects". The hook collects it when it is back (`approval.collected` in the ship's log). An answer is applied once: a second answer is refused, as it always was, and a recorded answer is never replaced by an expiry.
- **A waiting approval whose hook has not come back 15 seconds after a start is expired** and leaves every list (before: one whose pane was kept stayed until the owner's first answer found nobody; one from a hook of a version before this has no id and is expired the same way). The hook, if it turns up later, is told nothing and the agent shows its own prompt. One whose agent went with the daemon is expired at the start, as since 15 Nov 2026.
- **The id is the hook's secret, and gives nothing new.** It is never shown: `approval.list`, the conversation view and the snapshot leave it out, and what is stored is a hash. A row is found again only for the pane whose token the call came with (`hook.ingest` is a pane's own call, for its own pane). `approval.answer` and `approval.list` stay the owner's; an agent has neither. What an agent can do with its own token is what it could before: fire its own hook.
- **`approval.list` says `attached`** for a waiting approval: false while its hook is finding its way back. The Control Deck does not show it yet ("waiting for the agent to reconnect" is the deck's to add).
- **What a crash at the worst moment does.** A row that was not yet written when the daemon was killed is gone: the hook asks again and a new approval is made (the owner is asked again, once). An answer that was delivered to a hook whose connection then ended before it read it is given again to that same hook: the agent acts on it once.

**The switch `hooks_when_down`** (`[flags] hooks_when_down = "allow"`, or `station.flags`; the default is `"deny_enforced"`). With `"allow"`: a hook with no answer says nothing, after 3 seconds, as before this. It is written into every guard, since a hook reads it while the daemon is away. What the switch does not take back: a tool-call hook still asks again when its connection ends in the middle, the timeout of 75 seconds, and everything about approvals.

A hook from before against this daemon sends no id: its approvals are as before. ## A station that is slow or away slows nobody else down (15 Nov 2026, the owner's requirement)

"The slow or absent station has to be fixed with the right architecture for a system like this, never to slow everyone else down." That sentence is the acceptance rule for step 7 of the performance and continuity plan (`crates/core/src/rounds.rs`, `loops.rs`, `fleet.rs`). What was measured before it: everything periodic was awaited in one loop, twice a second, so with one station that did not answer and one message queued for it an agent on the same station as its sender was told of its mail after 1.68 s at the median and 8.4 s at worst; twelve online devices under the owner's login were asked every 10 s whether they run spandeck, and the whole round was awaited in that loop. Measured with four real stations on one machine, one frozen and one behind a link that adds a quarter of a second each way, a message waiting for the frozen one (`crates/cli/tests/isolation.rs`, three runs after and one before). Before: the mail wake-up 2.42 s at the median and 8.96 s at worst, the owner's change to a synced document answered after up to 3.5 s and held by the healthy station after 0.56 s at the median and 5.5 s at worst, local periodic work up to 4.7 s late. After: the wake-up 0.45 s at the median and under 0.95 s at worst, which is what it is with all four healthy (0.45 s; it is the one-second poll); the change answered within 0.1 s and held by the healthy station within 0.17 s (healthy: 0.06 to 0.13 s); local periodic work about 1 ms late at the 95th percentile. No Guarantee is changed.

**The rule, held by how the code is built and not by tuning: no periodic work waits for another station inside a loop that this station's own work, or work for a different station, also depends on.**

- **Local work has loops of its own that wait for no other machine**: screens, keep-awake and agent restarts (every half second); mail wake-ups and the database's health (every second); the session archive and usage (every second); recipes (every half second); upkeep (every ten seconds: when the station was last running; now and again the price list, agent versions, ended panes). Each loop is timed by itself. A loop whose work panics is logged, counted and started again; before, one panic anywhere ended all periodic work.
- **Everything this station does with another station is done in that station's own round**: is a station there and what does it say of itself (`station.hello`, `station.info`, 2.5 s for the two), the roster, handing the key to a station that was away when it was replaced, taking a newer copy of a synced document and offering this station's (deck, look, setup, preferences), `trust.relay` and `trust.sync`, `tailnet.report`, fetching fonts. A round is a task of its own and is cut off after 8 seconds. One station's round never waits for another's, and nothing local waits for any.
- **Rounds do not pile up, and a station that keeps failing is asked less often.** A round for a station is not started while its last one is running. A member is asked at every look (10 s); after three rounds in a row with no answer every second look, then every third (30 s), and no less often than that. It is asked at once again when it answers, when it makes a signed call here (it is back, and said so itself), or when Tailscale says it is online again.
- **A machine under the owner's login that has not joined** is asked at every look for its first minute online, then once a minute; after three failures in a row every five minutes. All of them are asked at once when the owner opens "Add a machine" (`fleet.candidates`), adds one, runs `spandeck fleet`, or joins a fleet. An address named in the station's config is asked like a member's.
- **The look only starts rounds.** Every ten seconds it asks the local Tailscale client (given four seconds; one that hangs holds up nothing else), works out which addresses to ask, and starts the rounds that are due. It waits for none of them.
- **What is still one at a time, and why it cannot couple stations: the wait before the owner's change to a synced document.** "A station that has not looked at the fleet in the last 12 seconds looks first" and "a change waits for a look that is under way" stand, and so does the lock (`sync.looking`). It is taken only by a caller that has chosen to wait for the fleet (that change; `fleet.refresh`; a join); no round and no loop takes it, so it orders the callers that wait and nothing else. Such a caller starts a round for every member at once and waits for those under way, **five seconds at most in all**, however many stations do not answer (before: 2.5 s for the look, then up to 5 s for each call to a station that was listed as on and did not answer). A station "has looked" when the members asked at a look have all answered or run out of time. In ordinary running that is every ten seconds, so a change waits for nothing; it waits after a start or a sleep, which is what the rule is for.
- **The owner's change is offered to every station at the same time**, each in a call of its own (before: one station after another, so a station that did not answer held the next one's copy back five seconds). The same for an agent setup saved for the fleet: its answer names every station and so waits for the slowest of them, five seconds at most, not for the sum.
- **Which copy is taken.** A station's round takes that station's copy of a document only when no other station that is on has said it holds a newer one; that one is taken in its own round. So a copy is not taken only to be replaced a moment later, which could have told the owner of a lost change that was not lost. In one case it still can: three different copies, when the station holding the middle one answers first after this station starts.
- **Work that waits for another machine and is not a round has a loop of its own**, so it can make only itself late: the message relay's safety net (every half second; since the same day it only starts each station's sender and waits for none: see A message for another station goes at once), pushes to ntfy or a webhook (every two seconds), the vault's checks (every ten seconds, first after the fleet has been looked at). Stops already had theirs.
- **The relay's retry times are counted on a clock that only goes forward**, in memory ("not before"), not on the wall clock in the database: a message once waited 223 s after a clock was corrected. After a restart every waiting message is tried at once.
- **The Performance page's numbers.** "Periodic work, late" is now the local loops alone, so it says whether this station's own work is held up. `perf.get` also carries each loop by itself (`periodic.loops`: how late, how long, panics) and, for each station, its rounds (`links[].round`: how long they took, how many went unanswered, how many in a row, when the next is due). The page itself shows the per-station figures it already had (round trip, calls, failures) until it is given these.
- **The switch `split_tick`** (`[flags] split_tick = false`, or `station.flags`; read when the station starts). Off: one loop again, everything awaited in turn, and every machine asked at every look. What the switch does not take back: a look is still made of one round per station, each with its deadline, so it waits five seconds at most; a change is still offered to every station at once; the relay's forward-only clock.
- **Where one station can still hold something up, and which step removes it.** (1) Messages for other stations were tried one station after another, so a station that did not answer held the next station's message up to five seconds at each try: removed the same day, each station has a sender of its own (see A message for another station goes at once). (2) A deck's requests on one connection are taken in turn, so a request passed to a station that does not answer holds the ones behind it: step 2 (lanes). (3) A request that asks every station and answers once (recall across the fleet, a setup saved for the fleet, an agent command for the fleet) waits for the slowest station, five seconds at most, by its meaning. (4) A station that stops answering is still listed as on until its next round fails, up to 10 s plus the 2.5 s (step 3, heartbeats), and until then is sent what the others are sent, each call on its own. (5) The page's own refresh asked every station every 2.5 s, seven questions each, whether or not the last had been answered: step 6, done the same day (see The deck asks each station one question). (6) A font is fetched from the station that sent the document, then from the others in turn, in a task of its own; and an agent's search of findings in projects linked on several stations asks those stations in turn, each within its own limit. Neither is in a step of the plan.
- **Mixed versions.** Nothing here crosses stations: no new call, nothing in `caps`, no change to a call's meaning or to `PROTOCOL`. A station on 0.4.4 is asked and answered as before, and still does its own work in one loop until it is updated: its own mail wake-ups are still late when a station does not answer, and it still offers its copy one station after another.

## A message for another station goes at once (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the rule all of it is held to: "the slow or absent station has to be fixed with the right architecture for a system like this, never to slow everyone else down." This is unit 08a of the performance and continuity plan (`crates/core/src/relay.rs`, `messages.rs`). What was measured on 0.4.5, three throwaway stations on one machine with no delay between them: a message was stored at the other station 331 ms after it was sent at the median and 496 ms at worst, because messages rode a half-second tick; the tick took one message per station, so ten sent together arrived at 0.5, 1.0 … 5.0 s and a hundred took 50 s; and the stations were tried one after another, so with one station frozen a message for a healthy one took 5.2 s at the 95th percentile. A message the other station refused for good was marked refused and nothing was said to whoever sent it (the audit: a task that waited more than ten minutes for a station that was away). Measured after, same stations: 1.5 ms at the median and 2.7 ms at worst; ten together all there within 9 ms and a hundred within 98 ms, in the order sent; with one station frozen and messages waiting for it, 1.6 ms at the median and 2.4 ms at worst for the healthy one. With a link of 21 ms round trip and a station frozen (`crates/cli/tests/isolation.rs`, nightly): 22.5 ms at the 95th percentile, and a hundred together there after 2.2 s. No Guarantee is changed; one is added (Messages).

- **Each destination station has a sender of its own**: a task that takes the oldest message waiting for that station, sends it, and takes the next only when that one is settled (stored there, or refused for good). It has its own place in its own queue, its own limit on a try (the link's five seconds; eight in any case) and its own wait after a failure (half a second, doubling to 30 s). No sender waits for another, nothing else in the station waits for any of them, and there is no loop that tries stations in turn. A sender leaves when nothing waits for its station.
- **It is started the moment a message is stored**, after the message's transaction is committed (`msg.send`, `msg.reply`; the request id is still written in that transaction). Sending never waits for the other station: the sender of a message is answered "queued" as before.
- **The order and the count are exactly as they were.** One message in flight per destination, the next only after the one before is settled: so "ordering within a thread" holds, by the same single queue per destination. A message is marked delivered only when the other station said it stored it, and is sent again otherwise: "at least once, duplicates dropped by id". The Turmoil test (`crates/core/tests/relay_sim.rs`) runs its old cases with the senders, and new ones: a station that hangs does not delay another station's messages, with the senders and with the switch off; a burst arrives at once and in the order sent, through a link cut in the middle of it, with none stored twice.
- **Nothing depends on the push.** The half-second pump stays as the safety net: it lists the stations something waits for and sees that each has a sender; it starts tasks and waits for none. A message nobody was told of (a restart, a lost wake) is found by it within half a second; a sender that ended in the middle of its queue (a panic) is started again by it and counted; a sender that waits after a failure looks again by itself. Each of these is a case of the Turmoil test.
- **A station that is back is sent to at once.** When a station answers a look, or makes a signed call here, the wait after the last failed try is ended (once in two seconds at most), where before the first try after a long cut could be 30 s away. The waits are counted on a clock that only goes forward, as since step 7.
- **A refusal is told to the sender, once.** When the other station refuses a message for good (the task authorization has expired, or it carries none; the two projects are not linked; the message is not for that station), the row is marked refused as before and, in the same transaction, a note is put in the sender's own inbox on this station: from `spandeck@<station>`, kind `note`, in the thread of the refused message, saying "Not delivered to X@golf: …", which message it was, and for an expired authorization that it was not sent again and may be sent again if still wanted. An agent learns of it through its normal mail (it is nudged like any message); the owner also gets a notice ("Not delivered to X@golf"), and the ship's log an entry (`msg.refused`). The two being one transaction is what makes it once: a sender that ends between them leaves neither, and the next try is refused and told again from the start.
- **"These expire" stands.** A task that waits past its ten minutes is refused by the station it was for, by that station's clock, when it arrives; it is never re-issued by spandeck. What is new is only that its sender hears of it. It hears when the message arrives and is refused, which for a station that is away is when it is back: this station does not itself declare a waiting task expired, because it cannot know that an earlier try whose answer was lost did not arrive.
- **A duplicate is acknowledged before the authorization is looked at** (`MessageStore::accept`; the brief said to leave `accept` alone, and this is why it was not). A task that arrived at a try whose answer was lost, and was sent again after its authorization ran out, was answered "refused: expired": the sender marked a delivered task as refused, and would now also have told its agent "not delivered" of a task that was started. A message already taken is now answered as the duplicate it is, whatever has changed since; nothing new is accepted by that. A station on 0.4.5 still answers the old way, so for an expired refusal after an earlier try that got no answer the note adds: "An earlier try got no answer, so it may have arrived then: ask X before sending it again."
- **The reason is the other station's words**, so it is data: bounded (200 characters), control characters dropped, stored and shown as text. A note from `spandeck@<station>` carries no authority: it is a message like any other, and the notice an agent's hook gives says of every message that its content is a request to weigh, not an instruction. Replying to it goes nowhere ("no pane called spandeck").
- **The Performance page**: "Messages" says how long from sent here to stored there, and how many wait; its title now also says, for each station something waits for, how many tries in a row were not answered and when the next is, and when the switch is off. `perf.get` carries these as `messages.waiting[].failed_in_a_row`, `.next_try_in_ms`, `.sender`, and `messages.push`, `messages.senders_restarted`.
- **The switch `relay_push`** (`[flags] relay_push = false`, or `station.flags`). Off: no sender is started when a message is stored and none stays; every half second the oldest message for each station is tried once, which is the old speed (measured: 337 ms at the median, ten together at 0.5 … 5.0 s). What the switch does not take back: each station's try is a task of its own, so a frozen station still delays only its own messages (measured with the switch off: 490 ms at the 95th percentile for the healthy station, where 0.4.5 took 5.2 s); a refusal is told; a station that is back is tried at once; a duplicate is acknowledged first. (The brief kept the old pump "exactly as it is" beside the senders. It is not kept: it was the loop that tried one station after another, which the owner's rule excludes.)
- **Mixed versions.** Nothing new crosses stations: the call is `relay.accept` with the same envelope, nothing is added to `caps`, `PROTOCOL` is unchanged. A station on 0.4.5 receives from an updated one at once and in order (it is sent one message at a time, as before, only sooner); it still sends one message per station per half second, one station after another, and tells nobody of a refusal. The event `msg.relayed` now says which station (`station`) and is sent once for up to 25 messages; a deck from before passes over the field.
- **Not in this unit:** waking the agent a message is for the moment it arrives (unit 08b, done on 16 Nov 2026: see An idle agent is told of its mail when it arrives); a sender's state is in memory, so after a restart every waiting message is tried at once, as since step 7.

## An idle agent is told of its mail when it arrives (16 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the words behind it: "the way we communicate across panes is too slow". This is unit 08b of the performance and continuity plan (`crates/core/src/wake.rs`, `messages.rs`). What was measured before it (two throwaway stations on one machine, an agent idle for more than 1.2 s, twenty messages each way, with the switch off, which is the code as it was): from `send` to the typed nudge 424 ms at the median and 943 ms at the 95th percentile on one station, 434 ms and 875 ms across two, because an idle agent was looked at once a second. Measured after, same stations: 1.0 ms at the median and 1.8 ms at the 95th percentile on one station, 1.9 ms and 2.5 ms across two; from `send` to the message read by the agent 32 ms (the pause before the nudge's Enter is 30 of them), where it was 456 ms. Fifty messages sent at once to one idle agent: one nudge, 2 ms after the first. No Guarantee is changed, and no migration is added.

- **The pane a message is for is looked at the moment the message is stored**: after `msg.send` and `msg.reply` to a pane on this station, when a message from another station is accepted (`relay.accept`), and when the note that tells a sender of a refusal is stored. The look is made off the caller's thread: whoever stored the message waits for none of it, and a sender is answered as fast as before.
- **A pane that goes idle is looked at again the moment it has been idle long enough.** The rule is unchanged: an agent is typed a nudge only when it has been idle (or done) for more than 1200 ms. Mail that arrives sooner sets one later look for that pane, at that moment; a pane that changes to idle sets the same look. (Measured: mail sent to an agent the moment its turn ended was announced 1203 ms after the turn's end.)
- **It is the same look, by the same rule, through the same gate.** The look once a second, the look on arrival and the later look are one function (`nudge_pane`): an agent, not ended, with none of the three marks (Pause, the stop's, the restart's), idle or done for more than 1200 ms. The nudge goes into the pane's input as an item only if that is still so with the input locked (`send_if`), and whatever sets a mark takes back a nudge not yet typed. So "The mail pump cannot pass a Pause or a Stop" holds for every road, and a nudge that is not typed announces nothing.
- **One road at a time tells a pane of its mail.** Each pane has a turn (a lock of its own) held for the whole of one look: read what is not announced, type, mark it announced. The notice a hook gives (`mail_notice`) takes the same turn. Two roads can therefore not both announce one message. (The brief made "find and mark announced" one database statement, marking before typing. That was not built: a hold that landed between the mark and the typing would have left mail announced that nobody was told of, against "a nudge that is not typed announces nothing", and undoing it is a second write. The turn gives the same exclusion with the order kept: typed first, then marked.)
- **A pane just nudged is not typed into again for a second, unless its state changed.** The look once a second could never type two nudges within a second; a look on every arrival could, for mail that arrives while the agent is taking the first nudge. Such mail is announced by the agent's own prompt hook, as before, or by the next look.
- **The look once a second stays** (`pump_mail`, the `mail` loop). It repeats a nudge for mail still unread after `nudge_secs`, tells a pane whose mark has just gone, and makes up a wake that was lost. Nothing depends on the look on arrival.
- **Marking mail announced still waits for the database**, as listed under Nothing waits for the database; it now waits on a thread of its own (the look on arrival) instead of in the loop, so a locked database holds up the look once a second no more than before and a sender not at all.
- **The Performance page**: "Messages" → woken (`perf.get`, `messages.woken`) is the time from stored to told, and shows this: on the receiving station of the measurement, 426 ms at the median and 852 ms at the 95th percentile before, under 1 ms after.
- **The switch `mail_wake`** (`[flags] mail_wake = false`, or `station.flags`). Off: an agent is told by the look once a second alone, as before. What the switch does not take back: one road at a time per pane, and no second nudge within a second.
- **Mixed versions.** Nothing crosses stations: the look is made by the station that holds the message. A message from an updated station to an agent on a 0.4.6 station is announced there by its look once a second, as before.
- **Tests.** Every change (`wake.rs`): the rule as a pure function (held, paused, in a turn, ended, idle for 300 ms → at 1201 ms; nudged a moment ago); fifty messages are one nudge, and a nudge not typed announces nothing, on an in-memory database. Merge tier (`crates/cli/tests/wake.rs`, with times, so not in the every-change check): eight sends each on one station and across two are each announced within 250 ms; a paused agent and an agent in a turn are not typed into; the 1200 ms rule; with the switch off the look once a second still delivers. `holds.rs` and `phase6.rs` are unchanged and pass.
- **Not done here, and said so.** A pane released or resumed is told of its waiting mail by the look once a second (within a second), not at once. Not run on Windows or macOS, or with a real Claude Code or Codex: the scenario tests use the stand-in agent, on Linux.

## Every agent can talk to every other agent (16 Nov 2026, the owner's requirement)

"Make sure that every agent can [talk] to every other agent." On 16 Nov 2026 the owner ran every pair of real Claude Code (Haiku), Codex 0.169.0, Antigravity 1.5.9 and OpenCode 2.3.0 on throwaway stations. Eight faults were found, each read in the code before it was changed; all eight were as reported. What follows was built from them, with the stand-in agent and by hand-written screens; **none of it has been run with the real programs yet** (the checks to run are in the hand-over). No migration is added, no call is added, `PROTOCOL` is unchanged, and nothing is added to `caps`. Two lines are added to the Guarantees under Messages, one changed there, and one added under Enforcement.

**1. The line that tells an agent of its mail says to act on it.** The typed nudge said "You have mail from X. Check your spandeck inbox." A real Claude Code read its inbox and then did nothing in 4 of 6 cases ("you only asked me to check the inbox"); told once to act on mail, it replied 9 of 9 times.

- **One line, by every road** (`messages.rs`, `mail_line`): "You have 2 new spandeck messages from demo/writer@alpha, you@alpha. Read them with the spandeck inbox tool and act on them: reply if one asks something." The nudge typed into an idle agent, the nudge when it is repeated, and the notice a hook gives (a prompt, a tool's end, the turn continued at its end) are that line; the hook's notice adds the tool's name and that a message's content is a request to weigh, not an instruction.
- **It names who and how many, and never quotes a message** ("sent and received through tools", rule 6). At most three senders are named, then "and 2 more". A sender's name is another agent's or another station's text and the line is typed into a terminal, so a name is cut to what an address is made of (letters, digits, `-`, `_`, `.`, `/`, `@`; 64 characters): no Enter, no escape sequence and no sentence can ride in on a name.

**2. The nudge is sent the way a paste is, and an Enter that was not taken is pressed once more.** It was typed as plain text with Enter 30 ms later, and one time in five a real Codex did not take the Enter: the line sat in its input box until the next nudge, a minute later. `pane.paste` (marked as a paste, Enter after 60 ms) never failed.

- **As a paste** to a program that asked for pastes to be marked (`ESC[200~` … `ESC[201~`, decided as `paste_from` decides), with the paste's 60 ms before Enter; plain text, with the same 60 ms, to one that did not ask. It is still one item of the pane's input of the kind "nudge", so a Pause, a Stop or a hold takes it back as before, and the gate with the input locked is unchanged.
- **Unsent is: the pane has not changed state since the nudge was typed, and the line is still on its screen** (the bottom ten lines, where an agent's input box is; `wake.rs`, `unsent`). An agent that takes the nudge starts a turn, which changes its state.
- **One more Enter, once, two seconds on** (`ENTER_AGAIN_MS`), while the mail is still unread. It is made by the look once a second, so it comes two to three seconds after the nudge. The ship's log has `msg.nudge_enter`.
- **A second copy is never typed on top of an unsent one.** When a repeat is due and the last nudge is unsent, Enter is pressed and nothing is typed. (A real OpenCode that could not take a turn had five copies in its input box after five minutes.)
- **What this cannot tell.** A program that took the nudge, ran a turn so short that neither a hook nor its screen showed it, and did not read its inbox, with the line still in its last ten lines: it is given Enter at an empty prompt, which does nothing, and is not typed to again until its state changes or the line scrolls away. An owner's half-typed draft in the input box is typed into as before.

**3. Mail that is not taken is announced less and less often, then not at all.** A recipient that could not take a turn (OpenCode out of quota; any program at a sign-in screen) was nudged every 60 seconds for ever.

- **The waits between nudges are 1, 2, 5 and 15 times `nudge_secs`** (a minute): told at once, then after 1, 2 and 5 minutes more; 15 minutes after the fourth nudge the station stops (`wake.rs`, `BACKOFF`, `due`). **Decided by default; the owner may overrule** the figures.
- **Something changing starts it again:** the pane's state changes (it took a turn, or its screen changed what it says), new mail arrives for it, or the owner types into it. Each of these sets the count to nothing and the first wait is a minute again.
- **The mail stays unread and waiting.** Nothing is marked read, returned or dropped by this.
- **The pane says why**, from the second nudge it did not take: its reason reads "has mail it has not taken: nudged 3 times", and when the station has stopped, "…nudged 4 times, and not again until it changes state, new mail arrives or you type into it" (`needs_reason` where the pane has no reason of its own, so every deck shows it on the pane's line, its dot and the station's tile; and `mail: {nudged, gave_up}` in the pane's view). **One notice** when the station stops: "stuck has mail it has not taken". The ship's log has `msg.nudge_gave_up`.
- The count is in memory: after the station's own restart it starts again (a restored agent is held until the owner releases it in any case).
- The notice a hook gives is not counted: it is given inside the agent's own turn.

**4. Screens that wait for the owner are shown as that, with the reason** (`crates/agents/src/detect.rs`). They read as idle or working.

| Program | On the screen | The pane's reason |
|---|---|---|
| OpenCode | "You've used today's free messages. They reset at 12:00 AM · 11/17/2026." | out of free messages until 12:00 AM · 11/17/2026 |
| OpenCode | "OpenCode Console account … Enter code: … Waiting for authorization…" | asks you to sign in |
| Codex | "Question 1/1 (1 unanswered) … tab to add notes \| enter to submit answer \| esc to interrupt" | asks you a question, in the terminal |
| Codex | "Hooks need review / N hooks are new or changed … 1. Review hooks 2. Trust all and continue 3. Continue without trusting (hooks won't run)" | asks you to review hooks: answer in the terminal (run /hooks); within the first 20 seconds of the program's start the pane's reason comes from "Trusting spandeck's own hooks" instead |
| Antigravity | "Do you trust the contents of this project? … Yes, I trust this folder / No, exit" | asks whether to trust this folder |
| Antigravity | "Allow calling this tool?" | asks permission for a tool call |

- **Each rule stands before the Working rule**: Codex's question ends in "esc to interrupt", which is why the pane was shown as working.
- **A screen that is known by name is believed while hooks report too.** Until now the screen was looked at only for a pane whose hooks had not reported. No hook tells of a sign-in or of the program's own permission prompt, and Antigravity's hooks report every turn, so its "Allow calling this tool?" would never have been seen. For a pane whose hooks report, the screen can say one thing only: that it shows one of the screens above. When that screen is gone (and the pane has printed nothing for a second and a half) and no hook has spoken since, the pane is what it was before; for a pane with no hooks, idle. Claude Code's rules have no such reason and are unchanged.
- **What is taken off the screen** for a reason (the time a quota returns) is data: at most 40 characters, no control characters, shown as text.
- **spandeck answers none of them.** It observes (Enforcement: "screen detection observes"). (Two exceptions, built the same day and each with a section of its own: a folder's trust question, on the owner's standing choice for that folder (The folder-trust question), and Codex's review of hooks when every hook can only be spandeck's own (Trusting spandeck's own hooks). A pane showing either says what that section's reader finds, and these rules leave it alone.) A pane that needs the owner is not nudged about its mail, which is what ends the nudging of a program that has no quota.
- The screens are written by hand from the words that were seen, and nothing else; the wording of a real screen that differs is a rule to fix.

**5. Only the station of the account writes the agents' settings in your home.** See the next section.

**6. A closed pane's unread mail goes back to its senders.** Mail is addressed by name, a name is free once its pane is closed, and a new pane given the name inherited the closed pane's unread mail and was nudged about it at once.

- **When a pane is closed for good** (`pane.close`, a project closed, every pane closed, or an ended pane leaving the list after its seven days), each message it had not read is marked `undelivered: its pane was closed before it read this`, which no pane's inbox shows and nothing is nudged for; and **each sender is told once**, in its own inbox, in the same transaction: "Not delivered to reader@alpha: its pane was closed before it read your note "…" (id). Nothing was passed to another pane: send it again to a pane that is running, if it is still wanted." One note for each sender, from `spandeck@<station>`, like the note for a refusal; a sender on another station gets it through that station's queue, as an ordinary note. The owner gets one notice ("Mail for reader was not read before its pane was closed"); the ship's log has `msg.returned`. A note of spandeck's own that went unread is not answered with another.
- **A pane that is restarted, brought back or restored keeps its id, is never closed, and keeps its mail.**
- **A name a project starts its own pane under is a role, and keeps role delivery.** A pane a project starts by name (its `panes`) is the same crew member each time the project starts it: the project already puts it back in its conversation. Mail for `demo/keeper` that the last keeper left unread is the next keeper's. Only the unrelated case is changed: a pane the owner or an agent started under a name.
- **What is left.** The mail is returned on a thread of its own, since closing a pane waits for no database: a pane given the name within the few milliseconds that takes could still be shown it. Mail left by a pane that was closed before this version is still inherited once. Mail addressed to a pane's old name after a rename is not looked at here.

**7. The sender's copy of a message is answered when the reply arrives.** Each station keeps its own copy of a message. The sender's station set its copy to "delivered" when the other station stored it, and nothing ever told it more, so it said "delivered" while the recipient's said "answered".

- **The cheaper honest option was taken: no receipt of its own, and a row that says what it does not know.** A reply now names the message it answers (`refs`: the id, which `reply` knows), and when it arrives the sender's station marks its own copy `answered`. It marks only a message that it sent to the pane the reply is from, and only on that station's signed call: naming a message's id answers nothing for anyone else. This rides on the reply, which is already delivered at least once and dropped as a duplicate by its id.
- **That a message was only read is not told between stations.** A row of `msg.recent` and `msg.thread` says whose copy it is (`at`), and one that was stored at another station and is not known to be answered says so in words (`status_words`: "stored at bravo, as alpha knows it: whether it was read is recorded at bravo only, and alpha learns that it was answered when the reply arrives"). A receipt for "read" would be a new kind of record on the relay, with its own duplicates, its own queue behind a station that is away and its own refusals on a station from before; it was judged not worth that for a mark nobody acts on. **The owner may overrule.**
- An explicit `ack` with no reply is likewise known at the recipient's station only.

**8. Antigravity asks the owner before every spandeck tool call.** So an Antigravity agent could neither read nor send mail without the owner at its terminal. What its documentation says (https://antigravity.google/docs/hooks, /permissions, /mcp, /plugins, /build-plugins, read 16 Nov 2026, and the guides shipped inside 1.5.9):

- **A hook that answers "allow" for spandeck's tools was not built, because the documentation is not of one mind.** The guide shipped in 1.5.9 says of a `PreToolUse` reply's `decision`: `"allow"`: "Automatically allow the tool execution." The online guide says: `"allow"`: "Allows the tool call to proceed, delegating to the next hook or default policy" (which for an MCP tool is to ask) and names a value the shipped guide does not have, `"auto_approve"`: "Automatically approves the tool call when the default policy would otherwise prompt, while honoring explicit user-configured rules". Neither says what a `matcher` is matched against for an MCP server's tool: the tools listed are Antigravity's own. And `decision` is required, with no "no opinion", which is why `PreToolUse` was never hooked.
- **A narrower route is documented, and that was built: allow rules in Antigravity's own permissions.** "`mcp`: `mcp(server/tool)`, `mcp(server/*)`, or `mcp(*)`"; "Unconfigured `mcp` tools … default to Ask"; "Deny > Ask > Allow"; the rules are in `permissions.allow` of `~/.gemini/antigravity-cli/settings.json`; a plugin's server is "namespaced with the plugin name as `<plugin-name>_<server-key>`", so spandeck's is `spandeck_spandeck`, the name the real prompt showed.
- **`spandeck integration install antigravity`** adds exactly four rules to that list and nothing else: `mcp(spandeck_spandeck/inbox)`, `…/send`, `…/reply`, `…/ack`. Never a wildcard, never another server, never another of spandeck's tools (delegating, the vault, notes and recall go on asking). ## The deck asks each station one question (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the rule all of it is held to: "the slow or absent station has to be fixed with the right architecture for a system like this, never to slow everyone else down." This is unit 06 of the performance and continuity plan (`crates/core/src/snapshot.rs`, `crates/web/assets/app.js`). What was measured on 0.4.5: a refresh of the Control Deck was 1 call for the list of stations, 7 to every station and 5 more to the station serving it (20 for two stations, 34 for four: 816 a minute for an idle deck), every 2.5 seconds and again 120 ms after almost any event, with nothing to stop one beginning before the last had ended; the seven were asked in four groups, each waited for, so with one station frozen a round took 20 s and every other station's approvals, notices and stops stood behind it. Measured after, same stations (5 panes each): 3 calls a round for two stations and 5 for four (120 a minute; in a real browser with four stations and twenty panes, 126 a minute with what events ask, 6.5 times fewer); a round in which nothing changed brings 13 KB down for four stations where it brought 31 KB (nearly all of it now the list of stations); and with one station frozen the others' answers were all on the page 3.4 ms after the round began, the frozen one's own question ending by itself after its five seconds. No Guarantee is changed.

- **`deck.snapshot`**: everything a deck shows of one station, in one answer: `panes`, `projects`, `tasks`, `msgs`, `approvals`, `notes`, `stops`, each built by the function its own call uses (`pane.list`, `project.list`, `task.list {active, limit 100}`, `msg.recent {limit 60}`, `approval.list`, `notify.list {limit 60}`, `stop.list`), so it says exactly what they say; a test holds it to that. With `docs: true`, which a deck asks of the station serving it, also `trust`, `deck`, `look` and `prefs` (`trust.status`, `deck.get`, `look.get`, `prefs.get`).
- **What the deck holds is not sent again.** Each section comes with a version (`v`); the deck sends back the versions it holds (`have`), and a section whose version is the same is answered `null`.
- **A version is worked out from the section's content, not counted where it changes** (the brief had a counter per section, bumped where events are raised, and an id made at each start). A pane's title set by its program, its last output, a task's state written by a hook raise no event: a counter would have left the deck showing the old section until the check found it. A hash of the content cannot miss a change, needs nothing kept between calls, and means the same after a restart, so no start id is needed. Two fields are left out of it because they change with the clock alone: a pane's `last_output_ms` (the deck does not show it), and a stop's `age_ms` (the deck counts a stop's age on from when it was told, by the passing of its own clock; the two clocks are still never compared).
- **Who may ask.** It is on the read-only list, since every part of it already is, and so reaches another station through `rpc.forward` like any read. It is on no agent's list (rule 7) and no station's.
- **Each station is asked by itself, and its answer is put on the page when it comes.** No station's answer waits for another's, and the page waits for none: a caller in the page that wants it up to date (after saving a layout) waits two seconds at most. The lists that are the fleet's (approvals, the inbox, stops) are put together again from what each station last said whenever one answers.
- **Never two questions to one station at once.** While a station's question is unanswered it is not asked again: the 2.5 s round passes it over, and anything else that wants it asked (an event, a click) gets one more question when that one ends. So the deck's questions for a station that hangs cannot pile up in the 20 places the connection gives it; measured in a browser with a station frozen for a minute: none refused for that, and no more questions a round than with all healthy.
- **A station whose answer is late or did not come is said to be so.** What it last said stays on the page, and its tile says "not answering: as of 5s ago" from the first round that finds its question still unanswered after two seconds, until it answers or the look at the fleet lists it as unreachable. The inbox names it under "Not counted", as before; the stops line says its stops are shown as they were. Nothing is concluded from what is held of such a station: a hidden pane is not taken for gone, and a leaf of a global layout is not given a station. A view of a station the page has not heard from yet says "Loading…" or "bravo is not answering yet", never that a pane is gone.
- **An event asks only the station it concerns.** The events a page hears are the serving station's, so they ask that station (one question, soon, and not put off by more events); one that names another station (a notice from it, messages that arrived there) asks that one too. An agent starting or ending a tool brings its pane's strip up to date from the event itself, with no question. New usage numbers ask the serving station, twice a second at most however many agents work. A change to the fleet or to a station's vault (both are read from the list of stations), a reconnect or lost events ask everything. A click that changes one station asks that station.
- **What the serving station alone is asked rides in its one answer**: who is trusted, the global layouts and pins, the look and the owner's preferences come with `docs: true`, unchanged ones empty, so they are right at every round and depend on no event. (The brief asked for them only when the deck opens and on their own events; a copy changed by another station's push, or an event lost, would then have stayed wrong until the page was reloaded.) A machine being added (`fleet.add_status`, which is never passed to another station) is asked when the deck opens, on its events, at every round while one is being added, and at the check.
- **The round every 2.5 s stays, as the repair for what no event told the page of**, until events come from every station with a place to go on from (unit 09b). **Every fourth round is the check**: each station is asked for everything, whatever the page holds. A section that comes back different under the version the page holds is a correction: without the check the page would have gone on showing the old one. It is repaired and counted ("Corrections" on the Performance page, under "This browser", with "Refresh questions" a minute beside it). It was 0 in every run made here; with versions made from the content it can only be something other than 0 if the page itself mishandles an answer.
- **A station from before (0.4.5 and earlier)** does not say `deck_snapshot` in its `caps`, and is asked the seven lists as before, all seven together, with the same rule of one round at a time. If it is asked the new question after all it answers "not found: method deck.snapshot", and the page asks it the seven from then on. Its own deck is the old page, which asks the old calls of every station, and every station still answers them. `PROTOCOL` is unchanged.
- **The switch `deck_snapshot`** (`[flags] deck_snapshot = false`, or `station.flags`): off, the station neither announces the call nor answers it, exactly as a station from before, and decks ask it the seven lists (and, when it serves the deck, the four of its own). The tests of a mixed fleet use it. What it does not take back is the page's: each station by itself, one question at a time, events asking one station.
- **What is still one question for everything**: the list of stations (`fleet.view`), asked of the serving station at every round; it is now most of what an idle round brings down (about 12 KB for four stations). It was not made a section here: it carries each station's load and last-seen time, which change at every look.
- **Tests.** Every change: the versions' rule, as a pure function (`snapshot.rs`); and on real stations (`crates/cli/tests/refresh.rs`): the answer against the seven calls and the four, nothing sent again when held, an agent refused, a station with the switch off answering as one from before. Nightly, in a real browser: three stations, one with the switch off and one frozen (the lists of all three filled; a pane and an approval started elsewhere on the page within a round while one is frozen; the frozen one marked; nothing piled up; nothing corrected); and four stations with twenty panes, the questions of an idle deck counted against the 816 a minute of before.
- **Found while building this, and fixed** (`crates/core/src/add.rs`). "Uninstall spandeck on X" first takes X out of the fleet and forgets it, and may then ask for a password; the try that carries the password looked X up again, and until the next look listed that machine again it was refused with "no station called X is known here". The deck used to show the password box some hundreds of milliseconds late, which hid it; it now shows it at once, and the scenario test, which types as fast as the page lets it, failed half the time. The try with the password now goes to the address the try before it had settled, when that job is an uninstall of the same station waiting for a password.
- **Not in this unit:** events from other stations (a change at another station still shows at the next round, up to 2.5 s: units 09b and 10); the conversation view, which has its own stream and is not part of the snapshot.

## A connection that has gone silent is noticed, and the screen says so (16 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026), and the two rules this is held to: "This has to be well designed and seamless to the user. 100% uptime from every client, control deck, session etc", and "the slow or absent station has to be fixed with the right architecture for a system like this, never to slow everyone else down." This is unit 03a of the performance and continuity plan (`crates/core/src/beat.rs`, `crates/web/src/lib.rs`, `crates/web/assets/api.js`, `app.js`, `term.js`). What the audit measured on 0.4.2: with the browser's link half-open (nothing passes, nothing closes) the page showed nothing at all at 1 s, 5 s, 30 s, 60 s, 120 s and 300 s, went on taking keys, and delivered every one of them when the link returned (232 keys up to 60 s late, 149 up to 5 minutes late); a pane reached through another station froze for 60 s and for 10 minutes with no notice; there was no ping anywhere, no time limit on a request in the page, and the owner was shown the transport's own error ("golf: unreachable: error sending request for url (…)"). Measured after, real stations and a real page in Chrome (`crates/cli/tests/heartbeat.rs`), at a computer's width and a phone's: with the page's link half-open the top bar said "no answer for 3 s" after 3.2 s, marked what is shown "as of" the last answer and turned typing off on the pane; the bar naming the station was up at 10.0 s; what was typed meanwhile never arrived; and the page was connected again 0.1 s after the link returned, by itself. A pane on a station that froze was told after 5.6 s (six seconds after the last thing heard), and was attached again by itself when the station was back. Over a link that takes two seconds each way, for forty seconds, the page gave up no connection and made no new one. No Guarantee is changed.

**The rule: every long-lived connection has a heartbeat, each end judges for itself, and each judgement drives something the owner sees. A connection is judged by silence (nothing at all heard), never by slowness; and time in which the judge itself was not running is nobody's silence.**

- **The page asks.** While it is being looked at and has heard nothing for one second, the page sends `{"ping": n, "t": …}`; the station answers `{"pong": n, "t": …, "s": <its forward-only clock, ms>}` in the task that reads the connection, which waits for nothing (so the answer says the link and the station are alive whatever its requests wait for). A ping is a frame, not a request: no method, no id, on no method list, answered only after sign-in. The page keeps the round trip (the middle one of the last 8; the Performance page shows it under "This browser", with when it last heard anything and its last gap). An idle healthy link so carries one small frame a second, and only while someone is looking. (Since What is typed, the same day: a ping also carries the page's round trip, and goes at least every 5 s on a busy link too, because the station reads the page's clock from it.)
- **"Not answering" is said after `max(1.5 s, 4 × the round trip)`, at most 6 s, without an answer** (the round trip is the middle one of the last 8 or the latest, whichever is longer, so a link that has just turned slow is given a slow link's time at once). From then typing is off and the screen says so; **the connection is kept**. An answer, or any frame, ends it.
- **The connection is given up and made again after 10 s with nothing at all heard** (`max(10 s, 3 × the round trip + 2 s)`, at most 30 s), whether or not the browser ever says it closed, which a half-open one never does. Any frame counts, so a link that is slow and alive is never taken down: its frames are late, but they arrive.
- **Only time the page was looked at and running counts.** The page's clock ticks twice a second and adds up only ticks that came on time while the page was visible; every bound above is measured on that clock. A hidden tab, a locked phone, a laptop that slept, or the page's own script held up for seconds therefore concludes nothing. **On being shown again, or after a tick more than 2 s late, or when the browser says the network is back, one ping decides**: answered, nothing happens; unanswered within the bound above, the connection is made again at once (the socket of a machine that slept is usually dead, and a new one costs less than waiting ten seconds). The brief had "1 s to answer" and "a timer more than 3 s late drops the connection": both would have taken down a slow link, or a healthy one after a long task, which the second review warned of; the page also asks its stations again at once when it is shown, instead of at the next round.
- **Trying again**: at once, then after 100, 200, 400, 800, 1600, 3200 and 5000 ms (each 30% either way), then every 5 s for ever; at once on being shown again or the network coming back. The schedule starts again once a connection has held for 3 s. A new connection is given 5 s to open (10 s after a try that ran out of time) and then `max(5 s, 3 × what opening took)` to be signed in: on a half-open link it would otherwise neither open nor fail. A pane's own re-attach and a conversation's watch use the same schedule (before: a fixed 800 ms and a fixed 3 s).
- **A station lets go of a page that is gone.** It sends a WebSocket ping every 15 s and closes a deck's connection when nothing was heard on it for 30 s, which frees its attached panes and watched conversations. A browser answers such a ping by itself, in the background too. Given up at the moment the silence has lasted 30 s, not at the first ping after.
- **A connection one station holds to another for one pane is pinged from both ends, every 2 s, and given up after 6 s with nothing heard** (`attach_remote`, `watch_remote`; and the other station's side of it, which is known by the signature it came with). The gateway then tells the pane's channel `{"chan", "unreachable": true, "station", "quiet_ms"}` (the message a page from before knows, with two fields more) and ends the task; the pane says "bravo has not answered for 6 s: typing is off. Trying again…", takes no keys, and is attached again by itself on the schedule above. A write towards that station that cannot be made for 2 s counts as silence, so a full buffer cannot stop the clock.
- **The gateway's pings feed the state the calls feed, and attaching reads it** (`FleetState::not_answering`, unit 02b; no second state was built). A connection given up for silence makes its station "not answering" from when it was last heard, at once (six seconds of unanswered pings are more than the two unanswered calls that state asks for); an answered ping on a connection that still stands, while the station is taken to be silent, ends it as an answered call does; a connection that cannot be made counts as an unanswered call. And `pane.attach` / `pane.conversation.watch` for a station that is not answering is refused at once in the same words as a call ("bravo is not answering (for 7 s now) …"), but for the one every two seconds that finds out, where each used to wait four seconds to connect.
- **A station that was itself away concludes nothing from it** (`Beat`, one rule for every connection a station holds, and the place unit 10's events socket takes its own from). A tick more than a whole interval late (the station slept, was frozen, or its loop was held up) gives the other end a whole new 30 s or 6 s; one that is a little late takes that much off the silence.
- **What the deck shows, from one value: for how long, of the time the page was looking, the link has not been known good.** Under 0.3 s nothing (an upgrade's reconnect is not worth a flash). To 3 s "reconnecting…" in the top bar. From 3 s, or from the moment an open connection is known not to answer, the time in amber ("no answer for 4 s" for an open one, "reconnecting… 12 s" for one being made again), beside it "as of 12:01:05", the same on every station's tile, and on every pane "Not connected to alpha: typing is off. What is shown is as of 12:01:05." From 10 s a bar: "alpha has not answered for 12 s. Your agents keep running there." with a button for each other station whose own deck this browser can be handed to (the existing hand-over). From 60 s "alpha last answered 1 min 12 s ago (12:01:05)". When it is back after 10 s or more: "alpha is back after 1 min 12 s." The times shown are by the clock on the wall since the last thing heard, so a page shown again after an hour says an hour. These three pieces are filled in four times a second while anything is wrong, apart from the page's drawing, so they are right while a menu or a dialog is open.
- **When only another station is affected, only its panes and its tile say so**: the pane as above, the tile "not answering: as of 5s ago" as since unit 06 (the page's question to it has gone unanswered). The page's own connection, and everything of every other station, carry on.
- **Nothing typed is sent while the page knows it is not connected**, then or later: not with the socket closed (as before), and now not with it open and unanswered either; the pane says so at the first key. Keys typed in the seconds before the page knows are still in the connection (unit 03c holds, numbers and refuses them at the receiving station: done the same day, see What is typed; the pane no longer says so "at the first key" but holds keys for 1.5 s and then says how many were not sent).
- **A question of the page's refresh has ten seconds** (twelve for another station, since the serving station gives a call up itself after ten and its words say more): then it is over ("alpha did not answer within 10 s") and asked again at the next round. Before, no request in the page had an end. Clicks are left as they are (unit 03d: a change may not be given up from the page's side alone).
- **Not built, and why: "at most 4 reads in flight per station from the page".** The connection already gives each station 4 places and 20 waiting (unit 02b), and the page asks each station one question at a time (unit 06); a third limit would have held nothing back.
- **No transport error is shown to the owner.** A call to another station that got no answer says which way: "golf did not answer within 5 s"; "golf refused the connection (spandeck may be stopped there)"; "golf could not be reached within 1.5 s (it may be asleep or off, or Tailscale may not be connected there)"; "golf cannot be reached from this station (Tailscale may not be connected here)"; "golf ended the connection before it answered". No address in any of them. (The brief had "Tailscale is not answering on golf" for a call that could not connect; this end cannot tell a machine that is off from one whose Tailscale is, and says so.) The same words where a stop's row, a setup or a refused attach names the reason.
- **When this station's own Tailscale client does not answer "who is at this address"**, the caller is neither let in nor remembered as a stranger (before: remembered as one for two minutes, so the owner stayed locked out after Tailscale was back). The station says "Tailscale is not answering here, so this station cannot tell who is connecting. It is asked again by itself", the page shows that and keeps trying, and the next connection asks again. "Knows no such device" is still a stranger, kept two minutes as before.
- **Every timer, and why.** Page: tick 0.5 s; asleep when a tick is over 2 s late; ping after 1 s of nothing heard; "not answering" after max(1.5 s, 4 × round trip) ≤ 6 s (1.5 s: three times a bad Wi-Fi round trip; 6 s: what a call to a station is given); given up after max(10 s, 3 × round trip + 2 s) ≤ 30 s; a new connection 5 s to open, then 10 s; sign-in max(5 s, 3 × opening); retry 0, 0.1 … 5 s ± 30%; schedule starts again after 3 s connected; refresh question 10 s (12 s through a gateway); screen 0.3 s, 3 s, 10 s, 60 s. Station to a deck: ping 15 s, let go at 30 s. Station to station, per pane, both ends: ping 2 s, given up at 6 s (three pings; told within the six seconds a call to that station is given); a write 2 s.
- **The Performance page**: per station "Silent connections" (decks, connections from stations, connections to stations, given up in the last 5 minutes; `perf.get`: `connections.closed_silent`); under "This browser" the heartbeat's round trip, when the page last heard anything, how many connections it gave up for silence, and its last gap.
- **The switch `deck_ping`** (`[flags] deck_ping = false`, or `station.flags`; read when a connection begins). Off: the station says nothing of pings in `caps`, answers none of a page's, sends none itself and lets go of nothing for silence: a station from before. Its own page then sends no ping and concludes nothing from silence. What the switch does not take back: the page's retry schedule and connection time limits, the ten seconds of a refresh question, the plain words, the Tailscale rule.
- **Mixed versions.** `ping` is announced in `caps` (the sign-in answer and `station.info`); `PROTOCOL` is unchanged; no call was added. A page is served by the station it talks to, so the two differ only when the switch is off. Between stations the pings are WebSocket protocol pings, which every version answers by itself: a pane on a 0.4.6 station reached through an updated one is watched by the updated gateway (told within 6 s); a pane on an updated station reached through a 0.4.6 gateway is not let go of, because that gateway answers the updated station's pings, and is not watched by it either, so there the pane freezes without notice as before until that gateway is updated. Both ways are a scenario test (a station with the switch off). A page from before ignores the two new fields of `unreachable`.
- **Tests.** Every change: the beat's rule (`beat.rs`: silence ends a connection; a slow link does not; the judge's own absence does not); the plain words (`fleet.rs`); the pings feeding the not-answering state (`lanes.rs`). Merge tier, real stations (`heartbeat.rs`): a pane told within seven seconds with the station's name and how long, the attach refused at once by the same state, attached again when the station is back, the pane's station letting go of a silent gateway, a station letting go of a deck behind a half-open link within the half minute and of no deck that is there, the pong's shape; and the mixed pair. Merge tier, in a browser: the page's rules as the plain functions they are (the schedule, what a tick means, the bounds, what the screen says). They run in a browser because the page's code does; the every-change tier has no JavaScript engine, so "≤ 0.3 s, every change" in the brief became this. Nightly, in a browser, with measured times: the page's half-open link at both widths, start to finish, hidden and held up included; a link two seconds away each way; a pane on a station that freezes.
- **What the later units take from here.** 03b (attachments' names): the `unreachable` message and the re-attach path. 03c (what is typed): `api.live` (connected and answering), `api.probe()` (a ping now; resolves with the round trip or rejects after the bound, and never drops the socket), `api.rtt()`, the pong's `s`. 03d (clicks): `call(method, params, {within})`, the code `no_answer`, and `api.live` for "not sent". 09a (resume): `PaneTerm.reattach()` is the one place a pane comes back. 10 (events between stations): `beat::Beat` with `beat::STATION`, and `FleetState::heartbeat` to feed the same state.
- **Not in this unit, and still true.** Keys typed in the two or three seconds before the page knows its link is silent, or in the six before a gateway gives a pane's connection up, are in the connection and arrive if it comes back (03c). A click made in those seconds is applied when it arrives (03d). The fleet's list still learns that a station is away from its rounds, 10 s apart (10). A re-attached pane is repainted from a snapshot (09a). Whether a phone that was locked finds its socket half-open or closed, and how soon its timers run again, was not measured on a phone.

## The conversation view (15 Nov 2026, the owner's request)

"I like the Claude mobile app, simple, lets you focus on working with an agent, lets you talk to it. This is a single pane for focus ... I still can see a need though if you need to get back to terminal arrow etc ... make the functionality the same as Claude code but also keep the best of spandeck." Then: "execute ... the mobile plan". The plan's decisions were taken as it recommends; each is the owner's to overrule, and the ones that matter are marked **(default)**.

**Built: the station side (phase M1) and the view (phase M2).** A station can turn an agent pane's session into the items a conversation view shows, serve them a page at a time, send new ones as they are written, and remember how far the owner has read. The exact calls are in `docs/conversation-api.md`. The view is in the Control Deck (`crates/web/assets/chat.js`, and `md.js`, which draws an agent's markdown); what it does is under "The view", below. Answering a question or approving a plan from the view was built on 16 Nov 2026 (phase M3): see "Answer in place", below.

- **A pane has two faces, on the phone and on the desktop (default):** its terminal, as today, and its conversation: what was said, as readable text, with the tool calls folded away. The terminal stays one tap away and is always the whole truth.
- **Built on the agents' own session files (default).** Claude Code and Codex write each conversation to a file as it happens, and the archive already copies every line of it. The conversation is read from those kept lines, so it is still there after the agent deletes its file, and no shipped migration changed: the index that makes paging cheap is in memory and is rebuilt when asked for.
  - **Both vendors say these files are internal and may change with any release.** So the builder is written to fail in the open. A record it does not know is left out and counted, and every answer carries the count and the kinds ("3 records not understood"), so the view can say that it has stopped understanding and send the owner to the terminal. The raw lines are kept as they were written: a fixed builder reads old sessions again. Fixtures with the shapes of Claude Code 2.1.302 to 2.1.325 and Codex 0.169.0, and made-up words, are in `crates/archive/fixtures/`.
  - **Hooks stay the only thing that decides anything.** The pane's state, its current tool and every approval come from the hooks, as before, and are sent beside the items (`live`). The session file only says what was said.
  - **A reply arrives a block at a time, not letter by letter.** An agent running in a terminal does not write its reply anywhere until a block of it is finished.
- **What an item is.** The owner's message (the words, a count of pictures, and where it came from: typed, queued, another agent); the agent's text, as markdown source; thinking, as a length of time and never its content; a tool call (name, one line of what it did, whether it worked, how long), with its input, output and diff fetched only when its row is opened; a question the agent asked and a plan it proposed, with the answer once given; a sub-agent it started; and notices (compacted, turn ended and how long it took, interrupted, error). A tool call is paired with its result by the id both carry. An item's id is its line in the session and its place in that line, which never changes; the line number is also the cursor ("what came after line N"), so a view that reconnects gets nothing twice and misses nothing.
- **What each agent program gets.** Claude Code: all of the above. Codex: its messages, tool calls with their output, and turn ends; no title, no diff, and whether a call worked is not in its file, so it reads "done". The Codex half was written against real 0.169.0 files, but no live Codex pane has been watched. OpenCode, Antigravity and shells: no conversation; the call says why in a sentence and the view opens the terminal (since 16 Nov 2026 their Chat is made from the screen: "Chat for every pane", below). That a pane was resumed is known from its hooks, not from the file, and is sent in `live`.
- **Who is served, and why the scrubbing Guarantee stands (default).** The Guarantee says other stations and agents see only the scrubbed view of history. The conversation is the raw history, unscrubbed: it has to be, or the owner would read `[redacted]` where the terminal beside it shows the real thing. So it goes to one reader only, **the owner's signed-in browser**, which is neither a station nor an agent, and which is already shown the same words by the pane's terminal (`pane.attach`, `pane.text`).
  - `pane.conversation`, `pane.conversation.detail` and `pane.read` are the owner's: on no agent's list, not on the read-only list, and on no station's list. An agent is refused its own pane's conversation too; it has `recall`, which reads the scrubbed copy, as before.
  - A deck served by another station reaches a pane's conversation as it reaches its terminal: the serving station passes on the owner's request (`rpc.forward`, or for the live stream a connection signed with the fleet key, as for `pane.attach`). **It passes the answer through and keeps none of it**: nothing is written to its archive, its log or its database. What a station can do on another as the owner is not widened by this: it could already attach to the pane.
  - What is new to say plainly: the raw text of a tool's output now crosses the tailnet to the owner's browser as JSON, where before it crossed as terminal bytes. A key an agent printed is in both.
  - Text from a session file is data (rule 6). The station drops terminal escape sequences and control characters and returns text and structure, never markup; the view will insert it as text.
- **The live stream.** While a browser watches a pane's conversation, the station looks at that session's file every 200 ms (the archive's own look is once a second) and sends what is new on the browser's existing connection; when nobody watches, nothing extra runs. Through another station the messages are passed along as a pane's terminal is. The event bus has no replay, and this needs none: the cursor is the resume point.
- **Unread is the fleet's, and is kept at the pane's station (default).** "It's all the same view from spandeck." Each pane has a mark: the line of its session the owner has read to. The mark is kept by the pane's own station (in its key-value table), set through any station's deck as the owner's forwarded request, and every pane in the pane list says `unread`: the agent has said something after the mark. So the dot is the same on every device and whichever station serves the deck. A mark belongs to one session of the pane; it only moves forward; it goes when the pane is closed. Looking at a conversation, marking it read and asking for a tool's detail do not count as the owner being at a keyboard, so a phone showing one conversation is still pushed the notice for another pane.
- **Bounds.** An item's text is cut at 16 KB and a tool's output at 64 KB a page, each with a mark and a way to fetch the rest; a diff at 2,000 lines; a page at 200 items; an index at 100,000 items a session and eight sessions, about 32 bytes an item. Reading is done off the daemon's async work, and the database is asked for a few hundred lines at a time, never held while they are parsed.
- **Cost, measured on the machine it was built on, on a real 51 MB Claude Code session (13,936 lines, 2,961 items):** the first request builds the index in 85 ms; after that, a look with nothing new takes 0.07 ms, and paging through the whole session 200 items at a time takes 85 ms in all. The index was 89 KB. The archive's copy of the file, which exists with or without this, took 0.5 s once.
- **Not built, and not claimed:** a queued message shown before it is sent; a background task's later report tied back to the row that started it; OpenCode's own streaming interface.
- **A station on a version from before this** has none of these calls: asked for a pane's conversation it answers that there is no such method, which the view treats as "no conversation: that station needs an update", and shows the terminal. Its panes have no `unread` and no title in the list. A deck served by an older station is its own older deck, as always.
- **Native app:** unchanged. "In the browser; no native app" stands until the plan's later gate.

### The view (phase M2, 15 Nov 2026)

The owner showed two pictures of the Claude app on a phone: a list of sessions with a dot on the unread ones and "New session", and one conversation with the reply as comfortable text, Copy and Read aloud under it, a "3 running tasks" link and a message box. The view follows them, and keeps what spandeck has that the app has not: the terminal one tap away, the fleet, approvals held by a hook.

- **A pane has two faces, chosen with "Chat | Terminal" on its bar.** Terminal is the pane as it always was. Chat is its conversation. **Chat never attaches to the pane**, so it sets no size and takes control from nobody ("One size per pane"): it watches the conversation, and sends what the phone's message box already sent. A shell, an agent spandeck cannot read (OpenCode, Antigravity), an agent that has not said which session it is in, and a pane on a station from before this are their terminal, and the bar says why in the place of the switch ("Terminal only: it runs a shell, not an agent"). A pane that gets a conversation later (its first hook arrives) gets the switch then. (Until 16 Nov 2026. Since then every pane has the switch, and only a pane on a station from before is its terminal: see "Chat for every pane", below.)
- **What the conversation shows.** The owner's messages as bubbles on the right (one from another agent, a schedule or a background task on the left, saying which); the agent's text as markdown at reading size; a run of tool calls folded into one line ("Ran 6 tools · 48 s"), which opens to a row for each call and a row to what the call was given, what came back (cut, with "Show more") and, for an edit, the change as a diff; thinking as "Thought 12 s" and never its content; a question or a plan as the agent wrote it, with the answer once given; turn ended, stopped, compacted and errors as quiet lines; a kind this version does not know as a quiet line with its name. When the station left records out it says how many and offers the terminal. Under a finished reply: Copy, and Read aloud where the browser can speak. The page above is asked for when the top is reached. The log stays where it was read, and follows new items only while the owner is at the end.
- **Above the message box, while the agent works:** "Working · Bash: cargo test · 42 s" (the time by the station's clock, never the browser's against it), with "Peek", which shows the last lines of the terminal; "3 running tasks" when the agent has sub-agents running; and Send becomes Stop while nothing is written.

When the pane needs the owner and there is nothing the view can answer (a picker, a login, a prompt after an approval ran out of time): "Waiting in the terminal: <reason>", the terminal's last lines, the keys 1, 2, 3, Enter, Esc and the arrows (`pane.input`), and "Open terminal".
- **The message box.** Sent as the phone's box always sent: one paste, then Enter (`pane.paste`). What is being written is kept for each pane through redraws and between Chat and Terminal. "+" sends a photo, a camera shot or a file (`pane.drop_file`: the station writes it and types its path, so it works for every agent). The microphone dictates where the browser can; where it cannot it says so, and says that it needs the station's HTTPS address when that is the reason. "/" offers Claude Code's text commands.
- **The phone's list opens on what matters.** In order: **Needs you** (approvals with Allow and Deny, then agents that wait or stopped on an error), **Pinned**, then **Recents**: every agent pane in the fleet, the one that changed state last first, each with its session's title (Claude Code names its sessions) or the pane's name, where it is and what it is doing, and a dot when it has said something not read. "Recent | By station" switches to the list as it was, with every control it had (stations, projects, layouts, Watch, New, Wake, Start, Stop, usage, performance, stopping the fleet): nothing was removed, it is one tap away. "+ New session" stays at the bottom: an agent, a station, a project or folder, "Continue the last conversation" and an optional first message, then the new pane's conversation.
- **Read, and "Next".** A conversation is marked read (`pane.read`) when its newest item is on screen and the page is in front; never by asking for it. "Next ›" on the bar, with a count, goes to what else waits in the fleet: approvals oldest first, then agents waiting for something else, then errors, then agents that finished and are unread.
- **On a computer** the same view is a pane's other face: "Chat" on a terminal's title bar, in a pane at full size and in a layout, and the switch on the conversation's bar leads back.
- **In a layout on a phone the pane shown is the pane itself (16 Nov 2026, the owner's report from a phone).** "Noticed that the window on mobile in a layout is the old style vs a pane not in a layout. The panes in the layout should work like the single panes." Until then the phone's one-pane-at-a-time layout view was the terminal only, with the keys and the old message box, for every pane.
  - **The same code, not a copy.** The pane a layout is showing is drawn by what draws a pane opened by itself: the conversation's bar (back, state, the session's title, agent · station, "Chat | Terminal" or why it is its terminal, "Next ›", the pane's menu), and under it the conversation with its cards, activity line, message box and unread mark, or the terminal with Fit to screen, the usage, Stop this turn, the keys and the message box. The face is the same remembered choice, per device and per pane, wherever the pane is opened. Chat attaches to nothing here either; in the Terminal face the layout view sizes a pane as it did (watching, or fitted and in control).

A dot is amber or red when that pane needs the owner, and the count turns amber when another pane of the layout does. A tap on the line opens the layout's name and where it is from (or the list of layouts), its map (hidden panes dashed) and "Hide <pane>" / "Show <pane>", **over the pane and not above it**, so opening the map takes no room from the conversation and never resizes a fitted terminal; a tap on a pane in the map, or anywhere outside, closes it. With the keyboard up the line steps aside, as the bars do.
  - **Measured at 390×844** (the deck's own top bar is 104 px in both): before, the layout's header ended at 356 px and the terminal had 339 px (177 px with an approval waiting); now the pane's bar and the line end at 253 px and the conversation's log has 532 px (373 px with an approval's card), against 577 px for the same pane opened by itself.

So reading, scrolling and selecting in a conversation are never a step; over a terminal it is as it was.

It makes paragraphs, headings, emphasis, code, lists and task lists, quotes, tables, rules and links, and no other element; the only attributes are `class` and a link's `href`. HTML in the text is the characters typed. A link is http or https or it is not a link, and it opens (new tab, `noopener noreferrer`) only after a sheet has shown where it leads. A picture is never fetched: it is a link with its label. The content policy is unchanged. A test draws text written to attack the page and checks exactly this.

### Answer in place (phase M3, 16 Nov 2026)

The owner's approval: "execute ... the mobile plan" (15 Nov 2026); this is the plan's phase M3 and its open decision 4, taken as the plan recommends. Until now a question an agent asked (Claude Code's `AskUserQuestion`) and a plan it wanted approved (`ExitPlanMode`) were shown in the conversation and answered in the terminal. Now the owner answers them where the conversation is. `crates/core/src/questions.rs`; the cards are in `chat.js`; the exact calls are in `docs/conversation-api.md`. No migration is added. One line is added to the Guarantees, under Enforcement.

**What it rests on, and what was not run.** Claude Code's hook reference (https://code.claude.com/docs/en/hooks.md, read 16 Nov 2026), "Tools that require user interaction": "`AskUserQuestion` and `ExitPlanMode` require user interaction"; a `PreToolUse` hook satisfies that when it "returns `permissionDecision: "allow"` together with `updatedInput` that holds the answer, so the tool runs without prompting. Returning `"allow"` alone is not sufficient for these tools. For `AskUserQuestion`, echo back the original `questions` array and add an `answers` object mapping each question's text to the chosen answer"; `answers`: "Multi-select answers join labels with commas"; `updatedInput` "replaces the entire input object, so include unchanged fields"; for a deny, `permissionDecisionReason` is "shown to Claude"; for `ExitPlanMode`, "Claude Code injects the plan content and file path before passing the input to hooks", and its permissions page says a hook that answers it "with `"allow"` and `updatedInput`" lets it run "without a prompt". It was built from that documentation, with the stand-in agent, which asks through the same two hooks and prints the input it is given back. **Then run by hand with the real Claude Code 2.1.325 (Haiku) on 16 Nov 2026**, on a throwaway station, answering through the API: the second entry fires (a question was held within 3 seconds, and the terminal showed "running PreToolUse hooks… 1/2" and no picker); `updatedInput` answers a question; two questions with several choices and "Other" came back as "Apple, Plum, quince", so the ", " is taken; a hold of 20 seconds ran out and the picker appeared in the terminal with nothing answered; letting go put the picker there at once; a plan was held with its text, sent back with a note (Claude Code kept planning and followed the note) and then approved (it left plan mode and went on to an ordinary permission prompt for its Write; which permission mode follows is Claude Code's own default flow, the hook chooses none). **Not yet known: that a hold longer than 600 seconds is honoured** (being run when this was written), and what Esc in the terminal does to a held question. The cards themselves were not driven with the real agent, only the calls under them. Three faults were found by that run and are fixed below ("Found with the real agent").

- **Two hooks for one call.** Hooks that match run side by side (the reference: "its matching hooks run in parallel"), and each handler has a timeout of its own. So Claude Code's entries (version 3) have a second `PreToolUse` entry beside the one every tool call has: matcher `AskUserQuestion|ExitPlanMode` (letters and `|`: a list of exact names), timeout 3600, and a command line that tells the hook it is this one: `SPANDECK_HOOK_DEADLINE=3600 SPANDECK_HOOK_ANSWERS=1 '<spandeck>' hook claude`. The first entry is unchanged: it still tells the station of the call and checks the rules within its 75 seconds, and its refusal wins (the reference: "precedence is `deny` > `defer` > `ask` > `allow`"). The second does one thing: it asks the station to hold the call for the owner, and says nothing in every other case. (Considered and set aside: one entry for every tool with a matcher that leaves these two out. A mistake in that pattern would stop every rule from being checked, and it could not be tried with the real agent here.)
- **The exchange.** The hook sends the call's input to its station (`hook.ingest` with `answers: true`, its own pane's call). When the owner answers, it prints, for a question, `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow", "updatedInput": {"questions": [...as given...], "answers": {"Which herons count?": "All herons", "Which rivers?": "Avon, Tamar, Dart"}}}}`: the question's text to the label chosen; several labels joined with ", "; what the owner typed under "Other" as typed, alone or after the labels of a question that takes several. For a plan that is approved: allow, with the input given back as it came. For a plan that is sent back: `"permissionDecision": "deny"` with "The owner read this plan in spandeck and did not approve it: keep planning, and do not start the work. The owner's note: ...". In every other case it prints nothing.
- **Nothing is ever answered for the owner.** When the owner does not answer in time, chooses "Answer in the terminal instead", or spandeck is away for longer than a minute, the hook says nothing and the agent shows its own prompt in its terminal, as it always did. A call that is not in a shape the card can show whole (no question text, no options, more than eight questions or sixteen options, two questions with the same text, an input over 256 KB) is not held at all.
- **How long, and why (default).** The station holds a question for **ten minutes**: long enough to see a push on a phone and answer, short enough that someone who sat down at the terminal instead is not kept from the prompt for long. The switch is `question_hold_s` (`[flags]`, or `station.flags`, in force for the next question): seconds; 0 turns holding off, and questions are then the terminal's, as before. The entry's hour is not the hold: it is the most a session can ever be asked to wait, since a running session keeps the entries it was started with, and the owner can raise the hold up to 59 minutes without starting sessions again. The station lets go 5 seconds before the hook's timeout and the hook answers 2 seconds before it, so the station decides and the agent never cancels the hook. The reference gives a command hook 600 seconds when no timeout is named and names no upper limit; **that an hour is honoured has not been run.** If it is not, the hook is cancelled early and the reference says what follows ("a timed-out `command` ... hook doesn't block the tool call ... The call continues through the normal permission flow"): the prompt appears in the terminal, and the card stays until its ten minutes are over (see Not done).
- **While it is held the terminal does not show the prompt**, as with an approval. The card says until when ("Waits here for 9 more minutes, then moves to the terminal", by the station's clock) and has "Answer in the terminal instead", which lets it go at once. The pane's reason says the same for every deck: "asks you a question: answer it in Chat (in the terminal from 14:12 UTC)", and on a computer the terminal's title bar has "Answer in Chat" in the place of "Chat". When it has moved: "its question is in the terminal now (nobody answered it here in time)", or "(you chose to answer it there)", and the card becomes the keys for the terminal and "Answer in the terminal".
- **The same record as an approval, so the same promises.** A held question is a row of the approvals' book, with the kinds `question` and `plan`: found again by the hook's random id after a restart (unit 04b), its ten minutes counted from when it was first asked, an answer given while the hook is away kept for it (`delivered: false`), one nobody came back for expired 15 seconds after a start, cancelled when its pane ends. An answer is applied once: a second answer finds nothing waiting; a second try of the same answer with its request id (unit 04a) is told "done" from the question's own record and is never run again. No third mechanism was made.
- **It is in no list an approval is in.** What an agent asked is part of the owner's conversation. `approval.list` (which the read-only caller has), the snapshot and the fleet's "Approvals" never show it, and `approval.answer` refuses it. It is read through the conversation's calls only (`live.questions`), which are the owner's. What is said elsewhere says that something is asked and never what: the pane list has `asks: {kind, until_ms}` and the reason above; the notice reads "<pane> asks you a question" · "Answer it in its conversation. It moves to the terminal at 14:12 UTC."; the ship's log has `question.asked`, `question.answered`, `question.released`, `question.lapsed`, `question.reattached` and `question.collected` with the id and how it stands, never the question or the answer.

## The folder-trust question (16 Nov 2026, the owner's request)

"I thought you were building a auto approve when a agent starts to trust this folder question." It was not being built; it is now. Until this, an agent program started in a folder it had not seen stopped at its own question and the pane sat at "needs you" until someone answered in its terminal. `crates/agents/src/foldertrust.rs` (reads a screen, presses nothing), `crates/core/src/foldertrust.rs` (whose choice, and the key). One line is added to the Guarantees, under Enforcement, and the line above it there now names this as an exception (since the same day there are two: see Trusting spandeck's own hooks).

**The rule.** The owner's own act of starting an agent in a folder, with a visible and remembered choice, is the consent. spandeck then answers that one question, once, by pressing the key the owner would press, and never anything else.

- **Where the choice is made.** A tick in the New pane dialog and in the phone's New session sheet, "Trust this folder for <agent> if it asks", shown only for a program whose question spandeck can read (Claude Code, Antigravity), with the folder's path, what it allows in that program's own documented words, and the warning below. `spandeck pane new --trust-folder` is the same tick. **Off for a folder never used.** Ticked, it is remembered for that folder and that program on that station, and the tick starts on there next time; unticked at a later start, it is forgotten. A caller that sends no tick (the command line without the flag, a deck from before this, a project's launcher) gets the standing choice as it is.
- **A project's switch**, "Agents may be started in this project's folders without asking me to trust them" (the project's menu, "Folder trust for this project"). **Off until the owner turns it on**, per project and per station. On, it covers the project's folder, folders under it, and the worktrees and snapshots spandeck makes for that project's helpers.
- **Where the choices live.** In the station's own state (`folder_trust` in its key-value store), because a folder is a machine's. **Never in `.spandeck/project.toml`**: that file travels with the repository, and a repository must not be able to say that it is trusted. Listed, with Remove, in Agent setup ("Folders trusted for agents on <station>") and in the project's dialog. Removing one stops spandeck answering; what the program recorded for itself is the program's own and is not touched.
- **Who may use it (rule 7).** `pane.spawn`, `pane.trust_folder`, `foldertrust.choice`, `foldertrust.list`, `foldertrust.remove` and `foldertrust.project` are the owner's: on no agent's list, no station's and not the read-only one; they reach another station only as the owner's forwarded request, and what is remembered is remembered at the station the pane runs on. The choice on a pane is worked out by whoever starts it and is never read from a caller's parameters. A pane an agent asks for (`delegate`) is answered only inside a project the owner switched on, whatever the agent sends; with the switch off it waits for the owner like any other.
- **What is answered.** Only when all of these hold: the pane was started with the choice, and the choice still stands when the key would be pressed (a folder taken off the list, or a project switched off, is not answered); the screen is that program's own prompt **word for word, from the first thing on the screen to the last, naming the pane's own folder** (the shapes below; a line wrapped by a narrower terminal is the same words); it was first seen within 20 seconds of the program's start and before any hook of the session; it has stood unchanged for 0.7 seconds; the program's marker is **on the trusting choice** (where the program puts it on "No, exit", spandeck moves it first and reads the screen again: see "Fully automatic" below); the owner has not typed into the pane; and nothing was answered in this pane since the program started. Then Enter is sent, as one item of the pane's input (`terminal/input.rs`). Once per start of the program.
- **What is never answered** by this rule: Codex's "Hooks need review" (that is about hooks, not a folder, and has a rule of its own: Trusting spandeck's own hooks), a permission prompt, a login, "Allow calling this tool?", a question or a plan, the same words printed later in a session, a second question in the same pane, another program's screen, a screen for another folder, and **a screen that says anything more than the known one**. - **The programs' own trust files are never written** (`~/.claude.json`, `~/.gemini/antigravity-cli/settings.json`, `~/.codex/config.toml`): a key is pressed, and the program records what it records.
- **When nothing is pressed** the pane says "asks whether to trust this folder: answer in the terminal" (its `needs_reason`; `trust.asks` in its view says why: `not_chosen`, `own_choice_is_no`, `not_the_known_screen`, `switched_off`), and where spandeck can read the two choices the deck offers **Trust this folder** on the pane, with "remember" beside it on a phone and in the pane's menu on a desktop (`pane.trust_folder`). That is the owner's own tap: it moves the program's marker to the trusting choice if it is not there, reads the screen again, and presses Enter only when the marker is seen on "Yes, I trust this folder"; otherwise it says that nothing was confirmed.
- **On record.** `pane.trust_answered` in the ship's log: the pane, the folder, the program, `how` (`standing` or `tap`), who started the pane and why the choice stood (`folder` or `project`). The pane says "spandeck answered <program>'s folder-trust question, as you chose for this folder" for ten minutes. No notice is raised for a question spandeck answered. `foldertrust.remembered`, `foldertrust.removed` and `foldertrust.project` record the choices.
- **Restart.** A program started again in the same pane (the owner's Restart, an agent update, the station after a crash) is treated the same way, and only for a pane that was started with the choice, which is on the pane's record. spandeck answering lifts no Pause and no hold; the owner's own tap counts as the owner typing into the pane, which releases a hold as any key of theirs does, and never ends a Pause.

## Trusting spandeck's own hooks (16 Nov 2026, the owner's decision)

Codex shows "Hooks need review" the first time on each machine, and again whenever spandeck's hooks change, and runs no hook until someone answers. The owner asked: "There is no way for spandeck to auto approve?" It was proposed that spandeck answer that screen only when every hook is its own. The owner: "When starting a new pane, would it be a checkmark for any agent to trust spandeck hooks? Should be checked on by default". `crates/agents/src/hookstrust.rs` (reads the screen and the files Codex takes hooks from, presses nothing), `crates/core/src/hookstrust.rs` (whose choice, the safety condition, the keys), and `crates/core/src/startscreen.rs`, which now holds what this and the folder-trust question have in common, once. No migration is added. This is the **second named exception** to "spandeck answers none of an agent program's own prompts"; the Guarantee line under Enforcement and `SECURITY.md` name both.

**The rule.** The owner's standing choice, visible where a pane is started and on by default, is the consent. spandeck then chooses "2. Trust all and continue" on that one screen, once per start of the program, and only when the hooks under review can only be spandeck's own.

- **Where the choice is made.** A tick in the New pane dialog and in the phone's New session sheet, "Trust spandeck's own hooks in <agent> if it asks", shown for a program that has such a review and whose screen spandeck can read (today Codex; another program is one screen and one list of hook sources in `agents/hookstrust.rs` away). `spandeck pane new --no-trust-hooks` is the tick taken off (`--trust-hooks` puts it back). Agent setup has the same choice as a switch per station, "Trust spandeck's own hooks when an agent asks". **On by default.** Unticking is remembered for the station and for later panes; ticking turns it on again.
- **Where it lives.** In the station's own key-value store (`hooks_trust`), like folder trust: **never in a project's file**, which a cloned repository could carry.
- **Who may use it (rule 7).** `pane.spawn` with `trust_hooks`, `hookstrust.choice`, `hookstrust.set` and `pane.trust_hooks` are the owner's: on no agent's list, no station's and not the read-only one; they reach another station only as the owner's forwarded request. The choice on a pane is worked out by whoever starts it and is never read from a caller's parameters. A pane an agent asks for (`delegate`) and a project's launcher start with the owner's standing choice as it is; an agent can neither set it nor call anything that answers the screen.
- **The safety condition: spandeck trusts only its own hooks.** "Trust all" trusts every new or changed hook Codex found, from every source. So before any key, and again each time the screen is looked at, the station reads the files Codex takes hooks from and presses nothing unless all of this holds:
  - the station is the one that keeps the agents' settings (`agent_home`, or the station of the account); another station installs no hooks and answers nothing;
  - the hooks file it manages (`~/.codex/hooks.json`) holds spandeck's entries and nothing else, and its `hooks` are **exactly** what this version writes for this station's own program path (the marker comment alone is something anyone could write);
  - there is no other source: no table of hooks in `~/.codex/config.toml` (anywhere in it, a profile's included; Codex's own `[hooks.state."…"]` trust records are not hooks), no `.codex/hooks.json` and no `.codex/config.toml` with hooks in the pane's folder or any folder above it, none in `/etc/codex` (`hooks.json`, `config.toml`, `managed_config.toml`, `requirements.toml`), no plugin switched on in any of those config files (a plugin can bring hooks, and which do cannot be read, so any plugin that is on counts), no hook setting on the program's own command line, and no other settings folder (`CODEX_HOME`); a file that cannot be read or parsed counts as a source;
  - the number on the screen is **at most** the number of spandeck's hooks (12 today). It is not held to equal the number not yet trusted: that would need Codex's `trusted_hash` of each hook, and how it is made is not documented, so it is not guessed.

## AgentVault (14 Nov 2026)

- spandeck and AgentVault stay separate programs. spandeck works without a vault.
- The vault is the only place a token is issued, and only when the owner approves on the vault's own page. The vault passphrase is never typed into the Control Deck. Approval opens in a small pop-up window on the vault's address.
- One token per station, held by spandeckd in a file only the user can read. Panes and agents never get the token, and keys are never put in a pane's environment.
- The token can list keys and send requests through the vault's proxy, read-only by default, and is pinned to the station's Tailscale node.
- spandeck finds the vault by its Tailscale name; the address is never hard-coded. `[vault] url` in the config overrides it.
- Tokens do not expire by default. Rotation is a per-station setting (never, or every N hours, at least 1) that only the owner changes; spandeckd rotates by itself.
- The owner is told when the setting changes outside the Control Deck, or the token is swapped or refused.
- Connecting a station is the only step: by default its agents may use every key the owner allowed that station's token at the vault (changed 14 Nov 2026 at the owner's request; before, a project had to list its keys). A project can narrow its agents with `[vault] keys` in `.spandeck/project.toml`.
- When a station has a token, a raw key in an agent's command is blocked and reported to the vault; one pasted into a prompt, or found in a transcript, is reported.
- **Connect prompt** (the owner's request, 14 Nov 2026: "there should be nothing I need to do"). A Control Deck that opens on a station that found a vault and has no working token says so once, in a bar that blocks nothing, with one button that starts the connect flow. "Not now" is kept by the station (so it holds in every browser), is undone from the Vault screen, and is forgotten when the station connects. No prompt when no vault was found or `[vault] enabled = false`.
- **Check and repair.** spandeckd checks the chain from an agent to a key when it starts, when a Control Deck opens (at most once a minute) and when asked (`vault.check`, the owner's only): the vault's address, its lock, the station's token (accepted, and tied to a machine), the key list, and what panes need (spandeck's own program and socket; Antigravity's plugin). It repairs without the owner: a token the vault calls overdue is swapped, Antigravity's plugin is rewritten (since 16 Nov 2026 by the station of the account only: see Only the station of the account writes the agents' settings in your home). Each thing it cannot repair is one sentence with one action, in `vault.status` (`checks`, `health`), on the Vault screen and in `spandeck doctor`, and is told to the owner once (`vault.alert`), not on every check and not again after a restart.
- A repair never gets a token any way but the owner's approval at the vault.
- A connected station shows its token to no address but the one that issued it (a security fix of 14 Nov 2026: no other machine can ask for the token by claiming to be a vault). When that address stops answering and another AgentVault answers on the owner's machines, the station does not try its token there: it says "The vault seems to have moved to <address>" and offers Reconnect, the ordinary approval. Following a move with the existing token is behind `[vault] follow_moves = true`, off by default: relaxing the guard is the owner's decision, and the owner has not made it.

## Add a machine (14 Nov 2026, the owner's request)

- The fleet screen ends in an "Add a machine" tile. It lists the Mac and Linux machines under the owner's Tailscale login that are online and not stations; phones, Windows, tagged and shared machines are left out. The station the owner is using connects to the one picked over SSH, runs the same install script as the README, starts spandeck there now and at login, and has it ask to join as `spandeck fleet --join` does. The tile then shows the join code.
- **The approval step stays.** The new station is approved with the usual control, by its code. A code that arrives over SSH is shown only if this station holds a waiting request with the same code. The join step is one place in the code (`JoinBy` in `crates/core/src/add.rs`), so a single-use ticket could replace the code later; no ticket exists.
- **Its own setting, off by default: `add_machines = true`** in the config of the station that does the adding, not `remote_start`. Both let a station run a command on another machine, and both are off until the owner turns them on at that station. They are separate because they differ in what they risk: `remote_start` runs one fixed command on a machine that is already a station, with access the owner already set up; adding installs software on a machine spandeck has never run on, and can use a password typed into the deck. An owner who wants one has not agreed to the other. The picker works while it is off and says how to turn it on; nothing is run and no password is accepted.
- The owner can also turn it on, and off again, from the tile itself (changed 14 Nov 2026: the owner clicked the tile and asked why they could not add a machine). The switch is kept in the station's state, is logged, is the owner's alone (`fleet.add_enable` is on no agent or station list and is never forwarded), and applies only to the station whose Control Deck they are using. It stays off until the owner turns it on.
- **Only the owner, and only at the station being used.** The methods are on no list for agents or other stations, and are never forwarded between stations in either direction, so a password never travels from one station to another.
- **The password** is asked for only after a first try without one fails (Tailscale SSH or an SSH key that already works needs none). It is used for one connection and held in memory until ssh has asked for it once, or the connection ends. It is never written to a file, a log, the ship's log, an event, an error or a command line or environment: ssh gets it by running spandeck itself as its askpass helper, which is handed it once over a private socket, and only for a prompt that asks for a password. A second prompt gets nothing, so a wrong password is tried once. The ship's log records who added which machine as which user and how it went.
- **Host keys.** The address is the one the local Tailscale client gives for the machine picked, and must be a Tailscale address; a caller names a machine, never an address. The first connection saves the machine's host key in `known_hosts` in the state directory (ssh's accept-new); a different key later is an error, shown plainly, and nothing is sent. The owner's own ssh config is not read, so it cannot redirect the connection or switch checking off.
- What the machine prints is shown as it runs. It is text from somewhere else: control characters are dropped and the Control Deck inserts it as text.
- `add_machine_cmd` replaces the ssh command (`{user}`, `{host}`, `{known_hosts}`); the script arrives on its standard input. The script uses only commands every release has, since the release it installs may be older than the station that sends it.

## Adding a station that is running, and uninstalling one (15 Nov 2026, the owner's request)

"I dont know how to add these two machines, I shouldnt have to go to that machine, I should just say add to the fleet but its asking me to join their fleet." "I also cant delete the machine then re-add it."

- **"Add X to this fleet…"** is on the tile and in the menu of a station that is running but is not in this fleet. It replaces the instruction to go to that machine and type `spandeck fleet --join`, and it replaces "Join X's fleet…" and "Merge this fleet into X's…", which are no longer on any Control Deck menu: the owner adds to the fleet they are looking at. `spandeck fleet --join` stays in the command line, unchanged.
- It is Add a machine without the install (`fleet.add` with a station's name). The station the owner is using connects to the other over SSH, which is what shows the request is the owner's; finds the spandeck command there (where the installer puts it, then the PATH, then `~/.cargo/bin`); checks it answers; and has it ask to join this station, as `spandeck fleet --join` does. The code it is given appears here and is approved here, with the usual control. The switch, the user name, the password, the host key and the progress are those of Add a machine.
- **Its fleet-mates come with it**, because a join is a merge. The dialog says so beforehand, and names them once the request has arrived. A station tells whether it brings its mates in what it says of itself to any device under the owner's login (`station.hello`: `merge`, with its operating system). One that does not say so runs a version from before the merge: the dialog says it will join alone and that any station it shares a fleet with stays behind, to be added the same way.
- **The address** is the one this station found that station at, and it must be a Tailscale address or one the owner wrote under `peers` in this station's config. A caller names a station, never an address.
- **"Uninstall spandeck on X…"** is in the menu of every other station that answers (`fleet.uninstall`). In order:
  1. If X is in this fleet, it is removed from it exactly as "Remove this station from the fleet" does: its panes closed, a new key for the stations that stay, X forgotten. The browser that asked gets its new token in the reply.
  2. Over SSH, spandeck on X is told what a removal with "also stop spandeck there" tells it (`station.leave` with `stop`, through its own command line): it closes its panes, takes its login service out and ends. That code touches the login service only when the account it runs under has one.
  3. The script deletes the programs: `spandeck` and `sd` where the installer put them, or where the command was found if it was built from source (on Windows `spandeck.exe`, `sd.exe` and `spandeckd.exe`), and the copies kept for upgrades under the state folder.
- **Kept by default: the state and config folders**, which hold the station's history, archive and settings, so that adding the machine back picks them up. The tick box "Erase everything" deletes them too; a folder is deleted only if it is spandeck's (it holds the database, the key or the config, or is named `spandeck`), and never the home folder. Helpers' worktrees live under the state folder and go with it. **The owner's project folders are never touched**, with or without the box.
- If spandeck was not running on X, the script takes the login service out itself, and only if the service's own file is in that account. It never stops a process by name. No test reaches a real login service: the test's machine has stand-ins for `systemctl` and `launchctl` first on its PATH and a home folder of its own, and the test checks the stand-ins were what was asked.
- If the SSH step fails after step 1 (a password is needed, say), nothing has been deleted on X: it is running, outside the fleet, and the same dialog asks for the password and goes on from step 2. A station that does not answer cannot be uninstalled: "Remove" takes it out from the fleet's side. The station the owner is using cannot uninstall itself.
- The dialog names the station and its pane counts, opens on Cancel and acts only on the red button. Afterwards the machine is listed under Add a machine again.
- **Authority.** `fleet.add` and `fleet.uninstall` are the owner's alone, on no agent's list and no station's, never forwarded in either direction, and refused unless adding machines is turned on at the station being used (`fleet.add_enable`, or `add_machines = true`). The ship's log records who, which station, which user and how it went (`fleet.add`, `fleet.uninstall`).
- **Browsers signed out in a fleet stay signed out when stations arrive.** The key is handed over with the list of browsers signed out in that fleet, at a join and with `fleet.rekey`, and the station that takes the key refuses them too. Before, a station that joined accepted every token made with the key, including one the owner had signed out. A station on an older version ignores the list.
- After a request to join, the asking station looks for its answer every 0.4 seconds for the first 16 seconds, then every 1.5 seconds as before.

## Usage and cost (14 Nov 2026, the owner's request)

- Token counts are only what an agent wrote in its own session data: Claude Code's and Codex's session files, OpenCode's session database. Antigravity keeps nothing spandeck can read, and is shown as not reported. Nothing is typed in by the owner.
- Counted per conversation and per model, sub-agents included under the model that ran them; a model call written more than once is counted once. A new conversation starts from zero; the station keeps its totals.
- Cost is an estimate at list prices and is called that wherever it appears, with the list's source and date: a subscription is not billed per token.
- Prices and context windows come from a public list (models.dev) that spandeckd fetches by itself once a day and keeps. The request carries nothing about the owner or a project. No price or window size is written into the code; a model the list does not name has no price. `[prices]` in the config is an optional override, never needed.
- The context gauge uses the window the session data states (Codex), else the list's.

## Guarantees (contracts the build must meet)

### Tasks
- Fields: goal, acceptance criteria, agent, station, workspace, dependencies, outputs, review outcome, resume information.
- States: queued, running, waiting for approval, blocked, completed, failed, cancelled.
- An agent going quiet is not completion. A task is completed only by an explicit result or a sign-off.

### Stop, pause and offline
- Work already running continues if the network drops or the controlling station disappears.
- No new remote assignment is accepted without a valid task authorization; these expire.
- Pause: no new work is delivered; the current turn finishes.
- Stop: the agent's current turn is interrupted; the process stays.
- Kill: the process ends.
- A stop never reports a program it could not reach as stopped: a program that is not reading its terminal is listed as not reading, and the owner is told to use Kill (15 Nov 2026). What a stop can know is whether the terminal took the key, not whether the program read it: while a terminal that nobody reads still has room (its first few kilobytes), the key goes in and the stop says stopped.
- A stopped agent stays stopped: no mail reaches it by any road, typed or through a hook, until the owner releases it. An agent the station started again after a restart waits for the owner the same way. (Both decided by default on 15 Nov 2026 and switchable per station; see A stopped agent stays stopped.)
- Pause, the stop's mark and the restart's mark are apart: releasing a pane never ends its Pause, and no mail reaches a paused agent by any road.
- Only the owner releases a pane, and never by looking at it; no agent and no other station can.
- The Control Deck shows three separate states: stop requested, stop confirmed, station unreachable. It never implies an unreachable station has stopped.
- A stop request for an unreachable station is delivered on reconnect and applies only to the work that was running when it was issued.

### Messages
- Every message has a unique id. Delivery is at least once, duplicates dropped by id, so a reconnect cannot start the same task twice.
- Ordering is guaranteed within a thread only.
- Received and acted-on are separate acknowledgments.
- A message for another station is sent as soon as it is stored, by that station's own sender: no station's messages wait for another station. A message that the other station refuses for good is reported to its sender, once: a task whose authorization expired while it waited is refused there, as before, never sent again by itself, and its sender is told (15 Nov 2026; see A message for another station goes at once).
- An agent is told of its mail in one line that says to read it and act on it, by every road; the line names who sent it and how many, and never quotes a message. Mail that an agent does not take is announced less and less often and then not at all, stays unread, and the owner is told why; a nudge is never typed on top of one that was not sent (16 Nov 2026; see Every agent can talk to every other agent).
- Mail is for the pane it was sent to. When that pane is closed for good its unread mail goes back to its senders, who are told once; it is not handed to another pane that is later given the name. A pane that is restarted or restored keeps its mail, and so does the name a project starts its own pane under (16 Nov 2026).
- What a station shows of a message is what that station knows: the station a message was sent from learns that it was answered from the reply, is not told that it was only read, and says so (16 Nov 2026).
- A request that is tried again because its answer did not arrive carries the id it was first made with, and is carried out once: a `send` tried again is one message, its id written in the message's own transaction. What is typed or sent into a pane, a hook, and a call whose answer carries a token or a secret are never kept and never sent a second time; Stop, Kill, Pause and an answer to an approval are never held back by this, and are safe a second time by their own records. When a station cannot tell whether a change was carried out it says so, and does not carry it out again (15 Nov 2026; see A retried change is done once).

### Workspaces
- The parent agent, or the user, integrates a helper's branch. A conflict goes back to the helper as a task.
- After a crash the worktree and branch are kept, and the task is marked failed with its resume information.
- A sign-off names the commit reviewed and becomes stale if the code changes.

### Trust
- The user at the Control Deck has full authority on every station.
- An agent has only what its task grants. Permissions are separate: discover, read history, execute commands, administer a station. Agents never get administer.
- A station removed from the fleet can no longer act on the stations that took the new key: its signed calls are refused and browser tokens made with the old key are not accepted.
- A station that joins another fleet never leaves a station of its own fleet behind: each takes the same key, at once or when it is next seen.
- A request to be let in can be answered at any station of the fleet, by the owner only, never by an agent.
- Every station of a fleet lists the same signed-in browsers, and a browser signed out at one is refused by all, including a station that was off, as soon as it is back.

### Sharing and archive
- Captured events and posted findings: on by default. Transcripts via recall: own always; same project scrubbed; cross-project opt-in.
- Raw history stays on the station that recorded it. Other stations and agents only see the scrubbed view. Scrubbing is best-effort. The owner's own signed-in browser is neither: it is shown a pane's conversation as it was written, as it is shown the pane's terminal, and a station that passes that on to it keeps none of it (15 Nov 2026; see The conversation view).

### Enforcement
- Observing an agent and enforcing a rule on it are separate channels. Screen detection observes; only a hook or approval channel can block.
- A rule is shown as enforced for an agent only where that agent's integration can block it. Elsewhere it is guidance.
- Where a rule is enforced for a pane, it is not passed over because spandeck is away: the agent's tool call waits for the daemon and, if it stays away, is refused. Where none is, or the agent cannot be blocked, the call goes ahead. (Decided by default on 15 Nov 2026 and switchable per station; a session started before 16 Nov 2026 waits 8 seconds, a later one 60; see While spandeck is away.)
- An approval that is waiting when the station restarts is still the same approval afterwards: it can be answered, by the owner only, and the agent is given the answer once.
- A screen that waits for the owner (a sign-in, a quota that has run out, a trust question, a permission prompt of the program's own) is shown as needing the owner, with the reason in plain words. spandeck answers none of them (16 Nov 2026), with one exception, two lines down: a folder's trust question, on the owner's standing choice.
- A question an agent asks the owner, and a plan it wants approved, are answered by the owner only, with the agent's own choices or the owner's own words, and the agent is given the answer once. When nobody answers, the agent shows its own prompt in its terminal: nothing is ever answered for the owner (16 Nov 2026; see Answer in place), with the one exception in the next line.
- A program's question whether to trust the folder it was started in is answered by spandeck only on the owner's standing choice for that folder and program, or for a project the owner switched on: the program's own first screen, word for word, once, with Enter pressed only when its marker is seen on the trusting choice (spandeck moves it there first where the program starts it on "No", unless `folder_trust.move = false`). No agent and no other station can make, read or use that choice (16 Nov 2026; see The folder-trust question).
- A program's review of new or changed hooks (Codex's "Hooks need review") is answered by spandeck, with "Trust all and continue", only on the owner's standing choice for the station (on unless they turned it off) and only when the files the program takes hooks from show that the hooks under review can only be spandeck's own, as this version installs them, with no other source of hooks: the program's own first screen, from its first row to its last, once. Otherwise nothing is pressed, the pane says why, and no one-tap answer is offered. No agent and no other station can make, read or use that choice. These two are the only prompts of an agent program that spandeck ever answers (16 Nov 2026; see Trusting spandeck's own hooks).

### Upgrades
- Before: a version compatibility check between stations. After: a health check, and rollback to the previous binary if it fails.
- If live handoff does not complete, terminals are lost and agents resume by session id.
- Live handoff is a release acceptance test on macOS and Linux.

## Recommended defaults
- Helpers always start in a fresh pane; helpers cannot delegate further unless a role allows it.
- The ship's log keeps each tool call's name, timing and result; full contents live only in the session archive.
- The ship's log is best effort: under a locked database or a full disk its oldest waiting entries can be dropped, and are counted. A pane's record and the safety records (a stop, a pause, an answer to an approval) are tried again until they are written (15 Nov 2026; see Nothing waits for the database).
- Processes do not survive a daemon crash; agents resume by session id.

## Testing rules (from the Build and test plan tab)
- Test where spandeck can break: the terminal, each agent integration, the Guarantees, the link between stations, upgrades. Target 150 to 300 tests (raised from 250 on 15 Nov 2026, with the performance and continuity plan; its new cases that start a station are a few scenario tests with many assertions each, marked ignored and run with `--ignored`, not one test per case). Counted on 16 Nov 2026: 378 on Linux (306 in the every-change tier; 72 ignored, of which 12 are pictures and live canaries), and 18 more that run only on Windows. That is over the target, and the target was not raised for it: whether it is raised, or which tests go, is the owner's to say.
- A test needs a reason: a Guarantee, a phase's acceptance criterion, or a real bug. No tests of trivial code, no mocks of our own modules.
- Every-change tier under 90 seconds; merge tier under 10 minutes. A flaky test is fixed or deleted within a day.
- The station link sits behind a swappable transport so the message relay runs under Turmoil.

## Windows (14 Nov 2026, the owner's request: a Windows PC as a full station)

Built and tested on a real Windows 11 machine (rtx6000) since 14 Nov 2026; each line says
what was decided and why, and "unlike Unix" lines say what the owner gets less of. What has
not been tried on a real machine is said where it applies.

- **Native, not WSL.** x86-64, Windows 10 1809 or later (the first with ConPTY) and Windows 11.
- **Rule 4 of AGENTS.md now reads:** platform code lives only in `crates/terminal/src/sys/`:
  `unix.rs`, `windows.rs`, and `mod.rs` which picks one. Everything that differs by system
  (terminals, the local socket, private files, process control, the shell, start at login,
  keep-awake) is behind that one interface, and no other file in any crate names `cfg(unix)`,
  `cfg(windows)`, `nix`, `libc` or `windows-sys`. A value that differs (a folder, a command)
  is asked of `sys`, or chosen by `if sys::WINDOWS` in ordinary code that is compiled and
  checked on every system, never with a `cfg` where it is used. Exceptions, each one line:
  `spandeckd.rs` (the attribute that makes it a windowless program); a test that cannot run
  on Windows carries `#[cfg_attr(windows, ignore = "<the reason>")]`; a test file for one
  system only begins `#![cfg(unix)]` or `#![cfg(windows)]`. `pty.rs` keeps the types every
  system shares. Reason: the rule was written so a Windows port replaces one
  place; it is now a folder instead of a file because the port is more than the PTY.
- **Terminals: ConPTY** (`CreatePseudoConsole`), one per pane, with the program started by
  `CreateProcessW` inside a job object that is ended when it closes. Kill is ending the job
  (the whole tree, as `killpg` is on Unix). Hang-up is closing the pseudoconsole, which tells
  every program on it to close. Interrupt is Ctrl-C typed into the pane, as on Unix. A pane's
  exit is its first program's exit code (there are no signals, so `ExitInfo::Signal` never
  appears). A program that is a `.cmd` or `.bat` file (npm's `claude.cmd`) is run through
  `cmd.exe`, with every argument quoted the way Rust's standard library does it so that `&`,
  `|` and `%NAME%` in an argument stay text; an argument with a line break is refused.
  Because the job ends with the daemon, no pane's program outlives a daemon crash: the
  job belongs to the pane host (below), not to the daemon.
- **Local socket: a named pipe**, `\\.\pipe\spandeck-<hash of the state folder>`, in place of
  the Unix socket, behind one `sys::local` interface (listener, async stream, blocking client)
  that the server, the client, the askpass helper and the tests all use. Only the same user
  can open it: the pipe's access list names that user alone, remote clients are refused, and
  the daemon must be the pipe's first creator. The client checks that the pipe it opened is
  owned by its own user before it sends its token, so a pipe another account made first under
  the same name gets nothing. The token is still required, as on Unix.
- **The pane host** (the owner's decision, 14 Nov 2026: "build the extra helper"). Windows
  cannot replace a process's program in place, and a pseudoconsole belongs to the process
  that made it, so on Windows the panes are not in the daemon: `spandeck-pane-host.exe`, a
  small program of its own, owns every pseudoconsole, job and program, and the daemon is its
  client over a named pipe only the same user can open. So an upgrade, a restart and going
  back to the previous binary keep every terminal on Windows as they do on Unix
  (`live_handoff` is true everywhere), and the Upgrades Guarantee and its tests are the same
  on both. The new daemon is a new process there (on Unix it is the same one).
  - **The screen stays in the daemon.** The host knows nothing of screens, agents or
    projects: per pane it keeps the terminal, the exit status, and the last 8 MB the program
    wrote, each byte numbered. At an upgrade the old daemon hands the new one its picture of
    each screen (as on Unix) and the number of the first byte it did not take; the new one
    asks the host for output from that byte on. Nothing is lost or shown twice unless a pane
    writes more than 8 MB while no daemon is reading, and then the oldest of it is.
  - **A daemon crash no longer ends the panes on Windows.** The next daemon finds them in
    the host and rebuilds each screen by replaying what the host kept: the screen is right,
    and scrollback goes back as far as those 8 MB. This changes a recommended default
    ("processes do not survive a daemon crash") for Windows only; on Unix it stands. So that
    panes nobody can reach are not kept for ever, a host with no daemon ends its panes and
    itself after ten minutes (the supervisor starts a failed daemon again after a second; see
    Start at login).
    Stopping the station on purpose ends the panes and the host at once.
  - **The host is not upgraded while it holds a pane**: it cannot be without ending them.
    Its protocol is versioned and only grows; a daemon speaks every host protocol back to 1
    and never asks an older host for what it does not have, so an old host keeps serving its
    panes under a new daemon for as long as they live. A host older than the daemon is
    replaced by itself at the first moment it holds no pane (`station.info` shows
    `pane_host.outdated` until then). A change the old protocol cannot carry would need the
    panes ended: such a release must say so before it is installed, and the owner decides
    when. None exists.
  - If the host itself dies, its panes die with it (their jobs close); the daemon says each
    ended and starts a new host for the next pane. Agents are then resumed by session id at
    the next daemon start, as after a reboot.
  - On Unix the host is not used (exec in place needs none); `SPANDECK_PANE_HOST=1` turns
    it on there, which is how it is tested on Linux.
- **The installed program is replaced by renaming.** A running `.exe` cannot be overwritten
  but can be renamed, so an update moves `spandeck.exe` to `spandeck.exe.old` and puts the new
  one in its place; the old file is removed at the next start. `state\bin\running` and
  `previous` are hard links as on Unix (same volume), else copies. The same goes for the
  pane host's file while it runs, and for `spandeckd.exe`, which runs for as long as the
  station does. A program still running from `.old` at the next update keeps that name, and
  the file moved aside then is `.old2` (up to `.old9`); each is removed at the first
  replacement after nothing runs from it (15 Nov 2026: before, the second update while an
  old copy ran could not replace the file).
- **Start at login: a per-user Scheduled Task** ("spandeckd", at log on, restart on failure,
  no time limit, runs on battery), not a Windows Service: a service runs in session 0 without
  the user's profile, PATH or the agents' logins. The task runs `spandeckd.exe`, a windowless
  program that starts `spandeck.exe daemon` with no console window, so no window opens at
  log on.
  **Unlike Linux with linger, the daemon runs only while the owner is logged in** (a locked
  screen is fine; logged out is not). The owner accepted this (14 Nov 2026: the machine logs
  on by itself).
- **`spandeckd.exe` supervises the station, not the process it started** (15 Nov 2026, after
  a fault measured on rtx6000). Until then it waited for the one daemon it had started and
  passed on its exit code for the task's restart-on-failure. An upgraded daemon is a new
  process on Windows, so after the first upgrade the wrapper's child had ended with success,
  the wrapper with it, and nothing watched the daemon that was running. Measured: the
  station's daemon, upgraded many times, was ended with `taskkill /F`; nothing started it in
  150 seconds; `schtasks /run /tn spandeckd` brought it back, with its three panes under the
  same pane host. So a Windows station that crashed after its first upgrade stayed down until
  the next log on, its agents running where no Stop and no hook reached them. The rule now:
  - **It follows whichever daemon is current.** That is the process the station's pid file
    names, believed only if that process was started before the file was written (Windows
    gives a pid out again; only the daemon that wrote the file, or the one it was written
    for, can be older than it); failing that, the pid the station gives when asked on its
    pipe, which only a daemon of that state folder answers. A daemon that hands over (an
    upgrade, a restart in place, going back to the previous binary) writes the next one's pid
    in the pid file before it ends, so there is no moment when the file names nobody while
    the new daemon waits for the old one (`SPANDECK_WAIT_PID`).
  - **When that daemon ends:** another is already named: follow it, start nothing. It ended
    with success and the clean-stop mark is set (`restore.stopped_clean`): it was stopped on
    purpose; the supervisor ends too and nothing is started until the next log on or
    `schtasks /Run /TN spandeckd`. It ended with success, no mark, nobody named: a hand-over
    from a daemon older than this rule, so the next one is waited for, 30 seconds; if none
    comes and the station's database says it was not stopped, one is started. Anything else
    (a crash, a kill): a daemon is started after 1 second, then 2, 4, 8 and so on up to 5
    minutes between tries, and from 1 again once a daemon has stayed up 10 minutes. Each such
    start is an unclean one to the daemon, whose own guard still holds agents back at the
    third in 10 minutes (After a restart); panes in the pane host are not affected.
  - **Stopping on purpose is `spandeck service --stop`** (new with this): a daemon with no
    console can be sent no signal, and one that is merely ended is now started again. The
    daemon listens for a request named for its state folder and stops as it does for SIGTERM
    on Unix: panes and pane host ended, the mark written. On macOS and Linux the command
    prints the login service's own stop command. `station.leave` with stop, and the uninstall
    that uses it, stop the same way. Any program of the same Windows user can make the
    request, as any can end the process; no agent is given an RPC for it.
  - **One supervisor per station.** Being it is holding a named object that goes when the
    process does; a second copy (a second log on, the task run by hand) finds it held, ends
    with success and starts nothing. A copy started with nothing running adopts a daemon that
    is running instead of starting a second.
  - **It is replaced at an update without a log on.** The update moves the running
    `spandeckd.exe` aside and installs the new one (as above); the new daemon, once healthy,
    starts the new one, told to take over: the old one leaves and the new one follows the
    daemon. This is done for a station that has a supervisor, or that is the one started at
    log on (the usual state folder, the task's script present): so a station installed before
    this gets its supervisor at the update that brings this, with nothing to do by hand.
    The supervisor so started is not the task's own process: Task Scheduler shows the task as
    ready, not running, and running it then starts a copy that ends at once.
  - It writes what it did, and why, to `spandeckd-supervisor.log` in the state folder.
  - **Not covered:** a daemon that hangs without ending; a supervisor that is itself ended
    (the daemon runs on, and is supervised again at the next update, log on or run of the
    task); a stop whose mark the database did not take in the two seconds the daemon gives
    it, which is then taken for a lost hand-over and started again after 30 seconds.
  - **Tried on rtx6000** with stations under folders of their own and `spandeckd.exe` run
    directly: a daemon ended after two upgrades comes back with its panes, twice; a stop on
    purpose after an upgrade is not undone; an upgrade, and one that goes back, start
    nothing; a second supervisor ends; an update from a local release (`station.update`)
    replaces the file of a supervisor that is running, for the second time, and the daemon it
    brings starts the new one, which takes over and then restarts an ended daemon. **Not
    tried:** any of it under the Task Scheduler in the owner's desktop session (the tests ran
    in an SSH session, where the objects named for every session and for one are the same),
    and the update of a station that has the old wrapper, which is taken to be "the usual
    state folder and the task's script" and not something a test station can be. macOS and
    Linux are unchanged: systemd and launchd restart the daemon and follow it through an
    upgrade, since it stays one process.
- **Keep-awake** is `SetThreadExecutionState`, held by `spandeck keep-awake` (the same shape
  as `caffeinate` and `systemd-inhibit`: a helper that holds the machine awake while it runs).
  The helper ends when the daemon does. It does not stop a laptop sleeping when its lid shuts.
- **Shells.** A shell pane runs PowerShell 7 (`pwsh.exe`) when installed, else Windows
  PowerShell, else `cmd.exe`. One shell line (an install or update command from the catalogue)
  runs through Windows PowerShell 5.1, which every Windows has
  (`powershell -NoProfile -ExecutionPolicy Bypass -Command`); nothing needs PowerShell 7. Install-before-launch
  is not a second script in another language: on Windows the pane runs
  `spandeck install-then-launch`, the same steps written in Rust (say what was found, show the
  command, run it in the pane, Ctrl-C skips, start the first copy that answers).
- **The agent catalogue has a Windows list**, read from each vendor's documentation on
  14 Nov 2026: Claude Code (PowerShell script, npm, WinGet), Codex (PowerShell script, npm),
  OpenCode (npm only: its page has no Windows installer and says Windows package managers are
  not supported), Antigravity (PowerShell script). All four document native Windows. The
  update commands of Codex, OpenCode and Antigravity were read from the programs on Linux and
  are not confirmed for Windows.
- **Hooks.** Claude Code on Windows runs a hook in Git Bash when that is installed and in
  PowerShell when it is not; no one command line is right in both, so spandeck's entries name
  PowerShell (`"shell": "powershell"`) and use `& '<path>' hook claude`. Each hook then costs a
  PowerShell start; if that proves slow on the real machine, the no-shell form (`command` plus
  `args`) is the next thing to try. Codex documents no way to name the shell for a hook on
  Windows: the same line is written and is unverified, and screen detection covers Codex
  where its hooks do not fire, as on Unix.
- **Folders.** State in `%LOCALAPPDATA%\spandeck`, config in `%APPDATA%\spandeck`
  (`SPANDECK_STATE_DIR` and `SPANDECK_CONFIG_DIR` still win). Home is `%USERPROFILE%`; `~` means
  that. A program name is looked for with each extension in `PATHEXT`. Paths are compared as
  the file system compares them (by the file's identity, not its spelling).
- **Private files** (the client token, the fleet key, the vault token, agent setup): the
  state and config folders get an access list of the user, SYSTEM and Administrators only,
  not inherited from the parent, when the daemon starts; files written in them inherit it.
  That is what a default profile folder already has; setting it makes it true when
  `SPANDECK_STATE_DIR` points somewhere else. Administrators can read them, as root can on Unix.
- **Tailscale** is asked through its CLI on every system (`tailscale status --json`,
  `whois --json`), never LocalAPI, so Windows needs only the program's place:
  `tailscale.exe` on PATH, else `%ProgramFiles%\Tailscale\tailscale.exe`.
- **Install and update.** `scripts/install.ps1` is `install.sh` for Windows: the release zip
  for `x86_64-pc-windows-msvc`, SHA-256 checked, installed in `%LOCALAPPDATA%\Programs\spandeck`,
  added to the user's PATH, the task registered. The release has `spandeck.exe`, `sd.exe` and
  `spandeckd.exe` in a `.zip`; `station.update` picks it and unpacks with the `tar.exe` Windows
  ships. Other processors (ARM64) are not built yet.
- **Add a machine can add a Windows machine** (the owner's decision, 14 Nov 2026). The
  picker lists Windows machines too. The station connects with the same `ssh` command and
  hands the machine a Windows PowerShell 5.1 script with `install.ps1` inside it (as the Unix
  script carries `install.sh`): install, register and run the log-on task, wait for spandeck
  to answer, ask to join. The line that reads the script there has no `$` and no quote of
  its own inside, so it means the same whether that machine's OpenSSH hands it to `cmd.exe`
  (the default) or to PowerShell. The approval step is unchanged. It needs the OpenSSH
  server on there, which Windows ships switched off and only an administrator can add, and
  the owner logged on there (the station runs in their session, not in the SSH session,
  which ends). Its own failure sentences: the OpenSSH server not installed or not running;
  Windows refusing to run spandeck (Smart App Control blocks programs it does not know, and
  releases are not signed); installed but not started because nobody is logged on. The
  script is run on a real Windows in a test as far as its network check; a whole add of a
  Windows machine has not been done yet. A Windows station adding another machine uses the
  same code with `ssh.exe`; typing a password that way (askpass) is untried on Windows.
- **Certificates on Windows: the system's verifier, with the Mozilla roots as a second
  source** (15 Nov 2026, after a fault on rtx6000: the first contact with the vault failed
  with `UnknownIssuer` on a good Let's Encrypt chain, and worked once curl had connected to
  the same address). Windows keeps only the roots it has needed and fetches others on
  demand; that fetch did not happen for spandeck's check. Which of Windows' rules stopped it
  was not established: the machine has the root now, so the state cannot be made again. The
  fix does not depend on the answer: when Windows cannot build a chain to a root it has,
  the same Windows verifier is asked again with the Mozilla root list carried inside
  spandeck (`webpki-root-certs`). Verification is not weakened: Windows still checks names,
  dates, usage and signatures, and a root an organisation added to Windows still works. The
  cost: a public root the owner removed from Windows by hand is still trusted by spandeck if
  Mozilla lists it, and the carried list is as old as the release. Every outgoing client is
  made in one place (`crates/core/src/http.rs`). macOS and Linux are unchanged.
- **Smart App Control.** Where it is on, Windows refuses programs it does not know, which
  includes every spandeck build, since releases are not signed. The owner turned it off on
  rtx6000. Signing the Windows release is what would make that unnecessary; it is not done.
- **Not on Windows yet:** wake-on-LAN of a Windows station (its network card's address is
  not read), starting a stopped Windows station over SSH (`fleet.start` runs a Unix line),
  usage figures for OpenCode (where its database is on Windows is not documented), and the
  Codex sandbox repair (a Linux problem). ARM64.
- **Tests.** On rtx6000 the whole suite runs (`cargo test --workspace`): everything passes
  except the eight tests that drive a browser, because no Chrome is installed there; they
  have never run on Windows. A test that needs a Unix shell, a signal or a tar.gz release is
  marked ignored on Windows with its reason (about thirty); nothing changes on macOS or
  Linux. Windows-only tests cover what is new: ConPTY (input, exit code, resize,
  environment, a `.cmd` file's arguments, kill ending the whole tree, hang-up), a station
  end to end (a shell pane over the pipe, an agent's hooks, every pane kept through a daemon
  crash, the state folder's access list), `install.ps1` against a local release, and the
  script Add a machine sends. The pane host and the local socket are tested on every
  system. CI has a `windows` job with the same tests; the scenario step reports without
  failing the job until the browser tests have been seen to pass there.
