# spandeck decisions

Read this before starting any task. It is a condensed copy of the Decisions tab of the
spec doc (https://claude.ai/artifact/QT8LDppx4qGnuttvvMwmPt). Where it disagrees with
anything else in the repo or the Features tab, this file wins. Copied 13 Nov 2026.

## Decisions

- **Rust, our own daemon, written from scratch.** herdr and Wolfpack are read for lessons, not forked.
- **v1 runs on macOS and Linux.** Windows is being added (see Windows, below); platform code stays isolated (`crates/terminal/src/sys/`).
- **Name**: spandeck; daemon spandeckd; the command center is the Control Deck; machines are stations, agents are crew, the event log is the ship's log.
- **Live handoff on upgrade, no per-pane host process.** The old daemon execs the new binary in place (same pid, inherited PTY descriptors). After a crash or reboot each agent resumes its conversation by session id.
- **Stations under the same Tailscale login find each other automatically, and each joins the fleet on the owner's approval, once** (changed 14 Nov 2026; before, they trusted each other with no step). There is one fleet: a station that joins brings its fleet-mates, and a request can be approved at any station (15 Nov 2026). Tailscale identifies a device, not a program on it, so a station also signs its calls with a fleet key and a browser on another device holds a token the owner approved. An agent reaching another station gets only what its task grants.
- **Agent messages are stored records** sent and received through tools (send, inbox, reply, ack), never keystrokes. A typed one-line nudge only wakes an idle agent.
- **A durable task record** exists for delegated, scheduled and recipe work. A pane you are just talking to has none.
- **Workspaces**: the agent you talk to stays in the main checkout; a delegated helper that writes gets its own worktree and branch; review-loop reviewers read a snapshot at the commit; testers read the same tree. Sign-off is bound to the commit reviewed.
- **Shared project memory** (start digest, findings board, automatic capture from hooks) on by default.
- **Session archive**: spandeckd copies every Claude Code and Codex session file as it grows, keeps raw lines plus a normalised copy, keyword search through `spandeck recall`. Own history always searchable; same-project on by default with secrets scrubbed; cross-project opt-in.
- **Standing orders at five layers** (fleet, group, station, project, role), as guidance and as enforced rules.
- **Review loop is the first recipe**: three rounds, stall check, sign-off before push.
- **Activity strip on every pane.** Tree, timeline, heat view are v1.5.
- **Usage per agent** (the owner's request on 14 Nov 2026; before, usage and cost views were not in v1): each pane shows its agent's model, tokens and context, with an estimated cost; the station and the fleet show totals. See Usage and cost.
- **Phone**: status, blockers, approval requests and stop controls; and, since 0.2 (the owner's request on 14 Nov 2026), talking to any pane: a message box that can be typed or dictated into, the keys a phone lacks, fitting the pane to the screen, and starting a pane. In the browser; no native app. Since 15 Nov 2026 (the owner's request): a conversation view of an agent pane, for the phone and the desktop, and on the phone a list of sessions that opens on what needs the owner and what was last active (see The conversation view).
- **Station-to-station SSH** uses short-lived certificates spandeck issues per task (v1.5, with cross-station delegation).
- Not in v1: desktop shell, native iPhone app and widget, Officer of the Deck, fleet updates and channels (of spandeck itself), common config, cross-station delegation, flow view, agent tree and timeline. (OpenCode and Antigravity adapters were on this list until 14 Nov 2026: see Agent programs.)
- **Planned, not built: a browser pane** (the owner's decision on 15 Nov 2026: "add the web page stream to the future plan"). A Chrome runs on the station, beside the agent and its dev server, and what it shows is streamed into a pane of the Control Deck, so it works for any site and from the phone. The agent drives it through tools (open, read, click, type) and the owner watches or takes over. To settle when it is built: the browser has a profile of its own, never the owner's sign-ins; the owner approves which sites an agent may act on; an agent's browser is its own, and another agent reaches it only if its task allows; the streamed page is kept apart from the Control Deck so that a page an agent built cannot act as the owner; what happens on a station with no Chrome. A pane that only frames a web page in the owner's browser was considered and set aside: most sites refuse to be framed, and it cannot see a station's localhost.
- **Tailscale key expiry in the Control Deck: step 1 (information) is built, steps 2 to 4 are planned** (see "The Performance page and Tailscale key expiry", below; the owner's decision on 15 Nov 2026: "a Tailscale token expiring and lost access to the machine ... how can we expose this in control deck, either information, or renew or disable token expiration"; the direction below was agreed the same day). A machine whose Tailscale key lapses drops off the tailnet with no warning from spandeck today. In order: (1) **Information**: each station reads its own key's expiry from its local Tailscale client and tells the fleet, so every station shows the same thing: the days left on each station's tile and on the health page, a notice and a phone push at 14, 7, 3 and 1 day and on expiry, still shown for a station that is off (its fleet-mates remember the date), and for the owner's devices that are not stations, the phone above all. (2) **Renew**: the deck starts the sign-in for a station and gives the owner the link to open where they are, if that can be done without cutting the connection in use. (3) **Never expire**: for a station, either a button that uses a Tailscale credential held in the owner's vault, on no agent's list, or a link to that device's page in Tailscale's admin console; recommended for always-on servers, not for laptops and phones. (4) **Already expired**: the deck says what happened and what the owner can still do from another station. To settle when it is built, from Tailscale's own documentation: what a peer can see of another's expiry, whether a remote renewal is safe, and the permission the credential needs. Step 1 went out with the performance page (15 Nov 2026); 2, 3 and the rest of 4 later.

## Pre-build resolutions (13 Nov 2026)

- One `spandeck hook` command for every vendor. Claude Code: hooks first. Codex: hooks where accepted, screen detection otherwise; the Codex adapter is fixture-tested and unverified until a live canary runs.
- Remote approval is in v1: the permission hook holds for an answer from the Control Deck or phone, then falls back to the terminal prompt on timeout.
- spandeckd listens on localhost and the tailnet address. Tailnet connections are identified by a Tailscale whois on the real address and must be the owner's login; they then need the fleet key (stations) or an approved token (browsers). Localhost needs a token. Serve identity headers are never trusted.
- Every pane gets a pane-scoped token. Enforced on cross-station calls; advisory on the same station.
- OSC 7501 is read when present, never required.
- The activity strip shows state, current tool and elapsed time, and since 14 Nov 2026 the model and a context gauge (before: no context gauge or cost).
- Fleet, group and station orders live in `~/.config/spandeck/orders.toml`; project and role orders in `.spandeck/orders.toml` in the repo.
- Cross-station in v1: discovery, fleet view, attach, stop, recall search, message relay. An agent's first route to another station needs one approval.
- The v1 enforcement table covers Claude Code and Codex.
- The host's Tailscale; no embedding.
- v1 notifications: one inbox, browser notifications on connected clients, optional ntfy or webhook sink.
- Backpressure: the PTY reader never waits for a client; slow clients are dropped and resynced from a snapshot.
- Command is `spandeck`; the short command is `sd` (chosen by the user on 13 Nov 2026; note it shares a name with a find-and-replace tool some people install).
- Public repo at github.com/michaelbaker-dev/spandeck, Apache-2.0, releases built by CI (the user's decision on 14 Nov 2026; it replaces "local git only until the trademark check"). The trademark check has not been done.
- One size per pane, set by whoever has control; others letterbox.
  - **The rule is the same whichever station serves the deck** (15 Nov 2026, the owner's requirement: "it's all the same view from spandeck ... no matter which machine I'm on"; before, a pane shown through another station did not follow it). The pane's station decides. A browser tab that reaches a pane through another station is a client of its own there (`gw-<serving station>-<the tab's id>`, cut to the letters, digits and `-` and the 64 characters any station takes), where before every tab came as one client, `gw-<station>`, and two windows fought over the size. The serving station also listens to the pane's station's events on that same connection and passes each resize of the pane (size, and which client set it) down the pane's channel, so every deck showing the pane letterboxes or keeps control together, "Take control" works through a gateway, and a phone that watches or fits the pane through one behaves as at the pane's own station. Nothing new is allowed to anyone: the gateway still acts only for the owner's signed-in browser, with the calls it already made (`pane.attach`, `pane.resize`, `events.subscribe`).
  - **With a station on 0.4.0.** As the pane's station: everything above works, since all of it is done by the station serving the deck with calls 0.4.0 already has. As the station serving the deck: nothing changes for decks opened there (its tabs are still one client at the pane's station and are not told of resizes) until it is updated; decks served by updated stations, and at the pane's own station, are right.

## Fleet and device sign-in (0.2, 14 Nov 2026)

- Every station starts as a fleet of one with its own key. `spandeck fleet --join <station>` asks another station for its key; the owner approves there, matching a code shown on both sides. The asking station then replaces its key.
- Calls between stations carry a signature over the exact request, good for two minutes. A task authorization from another station is trusted because the call that carries it is signed.
- A browser on another device asks to sign in, shows a code, and gets a token when the owner approves at a station (`spandeck approve <code>`) or in a signed-in Control Deck. Any station in the fleet accepts the token. It can be revoked.
- Without the key or a token, a device under the owner's login can only ask a station its name and ask to be let in.
- There is no switch that turns this off, in tests or otherwise.

### One fleet: a join is a merge, and a request is answered at any station (15 Nov 2026, the owner's request)

"Should never have multiple fleets, every spandeck should be the same." "Shouldn't all machines get the request? ... you should be able to approve from any machine you're on at the time." What happened: a station that had two fleet-mates asked to join a lone station, took its key and left its mates behind, so there were two fleets.

- **A station that joins brings the stations of its fleet with it**, whichever side asked. After the approval the asking station takes the new key, keeps the old one in `fleet.retired`, and hands the new key to every station of the fleet it was in, in a call signed with the old key (`fleet.rekey`, the call station removal uses, with no station named as removed and the fleet joined named instead). It does so the next time it looks for stations, which it does at once. A station that was off is handed the key when it is next seen at the address it had, for 30 days, exactly as after a removal; after that it joins on the owner's approval. Each station that is handed the key keeps the old one for the same purpose, so a station that only one of them can reach is still told.
- **The key is taken first and the mates are told second.** A station that stops halfway is left with a list of stations still to tell, never with a fleet that moved without it.
- **What joins is whoever holds the old key, not a list of names.** The request does carry the names of the asking station's fleet-mates, so the owner reads "spark2 and 2 other stations (M4-Macbook, LLM-Server) ask to join this fleet" in the notice, under Access and in `spandeck trust`. Those names are text from another machine: cleaned, at most twenty, shown as text, never acted on.
- **Browsers.** A token is made with the fleet's key, so every browser signed in from another device to a station that moves signs in again, and those stations stop listing them. The join dialog says how many stations that is. Browsers signed in to the fleet that was joined are not affected. The station's own Control Deck (`spandeck cc`) is not affected.
- **A request is listed on every station of the fleet.** A station that is asked (by a station to join, or by a browser to sign in) tells the other stations of its fleet, in a signed call only a station can make (`trust.relay`), which requests wait there: the id, the kind, the names, the address it came from, the code, when it lapses. Never the value the asker collects with, and never the key. It sends the whole list again when one is answered, and each time it looks for stations while one waits. Each station lists them in `trust.status` with the station that was asked, raises the same notice, and drops one at the time it lapses.
- **It is answered at any of them.** `trust.approve` and `trust.deny` (the Control Deck, `spandeck approve <code>`, `spandeck deny <code>`) first look for the request at the station they are given to; one that waits at another station is passed to it as the owner's request (`rpc.forward`). The station that was asked decides, and hands over the key or the token as before. Its log says who decided and through which station ("you (via bravo)"); the station the owner used logs that it passed the answer on. The first answer to arrive stands; a later one is told there is nothing to decide, and the request leaves every list.
- **Only the owner answers.** `trust.approve` and `trust.deny` are on no agent's list and no station's, at any station; an agent has no call that reaches another station as the owner. `trust.relay` is a station's signed call, refused from the owner and from an agent: it can only add to or clear what is listed, and what it lists cannot be approved unless the station it names holds such a request.
- **A station on 0.4.0** takes the key when a mate hands it over (its notice words it as a removal, with no station named), and joins a fleet as before; but when it is the one that asks to join, it still leaves its mates behind, and it neither tells its mates of a request nor lists theirs. Update a station before using it to join.
- The ship's log records who asked for a join (`trust.join_asked`), which it did not before.

### The browsers signed in are one list for the fleet (15 Nov 2026, the owner's request)

"It's so important that no matter where I go, it's all the same view from spandeck ... these must stay the same no matter which machine I'm on ... the only thing that would be different would be a machine that didn't join a fleet yet." What was found: each station listed only the browsers approved at it (one station of a fleet listed six, another none), though every station accepts every one of those tokens; and a sign-out was sent once, to the stations that were on, so a station that was off went on accepting the token.

- **One list, the same on every station.** Each station keeps the browsers signed in to the fleet (name, the address it asked from, the station it was approved at, when) and the browsers signed out. Stations exchange both whenever they look for each other, and at once after an approval or a sign-out (`trust.sync`, a station's signed call only: each sends its copy and is sent the other's). A station that was off has both within one look of coming back. Access shows "Browsers signed in to this fleet".
- **A sign-out always wins, and is never dropped while it matters.** The signed-out lists are joined; a browser on the list is refused and listed nowhere. Nothing is ever taken off the signed-out list while the station holds the key that made those tokens, and there is no limit that drops one. The list is kept with the name of that key: once the station holds another key (a station was removed, or the fleet joined another), those tokens are refused for that reason alone and the list starts empty. That is the only time a sign-out is forgotten.
- **Entries say which key made them.** A browser's token is made with the fleet key, so an entry made under a key the station no longer holds is not signed in and is not listed. After a merge the stations that moved list the browsers of the fleet they joined, with its sign-outs (sent with the key); after a removal, only the browser that was given a new token.
- **Entries from before this** do not say which key made them. They stay listed, so that they can still be signed out, with a line saying they may no longer be signed in; one becomes an ordinary entry the first time its token is accepted, and they go when the key next changes.
- **A valid token is always listed.** If a browser shows a token the key made and no station has told this one of it (it was approved at a station on an older version), it is listed from then on as "a browser", first seen at this station, so the owner can sign it out.
- **Going from one station's Control Deck to another's needs no second approval.** Each station's deck is its own web address, and a browser keeps its sign-in per address, so the same phone used to be approved again at each station. A browser's token is already accepted by every station of the fleet. So the station menu has "Open X's own Control Deck", and the deck the browser is signed in to (A) hands X's deck (B) the browser's own token as a message between the two windows:
  1. A opens B's plain address in a new window, in the click itself, and keeps the window. Nothing secret is in the address.
  2. B's page, if it is not signed in and another window opened it, tells that window it is ready. The message holds nothing.
  3. A answers only the window it opened, only when the message came from B's origin, and has the browser deliver the token only to that origin. B's origin is `http://` and the address B gave in an answer signed with the fleet key. A answers once, within two minutes, and sends only a browser's own token, never the station's (`spandeck cc`).
  4. B takes a token only while it waits (30 seconds), only from the window that opened it, asks its own station whether the token is good, and keeps it only then.
- **The token is never in an address** (changed the same day: the first version put it in the address's fragment; a browser records the address it goes to, fragment included, in its history, and may copy that history to the owner's other devices). The only token a deck takes from an address is the station's own, from `spandeck cc` on that machine.
- **What a page the owner opens can and cannot do.** A page that is not the window A opened, or is not at B's origin, is sent nothing, whatever it sends A. A page that opens B's deck itself and sends it a token can only send a token it already holds: B's station refuses any other. With a good one, B shows the fleet in a browser whose owner that sender could already act as, so nothing is gained; this is said here because B does not, and cannot, know who its opener is. A station gains nothing either: B already accepts the token.
- **Where it does not work, the usual request is made instead**, which now shows on every station: a browser that blocks the new window (the deck then says so); a phone's home-screen app or any page with no opening window; a station on an older version. A station serves its deck over plain HTTP at its Tailscale address, and that is the origin used whatever address A's page was opened at (an HTTPS address from `tailscale serve` included). A one-time code made by one station for another to accept was not built: it would be a second way in, to be guarded, for no gain over the token the browser already holds.
- **A station on 0.4.0** in the fleet: it keeps its own list and shows only that; it is told of a sign-out one at a time and only while it is on, as before; a sign-out made at it is taken by the stations that are on and spread by them; a browser approved at it is listed by the others once it is used at one of them. Its deck does not ask the window that opened it, so opening it asks for an approval as before.
- Authority: `device.revoke` is the owner's alone, as before. `trust.sync` is refused from the owner and from an agent.

## Closing every pane, and removing a station (15 Nov 2026, the owner's request)

"I should be able to delete a machine and it should kill all the sessions that are running, or delete all sessions on a machine."

- **Close all panes on a station** (`station.close_all`; the station's menu; `spandeck pane close --all [--station NAME]`). Every pane is ended and taken off the list, as "Kill and remove" does for one. Projects, layouts, history and the archive are not touched. The owner's alone: on no agent's list and no station's; it reaches another station only as the owner's forwarded request, like `station.restart`. The ship's log says who and how many.
- **Ending a pane ends its whole session, not only its process group** (Unix; a change to Kill for every pane). A shell puts a job (`sleep 300 &`) in a group of its own, and that job used to outlive "Kill and remove". Kill now also reaches every process in the session the pane's program started. A program that started a session of its own (`setsid`, a daemon) is still not reached. On Windows the job object already ended the tree.
- **A station is removed by replacing the fleet key, because there is no other honest way.** Every station of a fleet holds the same key, and that key signs station calls and makes browser tokens. A list of removed stations would not stop a machine that still holds a key the others accept. So `fleet.remove` (the station's menu; `spandeck fleet --remove NAME [--stop]`) does this, in order:
  1. The station being removed, if it answers (`station.leave`): closes every pane, takes a new key of its own (a fleet of one), and forgets the other stations, its links to their projects and the browsers signed in to it.
  2. The station the owner is using makes a new fleet key and hands it to every other station that answers (`fleet.rekey`, a station's signed call only, never the owner's or an agent's), then takes it itself.
  3. The removed station is forgotten: the list of known stations, pinned panes and layouts that point at it, its panes in global layouts (a layout left empty goes), project links to its projects, stops and messages waiting for it. Project files in the owner's folders are not changed.
- **What follows, and is said in the dialog before anything is done:**
  - Every browser signed in from another device signs in again, and connections made under the old key are closed at once. The browser that asked for the removal gets its new token in the reply and stays signed in. The token of a station's own Control Deck (`spandeck cc`) does not rest on the key and is unaffected.
  - **A station that was away at that moment keeps the old key.** Until it has the new one it shows as not in the fleet, and the removed station, if it kept the old key, could still act on it. Each station that changed keeps the old key in a private file (`fleet.retired`) for one purpose, never to accept anything (a fleet that joins another one uses the same file the same way): when a station it knew is seen again at the address it had, still showing the old fleet, it is handed the new key in a call signed with the old one. No approval is needed for that, since it is a station the owner already approved. After 30 days it is no longer offered, and that station rejoins with `fleet --join` and an approval.
  - **A station that cannot be reached is removed from the fleet's side.** Nothing is done on it: its panes keep running until someone stops spandeck there. It keeps a key nobody accepts, so it cannot act on the fleet, and it cannot rejoin without a new approval. If spandeck is still running there it is listed again as "not in this fleet", like any machine under the owner's login that never joined.
  - **The vault token is that station's own.** A removed station keeps it and it keeps working there; the owner is told to revoke `spandeck:<station>` at the vault. spandeck does not revoke it: only the vault ends a token.
  - **"Also stop spandeck there and stop it starting at login"** is a tick box, off by default, not offered for a station that cannot be reached. It removes the login service (`systemctl --user disable` and the unit file on Linux; the launchd agent on macOS; the Scheduled Task on Windows) and the daemon then ends by itself. The programs, the state folder and the config folder stay on that machine's disk, and the dialog names them.
  - **Removing the last other station** leaves the station in use as a fleet of one with a new key. **Removing the station in use** is done through another station that answers, which does steps 2 and 3 for the rest; with none in reach the station leaves by itself (it throws its key away), says which stations were not told, and the owner removes it at one of them as well, which is what replaces their key. The only station of a fleet of one cannot be removed from it.
- **What this does not do.** It does not undo what a station did while it was trusted: a machine that was already hostile could have left something behind on the others. Removal is for a machine that is retired, sold, lost or no longer wanted.
- A machine that is not in the fleet and stops answering leaves the list (before, it stayed as "unreachable" until the daemon restarted). Stations of the fleet that are off stay listed, as before.
- Both dialogs name the station and its counts, open on Cancel, and act only on the red button. `fleet.forget` ("Forget this station") stays: it only takes an unreachable station off the list.

## A new pane can continue the last conversation (15 Nov 2026, the owner's request)

"We should have a resume session checkbox when creating a new pane, this way if it's there it would load, if it's not then it just start a new one."

- **`pane.spawn` takes `resume_last`** (the New pane dialog's tick, off until ticked and then remembered: since 15 Nov 2026 as one of the owner's preferences, for every station and browser, before that in the one browser; `spandeck pane new --resume-last`). The agent goes back to the conversation it last used in the pane's folder; with none, a new one starts and the pane says so (`resumed` in the pane and in `pane.created`). A caller's own `resume` id wins. A shell ignores it.
- **The agent's own saved conversations are read, not spandeck's records**, so one started outside spandeck counts. Claude Code: the newest session file in its directory for the folder that holds a message (not an empty file, not a sub-agent's). Codex: the first line of its session files, the 200 most recently started only. OpenCode: its database. Antigravity: none can be found, so a new one always starts. Only read, never changed.
- **Two live panes are never put in one conversation.** One a live pane on the station is in is passed over for the next most recent, or a new one.
- **`pane.last_session`** says what would be continued and when it was last used, before the pane is started. It reads only, and is for whoever may start a pane: on no agent's list, no station's and not the read-only one.

## Themes: how the deck looks (15 Nov 2026, the owner's request)

"I also want to think about custom theme and borders colors etc. … if I create one I like I should be able to set as a theme to reuse." "Ligatures should work, emoji should work, you should be able to customize, or edit these option in a pane or in a layout."

- **A theme skins the whole Control Deck, not only the terminals.** A theme is a set of settings by name: the terminal's colours (background, text, cursor, selection, the 16 colours programs use), the deck's colours (page, bars, buttons, lines, text, the five state colours, the outline of the pane with the keyboard and its width), the terminal's font (family, size, line height, letter spacing, weights, ligatures on or off), the deck's font and size, the cursor's shape and blink, and a contrast floor for terminal text.
- **Three levels, the most specific wins: the deck, a layout, a pane.** Each may name a theme, change single settings, or both; its settings win over its theme, and what it does not say follows the level above. The page's colours and the deck's font follow the deck, or the layout on screen. A pane's own look changes only that pane's terminal and its frame. "Appearance" in the top bar (and in ⌘K), "Appearance…" in a layout's menu and in a pane's menu open the same editor for that level; a layout and a pane can go back to "the deck's".
- **The editor shows the change on the real page as it is made**, in that window only, with a sample terminal; Cancel puts everything back and nothing is saved until Save. It warns, and never blocks, when text has less than 4.5:1 contrast with what is behind it, or two of the state colours (green, amber, red, blue) are close. A look can be saved as a theme under a name, and themes can be duplicated, renamed, deleted, exported to a file and imported from one (spandeck's own format, and other terminals': see Fonts, icons and other terminals' themes).
- **Built-in themes are in the Control Deck's code and cannot be changed or deleted, only duplicated:** Spandeck Dark, Spandeck Light, Solarized Dark and Light, Dracula, Gruvbox Dark, Nord (NOTICE has each palette's licence). **Spandeck Dark is the default and is the deck exactly as it was before themes**, so nothing changes for anyone until they choose. For it the worked-out shades (a pressed button, a chip's border) are the values written out before; for every other look they are mixed from the theme's colours, which is what makes a light theme light everywhere. The outline of the focused pane has width 0 in every built-in theme, because the deck had none.
- **Stored in a document of its own, `look.json`, kept the same on every station** (`look.get`, `look.set`, `look.theme.save`, `look.theme.remove`; `look.push` between stations), by the deck document's rules: only the owner changes it, the station where they did offers it to the others, the newer copy is kept. **It is not part of the deck document, and a layout's look is not written inside the layout**, because a station from before themes (0.3.0) reads the deck document and a project file into the fields it knows and writes only those back: it would drop the themes and, at its next change, push the document without them to the whole fleet. Such a station never holds this document: it is offered only to a station that says it keeps one. The same loss could happen between two later versions, so the document has a format number: a station takes no copy in a format newer than it knows, takes none in a format older than the copy it holds, and does not change a copy newer than it knows.
- **A layout's look and a pane's look are entries in that document**, named `global:<layout>`, `<station>/<project>/<layout>` and `<station>/<pane id>`. So both kinds of layout work the same way, and a pane on a station from before themes can have a look. A pane's look goes when the pane is closed (its station sees to it, and prunes looks of panes it no longer has at its next change; the Control Deck also asks, for a station that does not know how); a layout's goes when the layout is deleted and moves when it is renamed; removing a station forgets its panes' and its projects' layouts' looks.
- **Changing how the deck looks is the owner's.** No agent has a `look.` method, not even the read; another station has only `look.push`, as it has `deck.push`.
- **What is in a theme is data**, since it comes from a file someone imported or from another station. The station checks every value: a colour is `#rgb`, `#rrggbb` or `#rrggbbaa` and nothing else; a number is within its range; a font is a list of at most 8 names of letters, digits, spaces, `-`, `_` and `.`; names and counts are bounded; a setting it does not know is dropped. The Control Deck checks again and applies a look only as the value of a custom property (`style.setProperty`) and as options of the terminal: no style sheet or markup is built from it. A theme's name is put on the page as text.
- **A font is named.** The font setting is a plain list of names. A name is a font installed on the device showing the deck, or one the owner uploaded (next section).
- **Ligatures** are the font's and need nothing added; the switch turns them off with a style on the terminal's rows. **Emoji take two cells** in every terminal (the Unicode 11 widths, from xterm.js's own add-on): before, the terminal gave them one and drew the next character over them. One flaw stays: a character that a variation selector turns into an emoji (❤️) still counts as one cell, which is also what the station's own screen believes.
- **A font change follows the sizing rule.** The client in control of a pane fits it again and tells the station; anyone else only scales what it shows. A resize to the size a client already holds a pane at is not taken as losing control, so two windows that fit a pane alike do not both let go when a font change reaches them at the same moment.
- The deck's own look is also remembered in the browser, so the page (and the sign-in page) opens in it before the station has answered. The colour a phone's home-screen icon was installed with (`manifest.webmanifest`) does not follow the theme.

## Fonts, icons and other terminals' themes (15 Nov 2026, the owner's request)

"Think about how to setup fonts special characters colors etc." "Ligatures should work, emoji should work."

- **A font file can be uploaded** in the Appearance editor (WOFF2, WOFF, TTF, OTF; 5 MB each, 24 files) under a family name, and a theme then names it like any font. It reaches every browser that opens the deck, a phone too. A family can have several files: regular, bold, italic, bold italic, or one variable file for every weight. Removing a file takes it off every station; the editor first says which themes still name it, and they keep the name and fall back to the next font in their list.
- **Which fonts there are is in the look document** (`fonts`: id, name, face, format, size), so the list is the same everywhere and travels by that document's rules. **That is format 2.** A document is written as format 1 until the first font is uploaded, and never goes back: a fleet with a station from before uploaded fonts keeps sharing themes with it until then, and after that the old station keeps the copy it has until it is updated.
- **The files do not travel in the document.** Each is kept in the station's `fonts` folder (beside `look.json`) under an id that is the first 32 hex digits of the SHA-256 of its bytes. A station that takes a document naming a font it does not hold asks the sender for it, and after every look for stations asks any station that keeps fonts (`look.font.fetch`). What arrives is kept only if its bytes give that id and are in the format the document says. A file no longer on the list is deleted.
- **The file is not trusted.** Only the four formats are taken, told by their first four bytes; size and count are bounded; the name follows the rule for every font name and may not be one that means a kind of font (`monospace`). The station never reads into a font: the browser that draws with it checks it, as it does any web font.
- **Served at `/api/font/<id>`, to the owner's signed-in browsers only** (the token in a header; a pane's token is refused), found by looking the id up in the document, never by making a path from what was asked. It goes out with its font type, `nosniff`, and may be kept by the browser for good, since an id always names the same bytes. The Control Deck makes a `FontFace` object from the bytes; a font's name is never written into a style sheet.
- **Rule 7:** `look.font.add` and `look.font.remove` are the owner's. Another station has `look.font.fetch` and nothing else new. No agent has any of them.
- **A terminal measures again when a font arrives late**, because it measures its cells once, with whatever font stood in. Then the sizing rule, as for any font change: the client in control fits the pane and tells the station, anyone else rescales.
- **Prompt icons and powerline signs are drawn on any device** from a bundled font, last in every terminal's font list: Symbols Nerd Font Mono 3.5.1 (1.2 MB), under the name `Spandeck Symbols`. Its `unicode-range` is only where Nerd Fonts' icons live (the private-use ranges U+E000–E00A, E0A0–E0A3, E200–E2A9, E300–E3E3, E5FA–E6BB, E700–E958, EA60–EC84, ED00–F385, F400–F533, F0001–F1AF0, and the power signs U+23FB–23FE and 2B58), so the browser fetches the file only when such a character is on screen, and keeps it (the file's name has the version in it). The font's ♥ (2665), ⚡ (26A1), ☰ (2630) and angle brackets (276C–2771) are left to the device's own fonts, so it never replaces a letter, an emoji or a box-drawing line. A font earlier in the list that has an icon (a Nerd Font, or Fira Code's own powerline signs) wins.
- **Icons are one cell wide**: the font's glyphs are one em square, shown at 60%. **Powerline separators (U+E0B0–E0D7) come from a second file of 7 KB**, made from the same release by `scripts/make-powerline-font.py`: the same glyphs scaled to a cell 0.6 em wide and 1.2 em tall. A browser draws a fallback font's glyph at its own shape, so without this a separator is half the height of its row. A terminal whose font has an unusual cell (JetBrains Mono's is taller) shows a hairline gap; `font.lineHeight` over 1 does too, as in any terminal.
- **Import reads iTerm2 colour files (`.itermcolors`) and Windows Terminal colour schemes**, alone or in a whole `settings.json` (with its comments; the editor asks which scheme when there are several). They say only the terminal's colours. The deck's are worked out from them: the page is the terminal's background, bars, buttons and lines are steps from it toward the text, the five state colours are the palette's own (the normal or the bright of each, whichever reads better, moved toward the text until it has 3:1), and light or dark follows the background. The result is shown in the editor, unsaved, to be changed and then saved as a theme. An iTerm2 file is parsed as XML, which runs and fetches nothing, and only numbers are read from it; every colour goes through the same check as any theme's. iTerm2's colour space is not converted (P3 values are read as sRGB), and its colour for selected text and its bold colour have no setting here.

## Hiding and showing panes in a layout (15 Nov 2026, the owner's request)

"Having panes show and hide options so you can manage them better, for example if you have a layout of 2 over 1, if you hide the bottom one the 2 top ones would resize to take all the space, if you [unhide] it it will go back to its original size."

- **Hide is on a pane's title bar and in its menu; the layout keeps its shape.** The tree of splits and their sizes are not changed. A hidden pane is left out of what is drawn: a split with one side hidden shows the other side at full size, and one with both hidden takes no room. Show puts the pane back where it was, at the sizes the splits had. "Show only this" hides every other pane of the layout in one step; "Show all" is beside the chips and in the layout's menu.
- **Hiding changes only what is seen.** The pane's program is sent nothing and keeps the size it had: the Control Deck lets go of the hidden pane's terminal as it does of any terminal that leaves the screen, and resizes nothing but the panes that grew, by the sizing rule. When the pane is shown its screen and history come from the station's own copy, which is what a reload gives. A selection, or how far back the terminal was scrolled in that window, is not kept.
- **A hidden pane stays in sight as a chip beside the layout's name**: its agent's icon, its name and its state, and it stands out in amber when the pane needs the owner (red on an error), as a pane's own bar does. The chip shows the pane; the button beside it, or a right-click, opens the pane's usual menu. The list on the left marks the pane "hidden". Approvals, the inbox and notifications are untouched by hiding.
- **The last pane showing cannot be hidden** (its Hide is not offered, and is greyed in its menu), so a layout does not go blank by a slip. Every pane can still end up hidden when the one pane showing is taken out of the layout: the layout then says so, with the chips and a "Show all" button.
- **Saved with the layout, as a list beside the tree** (`hidden`: each entry names a pane exactly as its leaf in the tree does), in the project file for a project's layout and in the deck document for a global one, so it is the same after a reload, on every device and on every station. A layout hides at most 16 panes, each entry is a pane and never a split, and its names are checked like a leaf's. An entry that names nothing in the tree means nothing, and goes at the Control Deck's next save. Duplicating or renaming a layout carries it.
- **A station from before this (0.4.0 and earlier) reads such a layout and shows every pane.** It reads a layout into the fields it knows, so `hidden` is passed over and the layout is not refused; when it next writes that project file or the deck document it writes it without the list, and the hidden panes are showing again everywhere. Nothing else is lost: the tree and its sizes are untouched. This is the loss described under Themes, and here it is accepted because all it costs is pressing Hide again; a layout's look stays in `look.json`, where that loss would cost more. Hiding a pane of a project's layout that is kept on such a station does not last: the pane is back at the next redraw.
- **A hidden pane that is gone for good leaves the layout**, so no chip leads nowhere: a pane in no project that was closed, and a project's pane that is neither running nor one the project starts. The Control Deck does this when the layout is opened, and only for a station that is answering. A pane the project starts that is not running now keeps its chip, marked "not running"; a pane whose program ended but is still listed keeps it, marked "ended".
- **A pane added to a layout goes beside one that is showing**, so it is seen at once. In Arrange only the panes showing are moved about; the hidden ones keep their places in the tree and their chips.
- **On a phone**, where a layout is one pane at a time, a hidden pane is left out of the order that Previous, Next and a swipe go through, and is drawn dashed and dim in the map (not dimmed when it needs the owner). Tapping it there looks at it without changing the layout; "Hide" and "Show" beside the pane's name change it, for every device.
- Hiding is a change to a layout, so it is the owner's by the methods a layout is already saved with (`project.layout.save`, `deck.layout.save`): no new method, and nothing for an agent.

## The same view from every station (15 Nov 2026, the owner's requirement)

"It's so important that no matter where I go, it's all the same view from spandeck. I hop around across multiple machines and now I see my phone is different from my m5 and that different from rtx6000... these must stay the same no matter which machine I'm on ... I guess the only thing that would be different would be a machine that didn't join a fleet yet."

**The rule: a Control Deck shows the same things whichever station of the fleet serves it.** Whatever the deck shows is one of three kinds, and nothing may be a fourth: kept the same on every station (a synced document, or the roster); fetched from the station that holds it, from every station that answers, with a station that does not answer named as not counted; or the device's own. What is only the serving station's is said to be, by name. A machine that has not joined the fleet is the one exception the owner named.

- **The inbox is the fleet's** (before: the serving station's notices, unread count, "Mark all read" and "Messages to you" only). Each station keeps the notices it raised and the messages sent to "you" there; the deck asks every station that answers, and each entry says which station it is from. A notice is marked read at the station that holds it; "Mark all read" goes to every station that answers. A station that does not answer is named under "Not counted", as the Usage view does, and what it last said stays on screen.
- **A notice raised at any station reaches a deck served by any other at once.** The station that raises one tells the other stations (`notify.relay`, a station's signed call only: refused from the owner and from an agent), and each passes it to the decks connected to it as the same `notify.new` event, with the station it is from. Nothing is stored at the stations told. What is passed is text from another machine: bounded, control characters dropped, a link kept only if it is a place in the deck, shown as text. That an inbox was read is passed the same way. The deck also announces a notice it first sees in a station's list, so one from a station that does not tell the others (0.4.0) is announced at the deck's next look (2.5 s, while the page is in front; not while it is in the background).
- **The synced documents: the newer copy wins, and "newer" is made honest** (`crates/core/src/sync.rs`). The deck document (global layouts, pins), the look document, the agent setup and the owner's preferences are each one whole document, a copy on every station, the newer copy kept. What was wrong: a station only ever offered its copy, so one that had just come back held a stale copy until another station looked (up to 10 s); a change made to it in that time, by the owner or by the station itself when a pane closed, was stamped with the present time and replaced what had been changed while it was away, on every station. Now:
  - **A station takes a newer copy as well as offering its own** (`sync.pull`, a station's signed call only, since the agent setup can hold credentials; a 0.4.0 station has no such call and is read with the call a deck would make of it, `rpc.forward` of `deck.get`, `look.get`, `setup.get`). It does so at every look at the fleet, so at start, and before its own copy is offered.
  - **Before the owner's change to one of these documents is taken, a station that has not looked at the fleet in the last 12 seconds looks first** (it has just started, or the machine slept), and a change waits for a look that is under way. The change is then made to the newest copy in reach.
  - **A change nobody asked for never makes a copy newer.** A pane that is closed takes its own look out of its station's copy only: the stamp stays and the copy is not offered. The other stations drop the entry at the owner's next change to the looks made at that station, or when the deck that closed the pane asks (it does). Until then they hold a look for a pane that is gone, which shows nowhere.
  - **A stamp is later than the clock, than the copy it replaces and than every stamp the station has seen in the fleet**, so a station whose clock is slow does not lose.
  - **Each copy says which stations' changes it holds** (`changes`: per station, the stamp of the last change made there). A station whose copy is replaced by one that lacks a change it held raises a notice naming the station whose change went ("A change to the global layouts and pins made at alpha was not kept"); every station that held it says the same words and the inbox shows them once. A copy with no such record is taken to hold everything up to its own stamp.
  - **The agent setup is saved whole by an editor**, so its save says which copy the editor opened; if the setup was changed since, the save is refused ("not saved: … open it again"). A station that answers a save with "I kept mine" is reported as not saved, never as saved, and its newer copy is taken at once.
  - **What window is left.** It is still last-writer-wins on a whole document; there is no per-item merge and no record of deletions. A change is lost when the same document is changed at two stations and neither had the other's change: (1) both changed while they could not reach each other (one was off or off the network and its deck was used locally); (2) a station was out of reach for less than the 12 seconds and is changed within 10 seconds of coming back; (3) two changes within the time a copy takes to travel (normally well under a second; up to 5 s per station that is listed as on but does not answer, since copies are offered one station after another). In each case the later change wins whole, the other is lost, and the owner is told which station's change went, unless that copy passed through a 0.4.0 station (which drops the record) or the loss is of something only removed. Per-item merge with tombstones would close this; it was judged too much for what is left, and is the next step if the notice is ever seen in real use.
  - **A 0.4.0 station** reads these documents as before: the stamp and every field it knows are unchanged, `changes` is a field it passes over. It still only offers its copy and stamps with its own clock, so the fault remains at that station until it is updated: a change made at a 0.4.0 station that has just come back can still replace newer work, and because it writes the document without `changes`, nothing is said.
- **A global layout names the same panes on every station.** Each of its leaves names its station (the deck has always saved them so). A leaf with no station, saved through the API or kept from before, used to mean "the station serving this deck", so one layout showed different panes on each station, and a hidden one could be dropped by a deck that looked for it on the wrong station. It now means no station until it is given one, and it is given one once, by the first deck that can tell, which saves the layout: a pane in no project is named by its id, which is its own, so it gets the station it is found on; a named pane gets the one station that has such a pane only when every station of the fleet answers, because a project of the same name may be on a station that is away. Until then the leaf says it was saved without its station, offers the stations that have such a pane, and is never guessed or dropped. Nothing is knowable about where such a leaf was saved (the document does not say), which is why it is found and not assumed. In a fleet of more than one station a pane of a global layout always says "on <station>", not only when it is on another station than the serving one. A project's layout is unchanged: it is kept on one station and a leaf with no station is on that one. A 0.4.0 station reads the saved leaf like any leaf that names its station; its own deck still reads a stationless one as the serving station.
- **The owner at a deck is at a keyboard for every station.** A push (ntfy, webhook) is held back while the owner is at a full client; that used to be known only to the station serving the deck, so the others pushed to the phone meanwhile. The serving station now passes the deck's `presence.touch` (sent at most every 20 s while the owner types or clicks) to every station that answers, as the owner's call through `rpc.forward`, which a station of any version takes; one passed on is not passed on again. Each station still decides its own pushes, by its own `at_keyboard_secs`. What stays the serving station's: a call that changes something also counts as presence there, from a phone too, and that is not passed on.
- **The roster of the fleet's members is the same on every station.** A station used to list the members it had itself seen online, so a station that had never seen C did not list C while C was off, and "Forget this station" took it off one station's list. Each station now says in `station.info` which members it knows (name, address, when it last saw each, and the three things kept to wake or describe one) and which the owner said to forget and when; at every look a station makes its roster the union of its own and what each station of its fleet says, taking a member from whoever saw it last. **Forget is fleet-wide:** the station where the owner forgot one says so, the others read it at their next look (10 s at most; a station that is off, when it is back) and drop it too; a station seen after it was forgotten is a member again everywhere. Removing a station from the fleet marks it forgotten the same way, so a station that was off during the removal does not bring it back. The time of forgetting is set later than any time the station was last seen, so clocks that disagree do not undo it; a forgotten station is remembered as such for 90 days.
  - What a station says about the roster is data. Names and sizes are checked, only those three things are kept, and **an address is taken only if it is one this station would look at by itself**: one in its own config, or a device under the owner's Tailscale login, on spandeck's port. No station can make another send a call, or later a key, to an address of its choosing.
  - **What stays different:** up to one look (10 s) between a change and every station showing it. A 0.4.0 station neither tells nor reads a roster: it lists what it saw itself, as before, and Forget there is its own; the other stations still learn the members it is silent about from each other.
- **The owner's preferences follow the owner** (`crates/core/src/prefs.rs`). Each station is its own web address, so what a browser kept for one station it did not have for the next: which parts of the list on the left are folded, and the "Continue the last conversation" tick. They are now in one document for the fleet, `prefs.json` (`prefs.get`; `prefs.set`, the owner's alone; `prefs.push`, a station's only; no agent has any), synced by the rules above. **A document of its own, not a section of the deck or look document:** a 0.4.0 station reads the deck document into the fields it knows and writes only those back, so a preference kept there would be dropped fleet-wide at that station's next change; the look document would need a new format number, which would stop a 0.4.0 station taking themes at all. A new document costs an old station nothing: it is offered only to a station that says it keeps one, and it has a format number of its own. A preference is one of a fixed list, each value checked and bounded; one this version does not know is dropped. What a browser had chosen before becomes the fleet's once, if the fleet has none; the browser's copy remains only as what the page opens with before the station answers, and as what is used when the deck is served by a 0.4.0 station.
- **What is the device's own, and stays in the browser:** the sign-in token and the client's name; the look the page opens in before the station answers; which pane of a layout a phone is showing; a draft in a message box; fit-to-screen; the user name last typed in Add a machine; whether browser notifications are allowed. None of these is something the owner chose for the deck as a whole.
- **The deck says when the stations do not all run the same version.** The Control Deck is each station's own copy of it, so a station on an older spandeck serves an older deck (a page reloads itself only when the station that serves it changes), and everything in this section holds only between stations that know how. When a station of the fleet runs an older version than the newest one in it, a bar that blocks nothing says which, on every station's deck: when it is the serving station, that this deck is the older one and what is seen may differ; otherwise which stations are behind. It offers the update each station already has in its menu (`station.update`, for the stations that answer; one that is off or needs an update before it can be controlled is updated at that machine), and "Not now", which holds in that page until the versions change. The versions of stations that are off are the ones they last had.
- **Stops are shown from every station, sent to the fleet's members, and timed by the station that is stopped.** No Guarantee under "Stop, pause and offline" is changed; three faults in how they were met are.
  - A stop is kept by the station it was issued at. A deck showed only the serving station's; it now asks every station that answers (`stop.list`), so a stop is on screen wherever the deck is opened, with the station it was issued at. Stops issued at a station that does not answer are said to be not shown.
  - "Stop every agent in the fleet" went to every machine on the list, including one that has not joined; that one cannot take the fleet's calls, so its row said "station unreachable" for ever, which is the state the Guarantees keep for a station whose stop will be delivered. A fleet stop now goes to members only, a stop named for a machine that is not a member is refused with that reason, and a waiting row for a station that is no longer a member is dropped and logged (`stop.dropped`). A member on a version this station cannot otherwise control is still sent the stop, and is tried again like any other.
  - "Applies only to the work that was running when it was issued" compared the issuing station's clock with the stopped station's own times, so two clocks a few seconds apart could miss a turn that was running, or stop one started after. The issuing station now says how long ago the stop was issued (`age_ms`: a length of time, counted on one clock) and the stopped station counts back from its own now. What is left is the time the call takes to arrive, by which the cut-off is late: a turn started in those milliseconds is stopped too. The same for how old a stop is on screen: the station says, and the browser's clock is not compared with it.
  - **What stays the issuing station's:** delivering a waiting stop. If that station is off when the stopped one comes back, the stop waits until both are on; the row says so. A 0.4.0 station stopped by a newer one uses the issuing clock's time as before; a newer one stopped by a 0.4.0 station does too.
- **A stop is sent to every member at once, and aimed at the moment it was pressed** (15 Nov 2026; step 1 of the performance and continuity plan, `crates/core/src/stops.rs`). No Guarantee under "Stop, pause and offline" is changed. Measured before this: a station that answered waited 5.01 s behind one that did not, and a request written before a link was cut was applied 14 s late and stopped a turn started 6 s after the stop.
  - **At once.** This station's agents, the rows, and every other station's stop are started together; each station has its own five seconds, and none waits for another or for the database.
  - **The cut-off is the moment the stop was accepted, converted at each send to the stopped station's clock** (`cutoff_ms`, beside `age_ms`). The row keeps only that moment, on the issuing station's clock, as before. The difference between the two clocks comes from the standing readings (`station.hello`, taken at every look) only when the newest is under 15 seconds old, the one before it agrees to within 250 ms, and its age by the station's own clock matches its age by the clock that only runs forward; otherwise, and always when an earlier send of that stop failed (the station was away, or the first request may still be on its way), the station is asked its clock first and the stop follows on the same connection. The stopped station stops a pane whose work began at or before the cut-off, by its own clock, whenever the stop arrives.
  - **How right:** to half the round trip the clock was read in, plus any step either clock made after the reading (at most 15 seconds before the send; a step between two readings, or of the issuing station's own clock by more than two seconds, forces a new reading). If the issuing station's clock is set while a stop waits for a station that is away, the cut-off moves by that much: the row holds a time on that clock. The stopped station never takes a cut-off to be later than counting back by `age_ms` gives, so a wrong reading cannot stop more late-started work than the old rule did.
  - **When the work began** is the later of the last prompt a hook reported and the pane last going from idle to busy (kept in the pane's record from this version on). So an agent with no prompt hook is judged by when it became busy, and work that has changed state since (working, then asking the owner) is still the same work; counting back by age missed that. Where neither is known (a pane busy since before this version, with no prompt hook), the work is stopped. A pane made after the cut-off is never stopped.
  - **Once.** The ids of applied stops are kept in memory in front of the database's record of them, so a second arrival is not a second stop when the database cannot be written. **States only move forward:** requested, unreachable, confirmed; a failure that comes in after a station confirmed changes nothing.
  - **The row and the stop at the same time.** A stop is applied and sent whether or not its row can be written. The database is given one second; a row not written by then is held in memory, written by the stops task when it can be, and shown meanwhile as "waiting for golf · not yet saved on spark2" (`saved: false`): if the issuing station's daemon ends before it is written, that stop is not delivered. A row that is written survives a restart and an upgrade, as before; one that is not yet written is now carried through an upgrade too, and written by the image that takes over (see Nothing waits for the database).
  - **Waiting stops are delivered by a task of their own**, every 2 seconds and at once when the list of stations changes, every station at the same time; no longer inside the twice-a-second work.
  - **A station one version behind** does not announce `stop_cutoff` (`caps`, in `station.hello` and `station.info`): it is sent `age_ms` and nothing is asked of it first, exactly as before; a stop it issues carries no cut-off and is applied by its age, as before. `[flags] stop_cutoff = false` makes a station behave so in both directions.
- **Smaller things made the same.** A station's "working" and "need you" counts on its tile and in the list are counted from the pane list the deck has just fetched from it, as the top bar's count is (before: from what the serving station last heard, up to 10 s old, so two decks disagreed). An uploaded font the serving station does not hold yet is fetched through any station that has it (`look.font.fetch`), so a theme's font does not show on one station's deck and not another's. An action in ⌘K that acts on one station names it ("New pane on spark2…").
- **Fetched from the station that holds it, from every station that answers** (and so the same on every deck, with a station that does not answer named or shown as unreachable): panes, projects and their layouts, tasks, recent messages, approvals, the inbox and messages to the owner, stops, usage, vault state, agent versions.
- **Still the serving station's own, and said to be:** Add a machine, Wake and Start act from the station being used (by design: a password or an SSH connection never passes from one station to another), and their dialogs name it; which browsers are signed in is listed per station today (being made one list for the fleet separately); standing orders above the project level are each station's `orders.toml`; the Agent setup panel reads agent versions from the serving station's last look.
- **What can still differ between two decks, in one place:** (1) for up to one look, 10 s: the roster, a forgotten station, and a synced document a station could not be given at once; (2) for up to 2.5 s, the deck's own refresh: everything fetched; (3) a station on 0.4.0 keeps the old behaviour for whatever it serves or stamps, until updated, and the deck says which stations those are; (4) the three cases under "What window is left" where one of two changes to the same document is lost, which the owner is told of.
- **One thing every station raised is one entry.** A request to be let in is raised at each station; the deck shows notices with the same kind, title and text and no pane as one, naming the stations, announces it once, and marks every copy read.

## The Performance page and Tailscale key expiry (15 Nov 2026, the owner's request)

"Control deck should have a performance page that you can see across the fleet." "A Tailscale token expiring and lost access to the machine, how can we expose this in control deck, either information, or renew or disable token expiration." This is step 0 of the performance and continuity plan: it measures and shows. It changes nothing about how Stop, Pause, approvals, input, messages or hooks behave.

- **Each station counts for itself, always, in memory** (`crates/core/src/perf.rs`). How long requests took, by the way they came in (a Control Deck, the local socket that agents and the command line use, another station, plain HTTP); how long a deck's request stood behind the ones before it on its connection; the five slowest of the last five minutes, by method name and never with what they carried; how late the twice-a-second work ran and how long it took; how long a look at the fleet took; clients repainted because they fell behind a pane; a message from sent here to stored there, and from stored here to its agent being told; and per other station: the round trip of the unsigned `station.hello`, every call's time, calls that failed and how, the difference between the two clocks, and when the link last changed. Figures are of the last five minutes (ten-second windows). Nothing is written to disk, and nothing a station decides reads a counter. Restarts and their reasons come from the ship's log, which now also records a start (`station.started`: the first, after a stop, or after ending without one) and a stop on request (`station.stopped`).
- **`perf.get` is the owner's and a station's, never an agent's** (rule 7), and not on the read-only list: call timings show when other projects are busy, and it carries the Tailscale list below.
- **The page is the same from any station** ("Performance" in the top bar, the station menu, ⌘K, and a button on the phone's list; `#/perf`). Every number is asked of the station that holds it, from every station that answers. One that does not answer is "not answering", one on a version from before this is "not reported (its version)", and neither is ever shown as zero. Each station has one sentence, the first that applies: not answering; clock differs; Tailscale key expired or within 14 days, or Tailscale signed out or not running; restarted three times in an hour; its periodic work ran 250 ms late; a link's round trip over 150 ms at the 95th percentile; messages waiting over 30 seconds; else "fine". Stations send numbers; the page writes the sentence. Then a table of stations, a grid of links (each station's own view of each other), the slowest requests, restarts, Tailscale keys, and what this browser measured itself (key to echo for panes it controls, reconnects, how long its refresh takes), which is the device's own and is sent nowhere. The button carries a dot when a sentence is not "fine"; for that the page's question is asked once a minute while the page is closed, every four seconds while it is open.
- **First version.** No charts and no history beyond five minutes. Direct or relayed is what the local Tailscale client says of a link in use, and "path not known" otherwise. The switches of later steps are not there because those things are not built. (The database's figures were added with its writer, the same day: see Nothing waits for the database.)
- **A clock that differs is said to be that.** Two stations whose clocks were more than two minutes apart listed each other as unreachable, and a call answered "not in this fleet". The rule stands: such a call is refused. But `station.hello`, which needs no signature, now says the station's clock, so each works out the difference (the reading from the shortest of the last eight round trips, not used after a minute); a refusal of a signature that was made with the fleet's key says "clock" (to no other caller: any other signature is refused as before); and the station is listed as unreachable with the reason, on its tile, on the phone, on the Performance page and in `spandeck doctor`, where a difference over 30 seconds is already mentioned. Wake and Start are not offered for it: the machine is on. A station that was never seen before and is refused for its clock is now listed, where before it did not appear at all.
- **Tailscale key expiry, step 1: information.** With discovery on, a station reads `KeyExpiry` and `Expired` from the `tailscale status --json` output it already fetches at every look (`crates/core/src/tailnet.rs`); with `discovery = false` it asks Tailscale nothing and says "not read here".
  - **Whose keys.** Every station of the fleet, and the owner's other devices (same login, not tagged) that expire within 30 days or did in the last 30. A station's key is looked up in the local client's list by the Tailscale id that station gave (`tailnet.report`, asked when a station is first seen and then once a minute), so it is still shown, and still current, while the station is off; where the local client does not list it, what the station last said of itself is used, and that is remembered across a restart.
  - **Where.** A chip on a station's tile and in the phone's list from 30 days (amber) and from 7 days or expired (red); a line in its menu; the Performance page; `spandeck doctor` on the machine itself; and in the top bar, "This device's Tailscale key expires in N days", when the device the browser is on (the station tells the page which Tailscale device its connection comes from) is within 14 days. Each opens the steps: before expiry, "Disable key expiry" in Tailscale's admin console or sign in again at the machine; after expiry, "Temporarily extend key" in the admin console (30 minutes), then "Disable key expiry" or sign in at the machine. A station whose key has expired says so in place of "unreachable", and Wake and Start are not offered.
  - **Notices** at 14, 7, 3 and 1 day and at expiry, for each station and for each device that opened a Control Deck at any station in the last 30 days (a station remembers the Tailscale address a deck connects from, and says so to its fleet in `tailnet.report`). Every station raises it in its own inbox in the same words, which name no "this station" and give the date in UTC, so the deck shows one entry (as for a request to be let in). What was said is kept in the station's key-value table, so a restart does not repeat it; a station that was off says the level it finds when it is back, once. **One station pushes:** the one whose name sorts first among the stations it sees online that can tell, itself included; the others mark theirs "left to another station". Each decides alone, so a fleet split in two may push twice. The push follows the notification settings every other notice follows: sent only where an ntfy or webhook sink is set, and held back while the owner is at a keyboard. With no sink set, which is the default, nothing is pushed.
  - **Who may read it.** The list of the owner's devices, their addresses and expiry dates is in `perf.get`, `tailnet.view` and `tailnet.report` only: the owner's and a station's signed call. None of it is in `station.info` or `fleet.view`, which an agent or a read-only caller can read; `station.info` says only that the station answers these calls.
  - **Not built:** starting a renewal from the deck, a "never expire" button, the sign-in address on a machine's own deck, and the machine's last address on its own network in the steps.
- **A station on 0.4.2 in the fleet.** It has no `perf.get`: its row says "not reported (0.4.2)". Its `station.hello` says no clock, so a difference with it is not known and it reads as unreachable, as before. It says nothing of its own key and raises no notice; the other stations still show its key when their own Tailscale client lists the device at its address, and still warn. It is never the one that pushes. Its own deck has no Performance page.
- **Cost.** Recording is three atomic operations (measured: 1,000,000 samples in 10 ms with the time given and 50 ms reading the clock each time, so about 50 ns a sample, on the machine it was built on). A Control Deck's requests now pass through a queue of 64 between the socket and the loop that takes them, one at a time and in order as before, so that each can be stamped on arrival.

## Nothing waits for the database (15 Nov 2026, the owner's request)

"Low latency, high performance." This is the database part of step 1 of the performance and continuity plan (`crates/core/src/db.rs`). What was measured on 0.4.2 with the station's database held locked by another program for 12 seconds: one keystroke took 10 s, a hook 10.3 s, starting a pane 10 s, and that pane's record was never written, so the pane would not have come back after a crash. Measured after, same lock: a keystroke and its echo under 50 ms, a hook 7 ms, a pane started and answered for after the one second the database is given (told "not saved"), and its record written when the lock went. No Guarantee is changed, and no migration is added.

- **One thread writes, and nothing typed, stopped or answered waits for it.** The station's database has a connection that writes and one that only reads, so a read never stands behind a write that waits for a lock. What is written falls in four kinds:
  - **The ship's log is best effort** (and so are the notes a hook captures for project memory). An entry is handed to the writer and never waited for. 10,000 may wait; when more arrive the oldest are dropped and counted. `log.query` shows what still waits over what is written.
  - **Changes of state are kept until they are written**: a pane's record (its pause and holds included), a pane closed, a stop this station issued and the record that a stop was applied here, an approval asked for, answered, expired or cancelled, a notice, how far a conversation was read, when the station was last running, what it knows of the fleet's Tailscale keys and roster. Each is made in memory first, held as the newest state of that thing, written ahead of the ship's log in the order the changes were made, and tried again every second until the database has it. An answer to an approval is never replaced by an expiry that came after it.
  - **What the owner is answered about says whether it is saved.** Pause, an answer to an approval, a stop, and a pane started or closed take hold at once; their answer then waits for the database for at most one second and carries `saved: true` or `saved: false`. In ordinary running that is a millisecond or two and the record is written before the answer, as it always was. `saved: false` means held in memory and still being written: if the station's daemon ends before it is written, a pause is not kept (the pane comes back not paused), a pane just started is not started again and one just closed is listed again, who answered an approval is not recorded (the agent already has its answer), and a stop still waiting for an unreachable station is not delivered. Nothing is ever reported as saved before it is.
  - **A message is stored before its sender is answered, as before** (`msg.send`, `relay.accept`): the caller's own transaction, and a failure is told to the caller. It now asks for the write lock at its start, so it waits up to five seconds for another program's lock where it used to be refused in a moment; while it waits, the thread it runs on is given up to other work.
- **Reads never go backwards.** What is not written yet is laid over what the database gives: `approval.list` (and a pane's conversation view), `stop.list`, `notify.list`, `log.query`, and the values the station reads back itself. Panes were always listed from memory.
- **When the database takes nothing.** After 30 seconds of failed writes, or with 1,024 changes of state waiting, the station says it cannot write its database: one notice ("alpha cannot write its database", raised once, and listed although it cannot itself be written yet), an entry in the ship's log when it starts and when it ends (`station.database`), and the Performance page. From then until a write succeeds, what is only worth doing if it is stored is refused at once with "this station cannot write its database; nothing was changed": a new pane, a project added, opened, closed, removed or linked, a message sent, replied to, acknowledged or accepted from another station, a task delegated, given a result, cancelled or continued, a sign-off, a review started or cancelled, a note. **Stop, Pause, Kill, typing, pasting, answers to approvals, hooks, the switches and an upgrade are never refused for this.** At most 4,096 changes of state are held; past that a change to something not already waiting is dropped and counted, so memory is bounded on a disk that stays full.
- **Before the image is replaced, and before a clean stop, the writer is given two seconds.** At an upgrade or a restart in place it is then stopped, and what it could not write (pane records, stops, answers, notices, log entries) travels to the next image in the same private file as the terminals, and is written by it before anything it changes itself. So "a stop request for an unreachable station is delivered on reconnect" holds for a stop that was not yet saved when the station was upgraded. At a clean stop there is no next image: what the database did not take in two seconds is lost, and the daemon's own log says how much.
- **What a crash at the worst moment loses** (the daemon is killed, or the machine goes down, between a change and its write; ordinarily a few milliseconds, longer only while the database is locked or the disk full): log entries not yet written; a pane record's last change (a pane started in that moment is not started again; a pause is not kept); the record of who answered an approval (the row stays "pending" and is expired at the next start); a stop row (a stop already delivered stays delivered, one waiting for an unreachable station is not delivered: the Control Deck said "not yet saved"); that a stop was applied here (the issuing station's retry is then applied again, to work that began at or before the stop's cut-off only); a notice; a read mark (the conversation shows as unread again). Never a message: it was either stored and its sender told so, or refused and its sender told so.
- **The Performance page** has a "Database" figure per station ("0 waiting, 0 dropped"; its title gives the oldest unwritten change, log entries waiting and dropped, tries that failed, writes over 50 ms), and the station's sentence is "cannot write its database" when that is so. `perf.get` carries the figures as `database`.
- **The switch `db_writer`** (`[flags] db_writer = false`, or `station.flags`). Off: the ship's log, captured notes and changes of state are written by the caller that made them, waiting up to five seconds for a lock, as before this. What the switch does not take back: a change that cannot be written is still kept and tried again (before, it was dropped); the two connections; reads laying unwritten changes over the database; `saved` in the answers; the refusal and the notice; the hand-over at an upgrade; a message's transaction taking the write lock at its start.
- **What still waits for the database, and why.** Whatever must be stored before it is answered or acted on writes on its caller's thread, up to five seconds under another program's lock: messages (sending, accepting, marking one announced to its agent, so a hook that has mail to announce waits), tasks (a hook of a pane that is on a task writes the task's state), projects, recipes, sign-offs, posted notes, marking notices read, and the lists the trust rules rest on (browsers signed in and signed out, the fleet's roster when the owner forgets a station). The session archive is a database of its own and is not changed by this.
- **Mixed versions.** Nothing here crosses stations: no new call, nothing new in `caps`, no change to a call's meaning. A station on 0.4.3 in the fleet behaves as before. `saved` is a new field in the answers of `pane.spawn`, `pane.close`, `pane.pause` and `approval.answer` and in rows of `approval.list`; a deck or a command from before passes over it. An upgrade from 0.4.3 hands over nothing unwritten (it wrote everything itself); going back to 0.4.3 after a failed health check loses what this version had not written, since 0.4.3 does not read it.

## After a restart (15 Nov 2026, the owner's request)

"Make sure the plan … covers every situation like reboot, recovery … seamless to the user." "How to bring a session back on line in case of a failure." This is the restart part of step 1 of the performance and continuity plan. What was measured on 0.4.2 after `kill -9` of the daemon: agents were started again in their conversations and nobody was told; 49 of 50 restored agents' first hook failed ("spandeckd is not running"); an approval that was waiting stayed "pending" for ever; a task kept the state it had; a job that ignored hang-up ran on in no pane; a shell vanished from the list; requests to join or sign in were lost at an upgrade; the web server never tried an address again. No Guarantee is changed. "Processes do not survive a daemon crash; agents resume by session id" stands.

- **The order of start-up is not changed: panes are restored, then the station answers**, so no deck ever sees a station with its panes missing (a deck that did would take hidden panes out of saved layouts). The first hook of a restored agent used to arrive before the socket was served. So an agent's hook (`spandeck hook`) that finds no daemon to connect to (nothing listening, or no socket yet) tries again after 25, 50, 100, 200, 400 and 800 ms and then every 500 ms, for 3 seconds in all, and then gives up silently, as before. Only the connection is tried again, never a request that was sent. An agent's tools (`spandeck mcp`) do not wait yet.
- **A waiting approval whose agent went with the daemon is expired** at the start, so it leaves every list (`approval.resolved`, `expired`). One whose pane was kept alive (an upgrade, a restart in place, the pane host) is left waiting, for the step that lets a hook find its own approval again; until that is built, the hook that asked was cut off there as well and the agent asks in its own terminal, so the first answer the owner gives such an approval finds nobody waiting: it is told so, as before, and the approval is then expired and leaves the list instead of staying for ever.
- **A task whose agent's program went with the daemon is failed with its resume information** (the Workspaces Guarantee, which until now was met only when an agent ended while the daemon ran): the session, the pane, the worktree, the branch, the reason "spandeck restarted" and when. This holds whether the pane is started again or not.
- **"Continue this task"** (`task.continue`; a button beside a failed task that kept resume information, in a project's Tasks) sets the task back to running and types one line into its pane: "spandeck: your task was interrupted by a restart at 14:02 UTC. Check your last step, then continue." Refused when the pane is not running (bring it back first), is no longer on that task, or is paused: Pause means no new work. The owner's alone: on no agent's list, no station's and not the read-only one; it reaches another station only as the owner's forwarded request.
- **What a pane's program left running is ended only for a pane that is started again.** A job that ignored the hang-up used to run on beside the agent that replaced it, in no pane. The time a pane's program was started is now kept beside its pid; at a start, every process still in that program's session is ended before the pane is started again. Nothing is touched unless all of this agrees: the record has the pid and the start time; if a process has that pid now, it leads that session and started when the record says (else the number was given to something else, and nothing is done); and each process ended started no earlier than the pane's program and no later than 30 seconds after the station last wrote that it was running (it writes that every 10 seconds), so that a session which was given the same number while the station was down is not taken for the pane's. A pane from before this has no start time and its leftovers are not touched until it has been started once by this version (a pane kept through the upgrade to this version is given its start time then). On Windows nothing is left: the job object ends the tree.
- **What a pane that is not started again left running is not touched** (the owner may have detached it on purpose). It is named in the notice and in the log, ten at most, as the program's name and pid.
- **A pane that is not started again stays listed for 7 days as ended**, with the reason: "ended when spandeck restarted at 14:02". Its terminal says so, with **Bring back** (`pane.restart`, as for any ended pane: an agent goes back to its conversation if it has one, a shell is a new shell). Closing it takes it off the list for good. Before, a shell, and an agent with no conversation to go back to, were simply gone. An open terminal for a pane that is no longer on its station says so once, with a Retry button, where it used to ask again every 3 seconds for ever.
- **One notice and one entry in the ship's log per recovery.** `station.recovered` says why (`crash`: the station ended without being stopped; `stop`: it was stopped and started; `upgrade`: terminals were lost in a handoff), how long it was away, and how many sessions were kept, started again, ended or held back, tasks failed, approvals expired, and the leftovers. The notice: "spark2 restarted at 14:02 UTC (away 12 s)" · "4 sessions were started again, 1 shell ended, 1 task failed. They wait for you." Times in it are UTC, since it is written by the station. **At most one such notice in 10 minutes:** a recovery inside 10 minutes of the notice that stands rewrites it ("spark2 restarted 3 times since 14:02 UTC"), shows it as unread again and does not push it a second time. No notice when no session was open. The Performance page shows the last recovery under Restarts.
- **"They wait for you" is true of the agents' own turns and of their mail.** A session that is started again sits at its prompt, nothing is typed into it, and it takes no mail until the owner releases it (the same day: see A stopped agent stays stopped). The notice says so and how to release them, unless that waiting is switched off on the station (`holds.restored = false`), when it says only "They wait for you.".
- **Three restarts in ten minutes: sessions are listed and not started.** The station counts its starts that followed no clean stop (kept in its key-value table; a stop on request resets the count). At the third within 10 minutes it starts no agent: each is listed as "not started again: spandeck restarted 3 times in 10 minutes", with Bring back. Their records stay open, so the next start that is not held back (after a clean stop, or once fewer than three lie within 10 minutes) starts them. Panes kept alive by the pane host are not affected.
- **A request to join or sign in is still waiting after an upgrade or a restart in place.** The daemon that takes over is handed the waiting requests with everything else. They hold the hash of what the asker collects with, never the key, as before; one already answered and not yet collected is not carried, and neither is this station's own request to join another fleet.
- **The web server keeps trying, and follows the Tailscale address.** An address that could not be bound at start is tried again every 10 seconds. With no `web_bind`, at each look at the fleet the station compares its own Tailscale addresses with those it serves: a new one is bound and added to the Host values it answers to (within one look, 10 seconds), one that is gone is no longer served and its Host no longer answered. So a station that started before Tailscale was up is served there without a restart. With `web_bind` set the addresses are the owner's and only the retry applies; with `discovery = false` Tailscale is not asked and nothing is followed.
- **Switches.** `[flags]` in a station's `config.toml` (true or false, a whole number, or a short text; `holds.restored = false`) is read at start, and the owner can set one while the station runs (`station.flags`; kept in the station's state, never written to the config file; the owner's value wins, and taking it back restores the config's). The owner's alone, like `task.continue`. `perf.get` shows what is in force. (When this was written nothing read a flag; `stop_cutoff`, `db_writer`, `holds`, `holds.stopped` and `holds.restored` do now.)
- **`caps` in `station.info`** lists what a station can be asked for that an older one cannot (`task_continue`, `station_flags`); the Control Deck offers such a thing only for a station that says so.
- **A station on 0.4.3 in the fleet.** Nothing here crosses stations but the notice (relayed as any notice is) and `task.continue` through the owner's forwarded request, which a 0.4.3 station refuses as a method it does not have: the button is not shown for it. Its panes, restarts and approvals behave as before; a deck served by an updated station still stops asking for a pane that is gone there. A station taken back to 0.4.3 ignores what this version added to its records, and no longer lists the panes that were ended or held back.

## A stopped agent stays stopped, and what is sent to a pane goes as whole items (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is the input and holds part of step 1 of the performance and continuity plan (`crates/terminal/src/input.rs`, `crates/core/src/holds.rs`). The owner's requirement behind it: stops and pauses must hold through failures, and "100% uptime" must not mean agents waking themselves into paid work. What was found on 0.4.2 and was still so on 0.4.4: a stopped agent was woken again by the next message, by the typed nudge and by its hooks, and the turn it was stopped in was continued with that mail; an agent started again after a crash took mail at once; a stop's interrupt key was written like any input, behind whatever was waiting, and a stop of a program that was not reading was reported like any other. No Guarantee is weakened; four lines are added under "Stop, pause and offline".

**Decided by default on 15 Nov 2026** (the owner said "execute" without answering each question; the owner may overrule each, with the switch named):

- **A stopped agent stays stopped when mail arrives, and is released explicitly.** To overrule: `holds.stopped = false`.
- **A session started again after a crash or a reboot waits for the owner before it takes mail.** The consequence: after a crash at night, agent-to-agent work on that station halts until the owner releases it. So "Release all on this station" is one action, in the Control Deck (the station's menu and the recovery notice), on the phone (the same menu), and on the command line (`spandeck pane release --all`), and a per-station setting turns the waiting off: `holds.restored = false`.
- **A held pane is released by typing into it, Release, Release all, or the command line; never by looking at it.**

**The three marks.** A pane's record carries three marks, each on its own:

| Mark | Set by | What it blocks | Cleared by |
|---|---|---|---|
| `paused` | the owner's Pause | mail, and "Continue this task" | Resume (unpause) only |
| `held_stopped` (who, when, and whether the stop reached the program) | a stop of the pane: Stop on the pane, or a "stop every agent" that hit it (an agent that was idle when "stop every agent" was pressed is not marked: that stop is for the work that was running) | mail | the owner's release |
| `held_restored` (when, and why: `crash`, `stop`, `upgrade`) | the station, for every agent it starts again itself after a restart, a crash, or an upgrade that lost terminals | mail | the owner's release |

- **"Mail" is every road a message has to an agent**: the typed nudge that wakes an idle agent, the notice in the answer to its prompt hook and to its tool hooks, and the turn continued at its end. A pane with any mark gets none of them. The message stays stored, unread and not announced; `held.mail` in the pane's view counts it, and it is announced within a second or two of the last mark going.
- **Clearing one mark never clears another.** A paused pane that is stopped, or started again after a crash, and then released is still paused. Release is not Resume.
- **The marks are in the pane's record**, written like a pause (kept until the database has it; Stop on a pane and Release answer `saved`). They are carried through a restart of the pane's program by the owner, a restart by the station after an agent update, and a recovery. The window is the one "Nothing waits for the database" gives a pause: a station killed before the record is written comes back without that mark.
- **Release is the owner's alone** (rule 7): `pane.release {pane}` and `pane.release {all: true}` are on no agent's list, no station's and not the read-only one; they reach another station only as the owner's forwarded request. The ship's log says who released and how (`pane.released`: `release`, `release_all`, `typed`; `station.released_all`).
- **Typing releases, and it is decided at the pane's station**, so it works from a Control Deck of any version, through any station: `pane.input`, `pane.paste`, `pane.send_text` and "Continue this task" from the owner clear `held_stopped` and `held_restored` before what was sent is queued. **Looking never releases.** Attaching, watching, resizing and reconnecting send nothing that counts. A deck's terminal also sends, as input, things nobody typed: that the window gained or lost focus, the mouse, and its answers to the program's questions (where the cursor is, what kind of terminal it is, its colours). The station tells those apart and they release nothing. (Found while building this: without that, opening a held agent's pane released it, since agents ask their terminal to report focus.)
- **An agent's own turn is not blocked.** A held agent that the owner did not stop mid-turn and that goes on by itself (a prompt already typed) runs; it is its mail that waits. Pause and holds are about new work, as Pause always was.
- **The switches.** `[flags] holds = false` (or `station.flags`): no stop or restart sets a mark and none counts; mail is held back by Pause alone, as before this. `holds.stopped = false` and `holds.restored = false` turn off one mark each; a mark already on a pane stops counting while its switch is off. In the config file `holds = false` and `holds.restored = false` cannot both be written (TOML: one name cannot be a value and a table); with `station.flags` they can. Pause is not switchable.

**What is sent to a pane is whole items in one line.** Keys, a paste, a line of sent text and the mail nudge are each one item of the pane's input, written by the pane's own thread in the order they arrived, from whichever connection or station. A sent line's Enter belongs to its item (the pause before it, 30 ms, and 60 ms after a paste, is the pane's thread's; nobody waits for it and nothing lands between the text and its Enter).

- **A stop marks its place** the moment its request is read, before anything is waited for. When it runs: an item sent before the mark and not yet started is thrown away whole; the item being written is cut at the next 4 KB, and if it is a paste the program was told is a paste, the end marker `ESC[201~` is written first, so the interrupt key is not read as pasted text; a line whose text is written and whose Enter is not loses the Enter; then the interrupt keys are written, ahead of everything; what was sent after the mark is kept, waits for the stop, and is written after the keys.
- **Whoever sent what was thrown away is told**, as a count and never the content: `{"chan", "input_discarded": n, "why": "stopped"}` on that client's channel for the pane (through a gateway too), and the deck says "Not sent: the pane was stopped before …". The event `pane.input_discarded` carries the counts per client.
- **A program that is not reading cannot be stopped by a key**, because the key cannot enter a full terminal either. The keys are given two seconds. If the terminal has not taken them, they are taken back and never written late (a key that arrived minutes later would interrupt newer work). The stop then says so and nothing reports that pane as stopped: `pane.stop` is refused with the code `not_reading` and "this program is not reading input: Stop could not reach it; use Kill" (an error, so a deck of any version shows it); "stop every agent" lists the pane under `not_reading`, never under `stopped`, and the stop's row says "1 stopped, 1 not reading input and not stopped: use Kill"; the ship's log has `pane.stop_not_reading`, not `pane.stopped`; the pane's mark says `reached: false`, and the pane says the same words. Kill works on such a pane, and the station keeps answering (measured on the machine it was built on: `station.info` answered in under a millisecond with 20 KB waiting in a pane whose program read nothing).
- **What "the terminal took the key" means.** It is in the terminal's buffer. For a program that reads its terminal, that is the interrupt; a program that stopped reading a moment ago with room still in the buffer is not told apart, and is reported as stopped. That the turn ended is still confirmed as before, from the agent's hook or its screen.
- **The mail pump cannot pass a Pause or a Stop.** Its look at the marks is made again with the pane's input locked, and whatever sets a mark takes back a nudge not yet typed. A nudge that is not typed announces nothing.
- **Stops run off the request threads**, since one waits up to two seconds for a program that is not reading; "stop every agent" stops its panes at the same time, each on a thread of its own.

**What the owner sees.** A held pane's bar: "stopped by you at 13:58 · mail is waiting (2)" or "started again after a restart · takes no mail until released", with **Release**; the list on the left marks it "held"; its menu has "Release (take mail again)"; a station's menu has "Release all on this station"; the recovery notice says "They wait for you, and take no mail from other agents until you release them: type into one, or release them all …" and has "Release all on <station>" beside it in the inbox. On the phone the conversation shows a card with the same words and Release, the pane's menu and the station's menu are the same, and sending the agent a message releases it. `pane.list`, `pane.get` and a conversation's `live` carry `held: {stopped, restored, mail}` (null when not held).

**Mixed versions.**

- **A Control Deck from before this (0.4.4)** has no Release button and does not know `held`. Typing into the pane releases it, from that deck too. The pane's `needs_reason` says "stopped by you at 13:58 UTC: it takes no mail until you type into it or release it" when the pane has no reason of its own, and that deck shows it on the station's tile, in the pane list of a phone and as the title of the pane's dot. A refused stop is an error it shows. The recovery notice's words name the command and "type into one".
- **A station from before this** sets no marks and has no `pane.release`: its panes behave as before, a deck offers "Release all" only for a station that announces `holds` in `caps`, and shows Release only on a pane that says it is held.
- **Stops between versions.** `stop.apply`'s answer gains `not_reading`; an issuing station from before passes over it and counts `stopped`, which never includes such a pane. A newer station stopped by an older one marks the panes it stops, as for any stop.
- A station taken back to 0.4.4 passes over the marks in its records: the panes take mail again.

**Not done here, and said so.** The place of a stop is marked where the request is taken up to be run, in the dispatcher: today every connection's requests are taken one at a time and in order, so that is the moment it is read. When requests are handled in lanes (step 2) the read loop must take the marks itself (`Daemon::stop_marks`, `Pane::mark_stop`), which is what they are for. A pane the pane host holds (Windows, and the option elsewhere) is written through the host: a program there that is not reading should be found out the same way, by the two seconds, but that has not been run. Nor has any of this been run on Windows or macOS, or with a real Claude Code or Codex: the scenario tests use the stand-in agent, on Linux.

## A channel number names nothing on another connection (15 Nov 2026)

The owner's approval: "execute ... the updated performance plan" (15 Nov 2026). This is unit 02a of the performance and continuity plan (`crates/web/src/lib.rs`, `Channels`), and it goes in before requests are handled in lanes, which would widen the fault. What was measured on 0.4.2: every connection of a Control Deck counted its channels from 1, and a page that comes back after a drop keeps a terminal's old number until its new attach is answered, so a key carrying one pane's old number was written to the pane the new connection had given that number to. No Guarantee is changed.

- **Each connection starts counting at a place of its own**: a number below 2^30 from the system's random source, then one more for each channel, for a pane attached, a conversation watched and a pane or conversation of another station passed through this one alike. It never gives 0 or a number it still has open. The frame is unchanged (five bytes, the number in four), and a page uses whatever number an answer gives it, so a page of any version works.
- **What is sent with a number this connection did not give is refused** ("no such channel"), and a key sent that way, which asks for no answer, goes nowhere: typing, resizing and letting go alike. A number that does not fit four bytes names nothing; it used to be cut down to one that fits.
- **Through another station** the browser's number is the serving station's; the pane's station gives a number of its own on a connection made for that one pane, and the serving station puts its own in place of it both ways. So it is the station serving the deck that refuses a stale number.
- **What is left, and said so.** This makes a wrong pane unlikely, not impossible: a number left over names a live channel only if the two connections started within a few numbers of each other, which is a chance of about one in fifty million for a deck with ten panes open. Unit 03b closes it: the page names each attachment with a number it never reuses and the station takes input only for a name attached on that connection.
- **Mixed versions.** Only the station serving the deck matters. A deck served by a 0.4.4 station still counts from 1, for its own panes and for panes of an updated station shown through it; a deck served by an updated station is right for every pane, a 0.4.4 station's included. A 0.4.4 page loaded before its station was updated works unchanged.

## The conversation view (15 Nov 2026, the owner's request)

"I like the Claude mobile app, simple, lets you focus on working with an agent, lets you talk to it. This is a single pane for focus ... I still can see a need though if you need to get back to terminal arrow etc ... make the functionality the same as Claude code but also keep the best of spandeck." Then: "execute ... the mobile plan". The plan's decisions were taken as it recommends; each is the owner's to overrule, and the ones that matter are marked **(default)**.

**Built: the station side (phase M1) and the view (phase M2).** A station can turn an agent pane's session into the items a conversation view shows, serve them a page at a time, send new ones as they are written, and remember how far the owner has read. The exact calls are in `docs/conversation-api.md`. The view is in the Control Deck (`crates/web/assets/chat.js`, and `md.js`, which draws an agent's markdown); what it does is under "The view", below. Answering a question or approving a plan from the view is not built (phase M3).

- **A pane has two faces, on the phone and on the desktop (default):** its terminal, as today, and its conversation: what was said, as readable text, with the tool calls folded away. The terminal stays one tap away and is always the whole truth.
- **Built on the agents' own session files (default).** Claude Code and Codex write each conversation to a file as it happens, and the archive already copies every line of it. The conversation is read from those kept lines, so it is still there after the agent deletes its file, and no shipped migration changed: the index that makes paging cheap is in memory and is rebuilt when asked for.
  - **Both vendors say these files are internal and may change with any release.** So the builder is written to fail in the open. A record it does not know is left out and counted, and every answer carries the count and the kinds ("3 records not understood"), so the view can say that it has stopped understanding and send the owner to the terminal. The raw lines are kept as they were written: a fixed builder reads old sessions again. Fixtures with the shapes of Claude Code 2.1.302 to 2.1.325 and Codex 0.169.0, and made-up words, are in `crates/archive/fixtures/`.
  - **Hooks stay the only thing that decides anything.** The pane's state, its current tool and every approval come from the hooks, as before, and are sent beside the items (`live`). The session file only says what was said.
  - **A reply arrives a block at a time, not letter by letter.** An agent running in a terminal does not write its reply anywhere until a block of it is finished.
- **What an item is.** The owner's message (the words, a count of pictures, and where it came from: typed, queued, another agent); the agent's text, as markdown source; thinking, as a length of time and never its content; a tool call (name, one line of what it did, whether it worked, how long), with its input, output and diff fetched only when its row is opened; a question the agent asked and a plan it proposed, with the answer once given; a sub-agent it started; and notices (compacted, turn ended and how long it took, interrupted, error). A tool call is paired with its result by the id both carry. An item's id is its line in the session and its place in that line, which never changes; the line number is also the cursor ("what came after line N"), so a view that reconnects gets nothing twice and misses nothing.
- **What each agent program gets.** Claude Code: all of the above. Codex: its messages, tool calls with their output, and turn ends; no title, no diff, and whether a call worked is not in its file, so it reads "done". The Codex half was written against real 0.169.0 files, but no live Codex pane has been watched. OpenCode, Antigravity and shells: no conversation; the call says why in a sentence and the view opens the terminal. That a pane was resumed is known from its hooks, not from the file, and is sent in `live`.
- **Who is served, and why the scrubbing Guarantee stands (default).** The Guarantee says other stations and agents see only the scrubbed view of history. The conversation is the raw history, unscrubbed: it has to be, or the owner would read `[redacted]` where the terminal beside it shows the real thing. So it goes to one reader only, **the owner's signed-in browser**, which is neither a station nor an agent, and which is already shown the same words by the pane's terminal (`pane.attach`, `pane.text`).
  - `pane.conversation`, `pane.conversation.detail` and `pane.read` are the owner's: on no agent's list, not on the read-only list, and on no station's list. An agent is refused its own pane's conversation too; it has `recall`, which reads the scrubbed copy, as before.
  - A deck served by another station reaches a pane's conversation as it reaches its terminal: the serving station passes on the owner's request (`rpc.forward`, or for the live stream a connection signed with the fleet key, as for `pane.attach`). **It passes the answer through and keeps none of it**: nothing is written to its archive, its log or its database. What a station can do on another as the owner is not widened by this: it could already attach to the pane.
  - What is new to say plainly: the raw text of a tool's output now crosses the tailnet to the owner's browser as JSON, where before it crossed as terminal bytes. A key an agent printed is in both.
  - Text from a session file is data (rule 6). The station drops terminal escape sequences and control characters and returns text and structure, never markup; the view will insert it as text.
- **The live stream.** While a browser watches a pane's conversation, the station looks at that session's file every 200 ms (the archive's own look is once a second) and sends what is new on the browser's existing connection; when nobody watches, nothing extra runs. Through another station the messages are passed along as a pane's terminal is. The event bus has no replay, and this needs none: the cursor is the resume point.
- **Unread is the fleet's, and is kept at the pane's station (default).** "It's all the same view from spandeck." Each pane has a mark: the line of its session the owner has read to. The mark is kept by the pane's own station (in its key-value table), set through any station's deck as the owner's forwarded request, and every pane in the pane list says `unread`: the agent has said something after the mark. So the dot is the same on every device and whichever station serves the deck. A mark belongs to one session of the pane; it only moves forward; it goes when the pane is closed. Looking at a conversation, marking it read and asking for a tool's detail do not count as the owner being at a keyboard, so a phone showing one conversation is still pushed the notice for another pane.
- **Bounds.** An item's text is cut at 16 KB and a tool's output at 64 KB a page, each with a mark and a way to fetch the rest; a diff at 2,000 lines; a page at 200 items; an index at 100,000 items a session and eight sessions, about 32 bytes an item. Reading is done off the daemon's async work, and the database is asked for a few hundred lines at a time, never held while they are parsed.
- **Cost, measured on the machine it was built on, on a real 51 MB Claude Code session (13,936 lines, 2,961 items):** the first request builds the index in 85 ms; after that, a look with nothing new takes 0.07 ms, and paging through the whole session 200 items at a time takes 85 ms in all. The index was 89 KB. The archive's copy of the file, which exists with or without this, took 0.5 s once.
- **Not built, and not claimed:** answering a question or approving a plan from the deck (M3: today they are shown, and answered in the terminal); a queued message shown before it is sent; a background task's later report tied back to the row that started it; OpenCode's own streaming interface.
- **A station on a version from before this** has none of these calls: asked for a pane's conversation it answers that there is no such method, which the view treats as "no conversation: that station needs an update", and shows the terminal. Its panes have no `unread` and no title in the list. A deck served by an older station is its own older deck, as always.
- **Native app:** unchanged. "In the browser; no native app" stands until the plan's later gate.

### The view (phase M2, 15 Nov 2026)

The owner showed two pictures of the Claude app on a phone: a list of sessions with a dot on the unread ones and "New session", and one conversation with the reply as comfortable text, Copy and Read aloud under it, a "3 running tasks" link and a message box. The view follows them, and keeps what spandeck has that the app has not: the terminal one tap away, the fleet, approvals held by a hook.

- **A pane has two faces, chosen with "Chat | Terminal" on its bar.** Terminal is the pane as it always was. Chat is its conversation. **Chat never attaches to the pane**, so it sets no size and takes control from nobody ("One size per pane"): it watches the conversation, and sends what the phone's message box already sent. A shell, an agent spandeck cannot read (OpenCode, Antigravity), an agent that has not said which session it is in, and a pane on a station from before this are their terminal, and the bar says why in the place of the switch ("Terminal only: it runs a shell, not an agent"). A pane that gets a conversation later (its first hook arrives) gets the switch then.
- **What the conversation shows.** The owner's messages as bubbles on the right (one from another agent, a schedule or a background task on the left, saying which); the agent's text as markdown at reading size; a run of tool calls folded into one line ("Ran 6 tools · 48 s"), which opens to a row for each call and a row to what the call was given, what came back (cut, with "Show more") and, for an edit, the change as a diff; thinking as "Thought 12 s" and never its content; a question or a plan as the agent wrote it, with the answer once given; turn ended, stopped, compacted and errors as quiet lines; a kind this version does not know as a quiet line with its name. When the station left records out it says how many and offers the terminal. Under a finished reply: Copy, and Read aloud where the browser can speak. The page above is asked for when the top is reached. The log stays where it was read, and follows new items only while the owner is at the end.
- **Above the message box, while the agent works:** "Working · Bash: cargo test · 42 s" (the time by the station's clock, never the browser's against it), with "Peek", which shows the last lines of the terminal; "3 running tasks" when the agent has sub-agents running; and Send becomes Stop while nothing is written.
- **Cards, pinned above the message box.** An approval the hook holds: what it asks, a reason, Allow and Deny (`approval.answer`, as everywhere). **Only what a hook holds gets buttons.** A question or a plan that waits is shown with "Answer in the terminal". When the pane needs the owner and there is nothing the view can answer (a picker, a login, a prompt after an approval ran out of time): "Waiting in the terminal: <reason>", the terminal's last lines, the keys 1, 2, 3, Enter, Esc and the arrows (`pane.input`), and "Open terminal".
- **The message box.** Sent as the phone's box always sent: one paste, then Enter (`pane.paste`). What is being written is kept for each pane through redraws and between Chat and Terminal. "+" sends a photo, a camera shot or a file (`pane.drop_file`: the station writes it and types its path, so it works for every agent). The microphone dictates where the browser can; where it cannot it says so, and says that it needs the station's HTTPS address when that is the reason. "/" offers Claude Code's text commands.
- **The phone's list opens on what matters.** In order: **Needs you** (approvals with Allow and Deny, then agents that wait or stopped on an error), **Pinned**, then **Recents**: every agent pane in the fleet, the one that changed state last first, each with its session's title (Claude Code names its sessions) or the pane's name, where it is and what it is doing, and a dot when it has said something not read. "Recent | By station" switches to the list as it was, with every control it had (stations, projects, layouts, Watch, New, Wake, Start, Stop, usage, performance, stopping the fleet): nothing was removed, it is one tap away. "+ New session" stays at the bottom: an agent, a station, a project or folder, "Continue the last conversation" and an optional first message, then the new pane's conversation.
- **Read, and "Next".** A conversation is marked read (`pane.read`) when its newest item is on screen and the page is in front; never by asking for it. "Next ›" on the bar, with a count, goes to what else waits in the fleet: approvals oldest first, then agents waiting for something else, then errors, then agents that finished and are unread.
- **On a computer** the same view is a pane's other face: "Chat" on a terminal's title bar, in a pane at full size and in a layout, and the switch on the conversation's bar leads back.
- **An agent's text never becomes HTML (rule 6).** `md.js` parses markdown to a tree and builds elements itself (`createElement`, text nodes); nothing is given to the browser to parse. It makes paragraphs, headings, emphasis, code, lists and task lists, quotes, tables, rules and links, and no other element; the only attributes are `class` and a link's `href`. HTML in the text is the characters typed. A link is http or https or it is not a link, and it opens (new tab, `noopener noreferrer`) only after a sheet has shown where it leads. A picture is never fetched: it is a link with its label. The content policy is unchanged. A test draws text written to attack the page and checks exactly this.
- **The screen reader** is told a finished reply once, in a quiet region of its own; the log itself is silent, so every tool call is not read out. Touch targets are 44 px; text follows the deck's size and theme; holding the microphone has a tap that does the same.
- **One addition at the stations: `pane.titles`**, the titles of this station's panes' sessions. A title is made from what was said, so it is the owner's alone, as the conversation is (on no agent's list, no station's, not the read-only one), and it is not put in `pane.list`, which agents read. It reads only the lines written since it last looked, and does not build a session's index.
- **A pushed notice (ntfy) carries the address of its pane** (`Click`), at the station's own tailnet address, so touching it opens the pane, which on a phone is its conversation. A station with no tailnet address sends none. Not tried against a real ntfy.
- **Decided by default; the owner may overrule each:**
  - The phone's list opens on Recent, not By station (each device remembers which it last chose).
  - An agent's pane opens as Chat on a phone and as Terminal on a computer.
  - Which face a pane shows is the device's own choice, per pane. It is not saved in a layout, and is not the same on every station.
  - Holding the microphone fills the box and never sends: a misheard instruction to an agent with tools is costly.
  - A question and a plan are answered in the terminal for now.
  - Recents are ordered by when a pane last changed state, not by its last output, so the rows do not move about while agents print.
  - A link asks before it opens, every time.
- **Not built in this phase:** answering a question or a plan in place; choosing the model, the effort or the permission mode from the view; a list of ended conversations; search in the list; holding to talk on an iPhone at the plain address (its browser offers no speech there: phase M4, with HTTPS); web push; the conversation in a phone's one-pane-at-a-time layout view, which is still the terminal.
- **What a test cannot tell, and wants a look on the owner's phone:** the keyboard and the safe areas; dictation and holding to talk; reading aloud and the silent switch; the camera and photo picker; whether the page comes back after the phone was put away (an open fault of iOS on plain `ws://`).

## AgentVault (14 Nov 2026)

- spandeck and AgentVault stay separate programs. spandeck works without a vault.
- The vault is the only place a token is issued, and only when the owner approves on the vault's own page. The vault passphrase is never typed into the Control Deck. Approval opens in a small pop-up window on the vault's address.
- One token per station, held by spandeckd in a file only the user can read. Panes and agents never get the token, and keys are never put in a pane's environment.
- The token can list keys and send requests through the vault's proxy, read-only by default, and is pinned to the station's Tailscale node.
- spandeck finds the vault by its Tailscale name; the address is never hard-coded. `[vault] url` in the config overrides it.
- Tokens do not expire by default. Rotation is a per-station setting (never, or every N hours, at least 1) that only the owner changes; spandeckd rotates by itself.
- The owner is told when the setting changes outside the Control Deck, or the token is swapped or refused.
- Connecting a station is the only step: by default its agents may use every key the owner allowed that station's token at the vault (changed 14 Nov 2026 at the owner's request; before, a project had to list its keys). A project can narrow its agents with `[vault] keys` in `.spandeck/project.toml`.
- When a station has a token, a raw key in an agent's command is blocked and reported to the vault; one pasted into a prompt, or found in a transcript, is reported.
- **Connect prompt** (the owner's request, 14 Nov 2026: "there should be nothing I need to do"). A Control Deck that opens on a station that found a vault and has no working token says so once, in a bar that blocks nothing, with one button that starts the connect flow. "Not now" is kept by the station (so it holds in every browser), is undone from the Vault screen, and is forgotten when the station connects. No prompt when no vault was found or `[vault] enabled = false`.
- **Check and repair.** spandeckd checks the chain from an agent to a key when it starts, when a Control Deck opens (at most once a minute) and when asked (`vault.check`, the owner's only): the vault's address, its lock, the station's token (accepted, and tied to a machine), the key list, and what panes need (spandeck's own program and socket; Antigravity's plugin). It repairs without the owner: a token the vault calls overdue is swapped, Antigravity's plugin is rewritten. Each thing it cannot repair is one sentence with one action, in `vault.status` (`checks`, `health`), on the Vault screen and in `spandeck doctor`, and is told to the owner once (`vault.alert`), not on every check and not again after a restart.
- A repair never gets a token any way but the owner's approval at the vault.
- A connected station shows its token to no address but the one that issued it (a security fix of 14 Nov 2026: no other machine can ask for the token by claiming to be a vault). When that address stops answering and another AgentVault answers on the owner's machines, the station does not try its token there: it says "The vault seems to have moved to <address>" and offers Reconnect, the ordinary approval. Following a move with the existing token is behind `[vault] follow_moves = true`, off by default: relaxing the guard is the owner's decision, and the owner has not made it.

## Agent programs (14 Nov 2026, the owner's request)

- OpenCode and Antigravity are agents a pane can run, wired to spandeck's tools and skill when the pane starts. Neither can block a tool call or pass an approval to the Control Deck, so their rules are guidance.
- A pane started for an agent that is not installed on its station installs it first, in the pane, with the vendor's own install command (or the way the owner chose for that station, see below). That command is fixed in the code (a vendor's script is fetched over HTTPS only) or set in the station's own config; it never comes from a caller or another station.
- Looking for an agent's program has four answers, never fewer (14 Nov 2026, after a fault on the owner's Mac: a Codex whose real binary was gone was called installed, and one that was slow to answer was called not found): not installed; installed (it answered when asked its version); installed but not working (it exits with an error or cannot be run); installed but it did not answer in time, which is unknown, not broken. A program that is slow to say its version is never killed.
- When a program is in several folders spandeck looks in, the first copy that answers is used, not the first that exists.
- A pane started for a program that is installed but not working offers a reinstall in the pane, the same way a missing one is installed: what was found and the program's own error line, the command, Ctrl-C skips. Success is the program answering afterwards, not the installer's exit code. Whether an install should ask before it runs is still open with the owner; for now it announces the command and Ctrl-C skips.
- Each agent has the ways it can be installed that its vendor documents: the vendor's own script (the default), npm, Homebrew. A way is offered on a station only when its tool is there. The owner's choice is kept per station and per agent in the station's state; `install_cmd` in the station's config still wins over everything. Every command is fixed in the code, taken from the vendor's documentation or a package registry; a way that could not be confirmed is left out. Installing, like updating, is the owner's to do (`agents.install`): an agent cannot.
- The owner can see each agent's version on each station and update one or all of them. After an update that changed the version, an idle pane of that agent restarts into its conversation; a pane in a turn, or waiting on the owner, restarts when it is next idle. Updating is the owner's to do: an agent cannot.

## Add a machine (14 Nov 2026, the owner's request)

- The fleet screen ends in an "Add a machine" tile. It lists the Mac and Linux machines under the owner's Tailscale login that are online and not stations; phones, Windows, tagged and shared machines are left out. The station the owner is using connects to the one picked over SSH, runs the same install script as the README, starts spandeck there now and at login, and has it ask to join as `spandeck fleet --join` does. The tile then shows the join code.
- **The approval step stays.** The new station is approved with the usual control, by its code. A code that arrives over SSH is shown only if this station holds a waiting request with the same code. The join step is one place in the code (`JoinBy` in `crates/core/src/add.rs`), so a single-use ticket could replace the code later; no ticket exists.
- **Its own setting, off by default: `add_machines = true`** in the config of the station that does the adding, not `remote_start`. Both let a station run a command on another machine, and both are off until the owner turns them on at that station. They are separate because they differ in what they risk: `remote_start` runs one fixed command on a machine that is already a station, with access the owner already set up; adding installs software on a machine spandeck has never run on, and can use a password typed into the deck. An owner who wants one has not agreed to the other. The picker works while it is off and says how to turn it on; nothing is run and no password is accepted.
- The owner can also turn it on, and off again, from the tile itself (changed 14 Nov 2026: the owner clicked the tile and asked why they could not add a machine). The switch is kept in the station's state, is logged, is the owner's alone (`fleet.add_enable` is on no agent or station list and is never forwarded), and applies only to the station whose Control Deck they are using. It stays off until the owner turns it on.
- **Only the owner, and only at the station being used.** The methods are on no list for agents or other stations, and are never forwarded between stations in either direction, so a password never travels from one station to another.
- **The password** is asked for only after a first try without one fails (Tailscale SSH or an SSH key that already works needs none). It is used for one connection and held in memory until ssh has asked for it once, or the connection ends. It is never written to a file, a log, the ship's log, an event, an error or a command line or environment: ssh gets it by running spandeck itself as its askpass helper, which is handed it once over a private socket, and only for a prompt that asks for a password. A second prompt gets nothing, so a wrong password is tried once. The ship's log records who added which machine as which user and how it went.
- **Host keys.** The address is the one the local Tailscale client gives for the machine picked, and must be a Tailscale address; a caller names a machine, never an address. The first connection saves the machine's host key in `known_hosts` in the state directory (ssh's accept-new); a different key later is an error, shown plainly, and nothing is sent. The owner's own ssh config is not read, so it cannot redirect the connection or switch checking off.
- What the machine prints is shown as it runs. It is text from somewhere else: control characters are dropped and the Control Deck inserts it as text.
- `add_machine_cmd` replaces the ssh command (`{user}`, `{host}`, `{known_hosts}`); the script arrives on its standard input. The script uses only commands every release has, since the release it installs may be older than the station that sends it.

## Adding a station that is running, and uninstalling one (15 Nov 2026, the owner's request)

"I dont know how to add these two machines, I shouldnt have to go to that machine, I should just say add to the fleet but its asking me to join their fleet." "I also cant delete the machine then re-add it."

- **"Add X to this fleet…"** is on the tile and in the menu of a station that is running but is not in this fleet. It replaces the instruction to go to that machine and type `spandeck fleet --join`, and it replaces "Join X's fleet…" and "Merge this fleet into X's…", which are no longer on any Control Deck menu: the owner adds to the fleet they are looking at. `spandeck fleet --join` stays in the command line, unchanged.
- It is Add a machine without the install (`fleet.add` with a station's name). The station the owner is using connects to the other over SSH, which is what shows the request is the owner's; finds the spandeck command there (where the installer puts it, then the PATH, then `~/.cargo/bin`); checks it answers; and has it ask to join this station, as `spandeck fleet --join` does. The code it is given appears here and is approved here, with the usual control. The switch, the user name, the password, the host key and the progress are those of Add a machine.
- **Its fleet-mates come with it**, because a join is a merge. The dialog says so beforehand, and names them once the request has arrived. A station tells whether it brings its mates in what it says of itself to any device under the owner's login (`station.hello`: `merge`, with its operating system). One that does not say so runs a version from before the merge: the dialog says it will join alone and that any station it shares a fleet with stays behind, to be added the same way.
- **The address** is the one this station found that station at, and it must be a Tailscale address or one the owner wrote under `peers` in this station's config. A caller names a station, never an address.
- **"Uninstall spandeck on X…"** is in the menu of every other station that answers (`fleet.uninstall`). In order:
  1. If X is in this fleet, it is removed from it exactly as "Remove this station from the fleet" does: its panes closed, a new key for the stations that stay, X forgotten. The browser that asked gets its new token in the reply.
  2. Over SSH, spandeck on X is told what a removal with "also stop spandeck there" tells it (`station.leave` with `stop`, through its own command line): it closes its panes, takes its login service out and ends. That code touches the login service only when the account it runs under has one.
  3. The script deletes the programs: `spandeck` and `sd` where the installer put them, or where the command was found if it was built from source (on Windows `spandeck.exe`, `sd.exe` and `spandeckd.exe`), and the copies kept for upgrades under the state folder.
- **Kept by default: the state and config folders**, which hold the station's history, archive and settings, so that adding the machine back picks them up. The tick box "Erase everything" deletes them too; a folder is deleted only if it is spandeck's (it holds the database, the key or the config, or is named `spandeck`), and never the home folder. Helpers' worktrees live under the state folder and go with it. **The owner's project folders are never touched**, with or without the box.
- If spandeck was not running on X, the script takes the login service out itself, and only if the service's own file is in that account. It never stops a process by name. No test reaches a real login service: the test's machine has stand-ins for `systemctl` and `launchctl` first on its PATH and a home folder of its own, and the test checks the stand-ins were what was asked.
- If the SSH step fails after step 1 (a password is needed, say), nothing has been deleted on X: it is running, outside the fleet, and the same dialog asks for the password and goes on from step 2. A station that does not answer cannot be uninstalled: "Remove" takes it out from the fleet's side. The station the owner is using cannot uninstall itself.
- The dialog names the station and its pane counts, opens on Cancel and acts only on the red button. Afterwards the machine is listed under Add a machine again.
- **Authority.** `fleet.add` and `fleet.uninstall` are the owner's alone, on no agent's list and no station's, never forwarded in either direction, and refused unless adding machines is turned on at the station being used (`fleet.add_enable`, or `add_machines = true`). The ship's log records who, which station, which user and how it went (`fleet.add`, `fleet.uninstall`).
- **Browsers signed out in a fleet stay signed out when stations arrive.** The key is handed over with the list of browsers signed out in that fleet, at a join and with `fleet.rekey`, and the station that takes the key refuses them too. Before, a station that joined accepted every token made with the key, including one the owner had signed out. A station on an older version ignores the list.
- After a request to join, the asking station looks for its answer every 0.4 seconds for the first 16 seconds, then every 1.5 seconds as before.

## Usage and cost (14 Nov 2026, the owner's request)

- Token counts are only what an agent wrote in its own session data: Claude Code's and Codex's session files, OpenCode's session database. Antigravity keeps nothing spandeck can read, and is shown as not reported. Nothing is typed in by the owner.
- Counted per conversation and per model, sub-agents included under the model that ran them; a model call written more than once is counted once. A new conversation starts from zero; the station keeps its totals.
- Cost is an estimate at list prices and is called that wherever it appears, with the list's source and date: a subscription is not billed per token.
- Prices and context windows come from a public list (models.dev) that spandeckd fetches by itself once a day and keeps. The request carries nothing about the owner or a project. No price or window size is written into the code; a model the list does not name has no price. `[prices]` in the config is an optional override, never needed.
- The context gauge uses the window the session data states (Codex), else the list's.

## Guarantees (contracts the build must meet)

### Tasks
- Fields: goal, acceptance criteria, agent, station, workspace, dependencies, outputs, review outcome, resume information.
- States: queued, running, waiting for approval, blocked, completed, failed, cancelled.
- An agent going quiet is not completion. A task is completed only by an explicit result or a sign-off.

### Stop, pause and offline
- Work already running continues if the network drops or the controlling station disappears.
- No new remote assignment is accepted without a valid task authorization; these expire.
- Pause: no new work is delivered; the current turn finishes.
- Stop: the agent's current turn is interrupted; the process stays.
- Kill: the process ends.
- A stop never reports a program it could not reach as stopped: a program that is not reading its terminal is listed as not reading, and the owner is told to use Kill (15 Nov 2026). What a stop can know is whether the terminal took the key, not whether the program read it: while a terminal that nobody reads still has room (its first few kilobytes), the key goes in and the stop says stopped.
- A stopped agent stays stopped: no mail reaches it by any road, typed or through a hook, until the owner releases it. An agent the station started again after a restart waits for the owner the same way. (Both decided by default on 15 Nov 2026 and switchable per station; see A stopped agent stays stopped.)
- Pause, the stop's mark and the restart's mark are apart: releasing a pane never ends its Pause, and no mail reaches a paused agent by any road.
- Only the owner releases a pane, and never by looking at it; no agent and no other station can.
- The Control Deck shows three separate states: stop requested, stop confirmed, station unreachable. It never implies an unreachable station has stopped.
- A stop request for an unreachable station is delivered on reconnect and applies only to the work that was running when it was issued.

### Messages
- Every message has a unique id. Delivery is at least once, duplicates dropped by id, so a reconnect cannot start the same task twice.
- Ordering is guaranteed within a thread only.
- Received and acted-on are separate acknowledgments.

### Workspaces
- The parent agent, or the user, integrates a helper's branch. A conflict goes back to the helper as a task.
- After a crash the worktree and branch are kept, and the task is marked failed with its resume information.
- A sign-off names the commit reviewed and becomes stale if the code changes.

### Trust
- The user at the Control Deck has full authority on every station.
- An agent has only what its task grants. Permissions are separate: discover, read history, execute commands, administer a station. Agents never get administer.
- A station removed from the fleet can no longer act on the stations that took the new key: its signed calls are refused and browser tokens made with the old key are not accepted.
- A station that joins another fleet never leaves a station of its own fleet behind: each takes the same key, at once or when it is next seen.
- A request to be let in can be answered at any station of the fleet, by the owner only, never by an agent.
- Every station of a fleet lists the same signed-in browsers, and a browser signed out at one is refused by all, including a station that was off, as soon as it is back.

### Sharing and archive
- Captured events and posted findings: on by default. Transcripts via recall: own always; same project scrubbed; cross-project opt-in.
- Raw history stays on the station that recorded it. Other stations and agents only see the scrubbed view. Scrubbing is best-effort. The owner's own signed-in browser is neither: it is shown a pane's conversation as it was written, as it is shown the pane's terminal, and a station that passes that on to it keeps none of it (15 Nov 2026; see The conversation view).

### Enforcement
- Observing an agent and enforcing a rule on it are separate channels. Screen detection observes; only a hook or approval channel can block.
- A rule is shown as enforced for an agent only where that agent's integration can block it. Elsewhere it is guidance.

### Upgrades
- Before: a version compatibility check between stations. After: a health check, and rollback to the previous binary if it fails.
- If live handoff does not complete, terminals are lost and agents resume by session id.
- Live handoff is a release acceptance test on macOS and Linux.

## Recommended defaults
- Helpers always start in a fresh pane; helpers cannot delegate further unless a role allows it.
- The ship's log keeps each tool call's name, timing and result; full contents live only in the session archive.
- The ship's log is best effort: under a locked database or a full disk its oldest waiting entries can be dropped, and are counted. A pane's record and the safety records (a stop, a pause, an answer to an approval) are tried again until they are written (15 Nov 2026; see Nothing waits for the database).
- Processes do not survive a daemon crash; agents resume by session id.

## Testing rules (from the Build and test plan tab)
- Test where spandeck can break: the terminal, each agent integration, the Guarantees, the link between stations, upgrades. Target 150 to 300 tests (raised from 250 on 15 Nov 2026, with the performance and continuity plan; its new cases that start a station are a few scenario tests with many assertions each, marked ignored and run with `--ignored`, not one test per case).
- A test needs a reason: a Guarantee, a phase's acceptance criterion, or a real bug. No tests of trivial code, no mocks of our own modules.
- Every-change tier under 90 seconds; merge tier under 10 minutes. A flaky test is fixed or deleted within a day.
- The station link sits behind a swappable transport so the message relay runs under Turmoil.

## Windows (14 Nov 2026, the owner's request: a Windows PC as a full station)

Built and tested on a real Windows 11 machine (rtx6000) since 14 Nov 2026; each line says
what was decided and why, and "unlike Unix" lines say what the owner gets less of. What has
not been tried on a real machine is said where it applies.

- **Native, not WSL.** x86-64, Windows 10 1809 or later (the first with ConPTY) and Windows 11.
- **Rule 4 of AGENTS.md now reads:** platform code lives only in `crates/terminal/src/sys/`:
  `unix.rs`, `windows.rs`, and `mod.rs` which picks one. Everything that differs by system
  (terminals, the local socket, private files, process control, the shell, start at login,
  keep-awake) is behind that one interface, and no other file in any crate names `cfg(unix)`,
  `cfg(windows)`, `nix`, `libc` or `windows-sys`. A value that differs (a folder, a command)
  is asked of `sys`, or chosen by `if sys::WINDOWS` in ordinary code that is compiled and
  checked on every system, never with a `cfg` where it is used. Exceptions, each one line:
  `spandeckd.rs` (the attribute that makes it a windowless program); a test that cannot run
  on Windows carries `#[cfg_attr(windows, ignore = "<the reason>")]`; a test file for one
  system only begins `#![cfg(unix)]` or `#![cfg(windows)]`. `pty.rs` keeps the types every
  system shares. Reason: the rule was written so a Windows port replaces one
  place; it is now a folder instead of a file because the port is more than the PTY.
- **Terminals: ConPTY** (`CreatePseudoConsole`), one per pane, with the program started by
  `CreateProcessW` inside a job object that is ended when it closes. Kill is ending the job
  (the whole tree, as `killpg` is on Unix). Hang-up is closing the pseudoconsole, which tells
  every program on it to close. Interrupt is Ctrl-C typed into the pane, as on Unix. A pane's
  exit is its first program's exit code (there are no signals, so `ExitInfo::Signal` never
  appears). A program that is a `.cmd` or `.bat` file (npm's `claude.cmd`) is run through
  `cmd.exe`, with every argument quoted the way Rust's standard library does it so that `&`,
  `|` and `%NAME%` in an argument stay text; an argument with a line break is refused.
  Because the job ends with the daemon, no pane's program outlives a daemon crash: the
  job belongs to the pane host (below), not to the daemon.
- **Local socket: a named pipe**, `\\.\pipe\spandeck-<hash of the state folder>`, in place of
  the Unix socket, behind one `sys::local` interface (listener, async stream, blocking client)
  that the server, the client, the askpass helper and the tests all use. Only the same user
  can open it: the pipe's access list names that user alone, remote clients are refused, and
  the daemon must be the pipe's first creator. The client checks that the pipe it opened is
  owned by its own user before it sends its token, so a pipe another account made first under
  the same name gets nothing. The token is still required, as on Unix.
- **The pane host** (the owner's decision, 14 Nov 2026: "build the extra helper"). Windows
  cannot replace a process's program in place, and a pseudoconsole belongs to the process
  that made it, so on Windows the panes are not in the daemon: `spandeck-pane-host.exe`, a
  small program of its own, owns every pseudoconsole, job and program, and the daemon is its
  client over a named pipe only the same user can open. So an upgrade, a restart and going
  back to the previous binary keep every terminal on Windows as they do on Unix
  (`live_handoff` is true everywhere), and the Upgrades Guarantee and its tests are the same
  on both. The new daemon is a new process there (on Unix it is the same one).
  - **The screen stays in the daemon.** The host knows nothing of screens, agents or
    projects: per pane it keeps the terminal, the exit status, and the last 8 MB the program
    wrote, each byte numbered. At an upgrade the old daemon hands the new one its picture of
    each screen (as on Unix) and the number of the first byte it did not take; the new one
    asks the host for output from that byte on. Nothing is lost or shown twice unless a pane
    writes more than 8 MB while no daemon is reading, and then the oldest of it is.
  - **A daemon crash no longer ends the panes on Windows.** The next daemon finds them in
    the host and rebuilds each screen by replaying what the host kept: the screen is right,
    and scrollback goes back as far as those 8 MB. This changes a recommended default
    ("processes do not survive a daemon crash") for Windows only; on Unix it stands. So that
    panes nobody can reach are not kept for ever, a host with no daemon ends its panes and
    itself after ten minutes (the log-on task restarts a failed daemon within one or two).
    Stopping the station on purpose ends the panes and the host at once.
  - **The host is not upgraded while it holds a pane**: it cannot be without ending them.
    Its protocol is versioned and only grows; a daemon speaks every host protocol back to 1
    and never asks an older host for what it does not have, so an old host keeps serving its
    panes under a new daemon for as long as they live. A host older than the daemon is
    replaced by itself at the first moment it holds no pane (`station.info` shows
    `pane_host.outdated` until then). A change the old protocol cannot carry would need the
    panes ended: such a release must say so before it is installed, and the owner decides
    when. None exists.
  - If the host itself dies, its panes die with it (their jobs close); the daemon says each
    ended and starts a new host for the next pane. Agents are then resumed by session id at
    the next daemon start, as after a reboot.
  - On Unix the host is not used (exec in place needs none); `SPANDECK_PANE_HOST=1` turns
    it on there, which is how it is tested on Linux.
- **The installed program is replaced by renaming.** A running `.exe` cannot be overwritten
  but can be renamed, so an update moves `spandeck.exe` to `spandeck.exe.old` and puts the new
  one in its place; the old file is removed at the next start. `state\bin\running` and
  `previous` are hard links as on Unix (same volume), else copies. The same goes for the
  pane host's file while it runs.
- **Start at login: a per-user Scheduled Task** ("spandeckd", at log on, restart on failure,
  no time limit, runs on battery), not a Windows Service: a service runs in session 0 without
  the user's profile, PATH or the agents' logins. The task runs `spandeckd.exe`, a windowless
  program that starts `spandeck.exe daemon` with no console window and waits for it, so no
  window opens at log on and the task's restart-on-failure sees the daemon's exit code.
  **Unlike Linux with linger, the daemon runs only while the owner is logged in** (a locked
  screen is fine; logged out is not). The owner accepted this (14 Nov 2026: the machine logs
  on by itself).
  **Not yet checked on the real machine (asked for on 15 Nov 2026):** whether the task
  restarts a daemon that crashes after an upgrade in place. On Windows the upgraded daemon is
  a new process, which `spandeckd.exe` did not start and does not wait for, and the one it did
  start has ended; as the code reads, the task then sees its program end and nothing watches
  the daemon that is running. If the check on rtx6000 shows that, `spandeckd.exe` is to follow
  the station's pid file instead of its own child. Nothing was changed without the check.
- **Keep-awake** is `SetThreadExecutionState`, held by `spandeck keep-awake` (the same shape
  as `caffeinate` and `systemd-inhibit`: a helper that holds the machine awake while it runs).
  The helper ends when the daemon does. It does not stop a laptop sleeping when its lid shuts.
- **Shells.** A shell pane runs PowerShell 7 (`pwsh.exe`) when installed, else Windows
  PowerShell, else `cmd.exe`. One shell line (an install or update command from the catalogue)
  runs through Windows PowerShell 5.1, which every Windows has
  (`powershell -NoProfile -ExecutionPolicy Bypass -Command`); nothing needs PowerShell 7. Install-before-launch
  is not a second script in another language: on Windows the pane runs
  `spandeck install-then-launch`, the same steps written in Rust (say what was found, show the
  command, run it in the pane, Ctrl-C skips, start the first copy that answers).
- **The agent catalogue has a Windows list**, read from each vendor's documentation on
  14 Nov 2026: Claude Code (PowerShell script, npm, WinGet), Codex (PowerShell script, npm),
  OpenCode (npm only: its page has no Windows installer and says Windows package managers are
  not supported), Antigravity (PowerShell script). All four document native Windows. The
  update commands of Codex, OpenCode and Antigravity were read from the programs on Linux and
  are not confirmed for Windows.
- **Hooks.** Claude Code on Windows runs a hook in Git Bash when that is installed and in
  PowerShell when it is not; no one command line is right in both, so spandeck's entries name
  PowerShell (`"shell": "powershell"`) and use `& '<path>' hook claude`. Each hook then costs a
  PowerShell start; if that proves slow on the real machine, the no-shell form (`command` plus
  `args`) is the next thing to try. Codex documents no way to name the shell for a hook on
  Windows: the same line is written and is unverified, and screen detection covers Codex
  where its hooks do not fire, as on Unix.
- **Folders.** State in `%LOCALAPPDATA%\spandeck`, config in `%APPDATA%\spandeck`
  (`SPANDECK_STATE_DIR` and `SPANDECK_CONFIG_DIR` still win). Home is `%USERPROFILE%`; `~` means
  that. A program name is looked for with each extension in `PATHEXT`. Paths are compared as
  the file system compares them (by the file's identity, not its spelling).
- **Private files** (the client token, the fleet key, the vault token, agent setup): the
  state and config folders get an access list of the user, SYSTEM and Administrators only,
  not inherited from the parent, when the daemon starts; files written in them inherit it.
  That is what a default profile folder already has; setting it makes it true when
  `SPANDECK_STATE_DIR` points somewhere else. Administrators can read them, as root can on Unix.
- **Tailscale** is asked through its CLI on every system (`tailscale status --json`,
  `whois --json`), never LocalAPI, so Windows needs only the program's place:
  `tailscale.exe` on PATH, else `%ProgramFiles%\Tailscale\tailscale.exe`.
- **Install and update.** `scripts/install.ps1` is `install.sh` for Windows: the release zip
  for `x86_64-pc-windows-msvc`, SHA-256 checked, installed in `%LOCALAPPDATA%\Programs\spandeck`,
  added to the user's PATH, the task registered. The release has `spandeck.exe`, `sd.exe` and
  `spandeckd.exe` in a `.zip`; `station.update` picks it and unpacks with the `tar.exe` Windows
  ships. Other processors (ARM64) are not built yet.
- **Add a machine can add a Windows machine** (the owner's decision, 14 Nov 2026). The
  picker lists Windows machines too. The station connects with the same `ssh` command and
  hands the machine a Windows PowerShell 5.1 script with `install.ps1` inside it (as the Unix
  script carries `install.sh`): install, register and run the log-on task, wait for spandeck
  to answer, ask to join. The line that reads the script there has no `$` and no quote of
  its own inside, so it means the same whether that machine's OpenSSH hands it to `cmd.exe`
  (the default) or to PowerShell. The approval step is unchanged. It needs the OpenSSH
  server on there, which Windows ships switched off and only an administrator can add, and
  the owner logged on there (the station runs in their session, not in the SSH session,
  which ends). Its own failure sentences: the OpenSSH server not installed or not running;
  Windows refusing to run spandeck (Smart App Control blocks programs it does not know, and
  releases are not signed); installed but not started because nobody is logged on. The
  script is run on a real Windows in a test as far as its network check; a whole add of a
  Windows machine has not been done yet. A Windows station adding another machine uses the
  same code with `ssh.exe`; typing a password that way (askpass) is untried on Windows.
- **Certificates on Windows: the system's verifier, with the Mozilla roots as a second
  source** (15 Nov 2026, after a fault on rtx6000: the first contact with the vault failed
  with `UnknownIssuer` on a good Let's Encrypt chain, and worked once curl had connected to
  the same address). Windows keeps only the roots it has needed and fetches others on
  demand; that fetch did not happen for spandeck's check. Which of Windows' rules stopped it
  was not established: the machine has the root now, so the state cannot be made again. The
  fix does not depend on the answer: when Windows cannot build a chain to a root it has,
  the same Windows verifier is asked again with the Mozilla root list carried inside
  spandeck (`webpki-root-certs`). Verification is not weakened: Windows still checks names,
  dates, usage and signatures, and a root an organisation added to Windows still works. The
  cost: a public root the owner removed from Windows by hand is still trusted by spandeck if
  Mozilla lists it, and the carried list is as old as the release. Every outgoing client is
  made in one place (`crates/core/src/http.rs`). macOS and Linux are unchanged.
- **Smart App Control.** Where it is on, Windows refuses programs it does not know, which
  includes every spandeck build, since releases are not signed. The owner turned it off on
  rtx6000. Signing the Windows release is what would make that unnecessary; it is not done.
- **Not on Windows yet:** wake-on-LAN of a Windows station (its network card's address is
  not read), starting a stopped Windows station over SSH (`fleet.start` runs a Unix line),
  usage figures for OpenCode (where its database is on Windows is not documented), and the
  Codex sandbox repair (a Linux problem). ARM64.
- **Tests.** On rtx6000 the whole suite runs (`cargo test --workspace`): everything passes
  except the eight tests that drive a browser, because no Chrome is installed there; they
  have never run on Windows. A test that needs a Unix shell, a signal or a tar.gz release is
  marked ignored on Windows with its reason (about thirty); nothing changes on macOS or
  Linux. Windows-only tests cover what is new: ConPTY (input, exit code, resize,
  environment, a `.cmd` file's arguments, kill ending the whole tree, hang-up), a station
  end to end (a shell pane over the pipe, an agent's hooks, every pane kept through a daemon
  crash, the state folder's access list), `install.ps1` against a local release, and the
  script Add a machine sends. The pane host and the local socket are tested on every
  system. CI has a `windows` job with the same tests; the scenario step reports without
  failing the job until the browser tests have been seen to pass there.
